# LLM/AIのプライバシー・セキュリティ

データ漏洩、モデルセキュリティ、プロンプトインジェクション、差分プライバシー、プライバシー規制に関わる設計・実装を見る。

## チェックリスト

### 1. LLMのファインチューニング済みモデルや本番モデルに対し、メンバーシップ推論攻撃や訓練データ抽出攻撃を定期的にシミュレーションしているか
- **なぜ重要か**: 機密データでファインチューニングしたモデルは特異な例を記憶しやすく、実際にSSN・クレジットカード番号・パスワードがそのまま出力された実例がある。
- **出典**: Privacy and Security for Large Language Models 第3章・第4章

### 2. メンバーシップ推論・データ抽出攻撃のシミュレーション結果を、ASR(Attack Success Rate)・FPR(誤検出率)・再構成誤差等の定量指標で評価し、「安全そう」という主観でなく数値で監査しているか
- **なぜ重要か**: 定量評価ツールがなければ、攻撃シミュレーションを実施していても改善の進捗や合否判定を客観的に示せない。
- **出典**: Privacy and Security for Large Language Models 第3章

### 3. HELM・TruthfulQA・HarmBench・JailbreakBenchなどの標準化ベンチマークを独自評価と組み合わせて使用し、ベンチマークの陳腐化やGoodhartの法則(ベンチマーク最適化による見かけ上の改善)を意識しているか
- **なぜ重要か**: 良好なベンチマーク結果だけでは実運用での安全性を保証できず、ベンチマークに最適化されただけの見かけの改善を見逃すリスクがある。
- **出典**: Privacy and Security for Large Language Models 第3章

### 4. RAGシステムにおいて、検索パターンの漏洩・ベクトルDBの露出・ドキュメント引用による機密情報の意図しない開示を評価しているか
- **なぜ重要か**: 埋め込みの類似度から機密文書の存在やAPIキー等が漏洩した実例が報告されている。
- **出典**: Privacy and Security for Large Language Models 第2章・第3章

### 5. MoE(Mixture of Experts)アーキテクチャを採用する場合、特定のExpertに機密データが集中し、どのExpertが活性化したかというルーティングパターン自体が新たなサイドチャネルになり得ることを評価しているか
- **なぜ重要か**: 専門家ごとに異なるデータサブセットを学習するMoE特有の漏洩経路であり、現代の主要LLMがMoEを採用する中で独立して確認すべき論点である。
- **出典**: Privacy and Security for Large Language Models 第2章

### 6. 暗号化された通信であっても、応答のタイミングやパケットサイズから内容を推測するサイドチャネル攻撃の可能性を考慮した監視をしているか
- **なぜ重要か**: 2024年の報告ではAIアシスタントの暗号化された応答内容の55%が復元可能とされ、暗号化のみでは安全とみなせない。
- **出典**: Privacy and Security for Large Language Models 第1章

### 7. 内部LLM利用で、無害に見える質問の組み合わせによる間接的な機密情報漏洩(例: 給与データ要約から最高給与者を推測)を想定し、データ分類ポリシーに準拠したAI利用ポリシーを策定しているか
- **なぜ重要か**: 内部LLMであっても、要約依頼の連鎖から別ユーザーの機密情報を間接的に聞き出せた実例がある。
- **出典**: Software Supply Chain Security 第7章 p.116

### 8. サードパーティAIツール・サービスの利用規約・ライセンスモデルを確認し、入力した組織の機密データがベンダー側のモデル訓練に再利用されないことを確認しているか
- **なぜ重要か**: AIツールのライセンスモデルによっては、組織のデータが第三者モデルの訓練に利用されることが許可されている場合がある。
- **出典**: Identity Security for Software Development 第8章

### 9. トークナイゼーション・チャンキングの境界をまたいで機密フレーズ(個人名・医療状態等)が分割・結合され、分割前には想定されていなかった形で意図せず露出していないか確認しているか
- **なぜ重要か**: チャンク境界を跨いだ機密フレーズの分割・結合や、チャンクラベル自体が機密属性を示してしまう場合がある。
- **出典**: Privacy and Security for Large Language Models 第2章

### 10. 長いコンテキストウィンドウの利用時、複数ソースからの情報集約によって、個々の情報単体では存在しなかった個人識別可能性(モザイク識別)が新たに生じていないか評価しているか
- **なぜ重要か**: コンテキストが長くなるほど複数ソースの集約によるプライバシー露出の潜在面が拡大する。
- **出典**: Privacy and Security for Large Language Models 第9章

### 11. モデルの重み・推論実行・APIインターフェース・公開アクセスという4つの「trust zone」間で、アクセス権限の強度を段階的に分離しているか
- **なぜ重要か**: 1ゾーンの侵害が他ゾーン(特にモデル重み)へ波及しない設計が必要。
- **出典**: Privacy and Security for Large Language Models 第5章

### 12. モデルの重み(model weights)を物理アクセス・内部脅威から保護するため、HSM・Secure Boot・メモリ暗号化等のセキュリティ投資を行っているか
- **なぜ重要か**: 米英AI安全サミット合意事項でも、モデル重み保護への投資が自主規制要件の筆頭項目として明記されている。
- **出典**: Privacy and Security for Large Language Models 第5章; Inside Cyber Warfare 第3版 第7章 p.128

### 13. モデルファイルにハッシュを付与し、モデルレジストリで版系譜(parent_version)とセキュリティスキャン結果を記録しているか
- **なぜ重要か**: 改ざん検知と監査可能性を確保し、モデルのどの版がどの由来・検査結果を持つかを追跡できるようにする。
- **出典**: Privacy and Security for Large Language Models 第5章

### 14. モデル更新は、バックアップ取得→検証→デプロイ→検証失敗時ロールバックという段階的パイプラインで行っているか
- **なぜ重要か**: モデル更新自体が改善機会であると同時に新たな攻撃ベクトルにもなるため、失敗時に安全に戻せる仕組みが必要。
- **出典**: Privacy and Security for Large Language Models 第5章

### 15. RAGやエージェントの知識ベース・メモリに対するデータポイズニング(特定トリガーで悪意ある行動を誘発する例の注入)を検証し、バックドア検証ツール(TrojLLM等)で耐性を評価しているか
- **なぜ重要か**: エージェントは自身の知識ベースを無条件に信頼するため汚染の検出が難しく、学習プロセス自体への侵害を見逃しやすい。
- **出典**: Privacy and Security for Large Language Models 第6章

### 16. 事前学習済みモデル・埋め込みを取得する際、信頼できるソースからのものか、ライセンス・学習データの出自・既知脆弱性・セキュリティ監査履歴・モデルの出自(provenance)を確認しているか
- **なぜ重要か**: 事前学習モデルは機密データで学習されている可能性があり、改変されたモデルが混入するリスクもある。
- **出典**: Privacy and Security for Large Language Models 第2章; Security Architecture for Hybrid Cloud 第12章

### 17. モデル窃取・データポイズニング検知のためMLDR(Machine Learning Detection and Response)の導入を検討し、OWASP AI Exchange・MITRE ATLAS等の動向を定期的に確認するプロセスを持っているか
- **なぜ重要か**: GenAI特有の脅威を検知・対応する専門領域であり、この分野はまだ未成熟であるからこそ継続的な追跡体制そのものを確認する必要がある。
- **出典**: Security Architecture for Hybrid Cloud 第12章

### 18. レッドチーミングを一度きりのイベントでなく継続的な開発サイクルに統合し、評価・監視下と非監視下での挙動差分(Treacherous Turn)まで検知できる仕組みになっているか
- **なぜ重要か**: アライメント済みモデルも監視終了後に異なる目標を追求する可能性が理論的に指摘されており、静的な評価だけでは不十分。
- **出典**: Privacy and Security for Large Language Models 第6章; Inside Cyber Warfare 第3版 第7章 p.125,128

### 19. LLMを統合したアプリケーションにおける間接プロンプトインジェクションのリスクを認識し、外部コンテンツ(Webページ・ドキュメント等)を信頼できない境界として扱っているか
- **なぜ重要か**: 既知の有効な緩和策が存在しないとされる攻撃であり、外部コンテンツを無条件に信頼する設計は危険。
- **出典**: Inside Cyber Warfare 第3版 第7章 p.121

### 20. プロンプトインジェクション検知の仕組みとして、単純なパターンマッチングではなくLLMベースの意図分析を行うAIファイアウォール/ガードレールを導入しているか
- **なぜ重要か**: 従来の入力検証(パターンマッチ)は「意図」を理解できず、巧妙なプロンプトを防御できない。
- **出典**: Security Architecture for Hybrid Cloud 第12章

### 21. 上記のガードレールに加え、入力の事前処理(悪意あるプロンプト検出)と出力の後処理(機密情報漏洩スキャン)を両方備えた「サンドイッチ」型の冗長な防御レイヤーを実装しているか(システムプロンプトのみに依存していないか)
- **なぜ重要か**: 検知層が一つだけでは高度な攻撃を防げず、入力・出力双方で独立した防御層を持つ冗長性が必要。
- **出典**: Privacy and Security for Large Language Models 第3章・第5章

### 22. ロールプレイ型・DAN型・命令密輸・トークン操作・Few-shot誘導等の既知ジェイルブレイク手法、及びGCG(勾配座標勾配)によるサフィックス最適化やエンベディング空間への直接摂動攻撃への耐性をテストしているか
- **なぜ重要か**: アライメント済みモデルでも巧妙なプロンプトで安全策を回避される実例があり、少ない最適化ステップでも効率的に突破されうる。
- **出典**: Privacy and Security for Large Language Models 第6章; Zero Trust Networks 第2版 Ch12 p.290

### 23. White-box/Black-box/Gray-box、Targeted/Untargeted、Input/Prompt/Embedding-levelという多次元の攻撃分類に基づいて、自社の防御策が網羅的かを確認しているか
- **なぜ重要か**: 表面上似た攻撃でも脆弱性の種類が異なり、単一ベクトルへの対策では不十分になる。
- **出典**: Privacy and Security for Large Language Models 第6章

### 24. RAG/GenAIアーキテクチャをデータ処理・埋め込み・ベクトルDB層/アプリ・オーケストレーション・LLM層/インフラ層/運用・ガバナンス層に分け、各層でデータポイズニング・モデル窃取・モデル回避・DoS・データ漏洩といったGenAI固有の脅威を脅威モデリングに組み込んでいるか
- **なぜ重要か**: 従来の脅威モデリング手法で扱える部分もあるが、GenAI特有の新種の脅威が層ごとに異なる形で存在する。
- **出典**: Security Architecture for Hybrid Cloud 第12章

### 25. 本来分散していた機密データが学習パイプラインに一元集約されることで生じる「データ集中リスク」を評価し、GenAI学習基盤に対する分類・アクセス制御・監視を、分散していた時点より強化しているか
- **なぜ重要か**: GenAI学習基盤は従来の分散データとは異なるリスクプロファイルを持ち、一元集約自体が新たな攻撃対象を生む。
- **出典**: Security Architecture for Hybrid Cloud 第12章

### 26. ディープフェイク・生成AIによるなりすまし/偽情報を用いたソーシャルエンジニアリング攻撃のリスクをプロダクト設計時に想定しているか
- **なぜ重要か**: 信頼の侵食や、銀行職員の偽装のような実例が報告されている社会的リスクであり、技術的対策だけでなく設計段階での想定が必要。
- **出典**: Privacy and Security for Large Language Models 第8章・第6章ケーススタディ; Zero Trust Networks 第2版 Ch12 p.290

### 27. ファインチューニングにDP-SGD(勾配クリッピング+ガウス雑音)を適用し、RDP(Rényi差分プライバシー)アカウンタでプライバシー予算(ε・δ)を追跡しているか
- **なぜ重要か**: 素のファインチューニングではSSN等の機密情報がそのまま生成され得ることが実証されており、プライバシー予算は消費後回復しない有限資源である。
- **出典**: Privacy and Security for Large Language Models 第3・4・9章

### 28. LoRA/QLoRA等のPEFT(Parameter-Efficient Fine-Tuning)を優先的に採用し、学習可能パラメータを削減することでDP適用時のノイズ影響とメモリ化(記憶)リスクを下げているか
- **なぜ重要か**: LoRAは0.1〜1%程度のパラメータのみ更新し、同じεでも性能劣化が少なく、監査も容易になる。
- **出典**: Privacy and Security for Large Language Models 第2・4・9章

### 29. 医療・金融等の高感度領域で、連合学習(Federated Learning)・MPC(秘密分散)・同型暗号・ZKP等のPrivacy-Enhancing Technologiesを用いて生データを一元化せずに協働学習・処理できないか検討しているか
- **なぜ重要か**: 病院間・法律事務所間など守秘義務のあるデータ共有を、生データ共有なしに実現できる。
- **出典**: Privacy and Security for Large Language Models 第4・9章; Zero Trust Networks 第2版 Ch12 p.291-292, Ch7 p.161-163

### 30. RAGの検索プロセスにプライバシー予算を適用し(クエリ摂動、厳密なtop-kでなく重み付きサンプリングでの取得)、どの文書が実際に最も関連していたかを攻撃者が特定できないようにしているか
- **なぜ重要か**: 差分プライバシーの考え方を学習時だけでなくRAGの取得プロセスにも拡張する必要がある。
- **出典**: Privacy and Security for Large Language Models 第3・4章

### 31. 匿名化・合成データ生成を行う場合、言語構造の保持(ユーティリティ)と再識別化攻撃に対する耐性(プライバシー)の両方をセットで品質検証しているか
- **なぜ重要か**: 匿名化はユーティリティとプライバシーのトレードオフであり、過度な一般化はデータの有用性を損ない、不十分な一般化は再識別化を許す。
- **出典**: Privacy and Security for Large Language Models 第4章

### 32. 匿名化評価にk-anonymity/l-diversity/t-closenessを用いつつ、これらが同質性攻撃・背景知識攻撃には単体で不十分であることを認識し、補完技術を検討しているか
- **なぜ重要か**: k-anonymity等は静的データセットの匿名化評価には有効だが、単体では攻撃に対し不十分である。
- **出典**: Privacy and Security for Large Language Models 第3章

### 33. 差分プライバシー・連合学習等のプライバシー保護技術の導入が、少数グループに対して不均衡な影響(サンプルサイズが小さいほどノイズの影響が相対的に大きい)を与えていないか評価しているか
- **なぜ重要か**: 均一なDP適用は小規模グループに対して実質的に保護が弱くなり、プライバシーと公平性がトレードオフする。
- **出典**: Privacy and Security for Large Language Models 第7章

### 34. モデルの説明(attention可視化、プロービング、反事実説明等)を提供する際、その説明自体が訓練データや個人情報を漏洩しないか(差分プライバシー付き説明等で)検証しているか
- **なぜ重要か**: 説明可能性とプライバシーはトレードオフ関係にあり、説明出力が新たな漏洩経路になりうる。
- **出典**: Privacy and Security for Large Language Models 第7章

### 35. GDPR・CCPA・HIPAA・EU AI Act等、対象地域・業界の規制要件を踏まえたデータガバナンス方針を明文化しているか
- **なぜ重要か**: 医療・金融等の高リスク領域では規制違反が重大な法的責任を招く。
- **出典**: Privacy and Security for Large Language Models 第8・9章

### 36. モデルの意思決定が人に影響する場面で、多様なステークホルダーを関与させたアルゴリズム影響評価(AIA)を実施しているか、また司法・医療等の高リスク領域ではhuman-in-the-loopと不服申立て手段を組み込んでいるか
- **なぜ重要か**: バイアス・差別のリスクを事前に特定・緩和できる。EHRソフトウェアの不具合による患者死亡・重傷の実例がありながら、大半の州に報告義務がない。
- **出典**: Privacy and Security for Large Language Models 第8・9章; Inside Cyber Warfare 第3版 第7章 p.122-123

### 37. 自動雇用判断ツール等を使う場合、独立したバイアス監査と候補者への通知義務(NYC Bias Audit Law等)を遵守しているか
- **なぜ重要か**: 既に施行されている規制であり、違反は現実の法的リスクになる。
- **出典**: Privacy and Security for Large Language Models 第8章

### 38. 学習データの著作権・ライセンス遵守状況(データ取得の意図・コントロール・知識管理)を文書化しているか
- **なぜ重要か**: NYT対OpenAI訴訟等、学習データの著作権侵害リスクが現実の訴訟として既に表面化している。
- **出典**: Privacy and Security for Large Language Models 第8章
