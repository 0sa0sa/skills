# ネットワーク・ゼロトラストアーキテクチャ

マイクロセグメンテーション、境界なし設計、mTLS、PKI、ネットワーク分離に関わる設計・実装を見る。

## チェックリスト

### 1. ネットワークアクセス制御の基準をIPアドレスやネットワークロケーションではなく、検証されたID(ワークロードID/サービスアカウント)に置いているか
- **なぜ重要か**: ゼロトラストは「IDがネットワークアドレスより優先される通貨」という定義であり、IPのみに基づく信頼付与は境界内侵入後の横移動を容易にする。
- **出典**: Cloud Native Security Cookbook 第5章冒頭/5.1(p.181,186); Zero Trust Networks 2nd Ed Ch1 p.16, Ch5 p.101

### 2. ネットワーク(VPC/VNet/Kubernetes NetworkPolicy等)が既定で全通信拒否(deny-by-default)になっており、必要な通信のみを明示的に許可する設計になっているか
- **なぜ重要か**: 許可を明示しない限り塞ぐのが安全側の既定値であり、何も設定しないと全通信が許可されるKubernetes等では放置が致命的になる。
- **出典**: Cloud Native Security Cookbook 第5章5.1-5.2(p.183-184,193); Identity Security for Software Development 第7章

### 3. マイクロセグメンテーションをゾーン単位ではなく個々のホスト/ワークロード単位で適用しているか
- **なぜ重要か**: ゾーン粒度のセグメンテーションでは同一ゾーン内の侵害からの横移動を防げない。攻撃の25%にラテラルムーブメントが関与していたとする調査もマイクロセグメンテーションの必要性を支持する。
- **出典**: Zero Trust Networks 2nd Ed Ch9 p.210, Ch11 p.273; Software Supply Chain Security 第3章 p.47

### 4. サービスメッシュ/Pod間など同一トラストドメイン内のクライアント-サーバー型通信にmTLS(相互TLS)を適用し、証明書ベースのID検証でなりすましを防いでいるか。サーバー間の大規模な東西トラフィックについては、IPsec等の代替方式の併用も検討しているか
- **なぜ重要か**: mTLSは証明書による双方向ID確認を行うため、ネットワーク到達性だけで通信相手を信頼する設計特有のなりすまし(impersonation)攻撃を防げる。
- **出典**: Identity Security for Software Development 第7章; Zero Trust Networks 2nd Ed Ch8 p.178,197-198

### 5. 内部ネットワーク(データセンター内・プライベート接続)であっても通信を暗号化しており、「内部だから平文でよい」という前提を置いていないか
- **なぜ重要か**: NSAがデータセンター内の光ファイバーを盗聴した"Room 641A"の例のように、同一施設内の通信でも秘匿性は保証されない。
- **出典**: Zero Trust Networks 2nd Ed Ch1 p.18-19, Ch9 p.203; Cloud Native Security Cookbook 第5章5.13(p.262)

### 6. 全てのネットワークフローを「処理前に認証」しているか(送信前の暗号化とは別の必須要件として区別しているか)
- **なぜ重要か**: 認証(authentication)と暗号化(encryption)は別次元の要件であり、フロー認証は必須(MUST)要件として明示されている。
- **出典**: Zero Trust Networks 2nd Ed Ch9 p.202

### 7. 認証・暗号化の終端をVPN集線装置やTLS終端ロードバランサ等の中間者に委ねず、アプリケーション層のエンドポイント同士で実施しているか
- **なぜ重要か**: 中間者に信頼を委譲すると、その中間者自体が侵害された場合に全通信の秘匿性・完全性が失われる単一障害点になる。
- **出典**: Zero Trust Networks 2nd Ed Ch9 p.203, Ch1 p.17

### 8. PKI基盤をプライベートCAを基本とし、パブリックPKIへの依存を最小化しているか
- **なぜ重要か**: 国家主体がCAに介入するリスクがある(2022年ロシアが独自CAを発行した事例)ため、認証基盤を外部機関の信頼に委ねすぎない設計が推奨される。
- **出典**: Zero Trust Networks 2nd Ed Ch2 p.32-33, Ch5 p.77, Ch9 p.204-205

### 9. TLS証明書を信頼されたCAから発行し、本番環境で自己署名証明書を使わず、TLS1.2以上を強制しているか。また署名鍵・証明書の秘密鍵をHSMで管理し、鍵のローテーションが設定上だけでなく実際に機能しているか定期的に確認しているか
- **なぜ重要か**: 古いTLSバージョンや自己署名証明書は既知の脆弱性・検証回避のリスクを抱える。Microsoft Storm-0558侵害では2016年製の署名鍵が盗まれた経緯が未解明のまま放置されていた。
- **出典**: Privacy and Security for Large Language Models 第5章(HTTPS and TLS Implementation); Inside Cyber Warfare 3rd Ed 第3章 p.34-36

### 10. 期待される通信フローを列挙したデータベースを保持し、そこにない未知のフローを検知・拒否できる仕組みがあるか
- **なぜ重要か**: 「何が正常か」を定義していなければ異常な通信を検知する基準自体が存在しない。
- **出典**: Zero Trust Networks 2nd Ed Ch9 p.203-204, 207-209

### 11. セキュリティグループ(ステートフル)とネットワークACL(ステートレス)を併用し、0.0.0.0/0からの不要な開放ポートがないか自動検査しているか
- **なぜ重要か**: NACLは誤設定されたセキュリティグループでも回避できない強制ルールであり、無制限に開放されたポートはブルートフォース攻撃の侵入口になる。
- **出典**: Cloud Native Security Cookbook 第5章5.2(p.193-194); Security as Code p.25-27,32,53-55

### 12. デフォルトVPC・デフォルトセキュリティグループを削除・無効化しているか
- **なぜ重要か**: デフォルトVPCはサブネット分離が不十分で、デフォルトSGは無制限アクセスを許してしまう。
- **出典**: Cloud Native Security Cookbook 第5章5.2(p.193-194)

### 13. アウトバウンド通信のegressフィルタリング(明示的なegressルール定義を含む)を実施しているか
- **なぜ重要か**: egressフィルタリングは安価にC2通信・データ窃取を検知・遮断できる手段であり、暗黙の全許可アウトバウンドは意図しないデータ流出経路になる。
- **出典**: Defensive Security Handbook 2nd Ed 第16章 p.207-208; Security as Code p.33

### 14. 複数アカウント/VPC間の東西(East-West)トラフィックをVPCピアリングではなくハブ&スポーク(Transit Gateway等)で集中管理しているか
- **なぜ重要か**: VPCピアリングは非推移的でスケールせず、大規模環境では管理不能になる。
- **出典**: Cloud Native Security Cookbook 第5章5.8(p.230); Security Architecture for Hybrid Cloud 第9章

### 15. ZTNAとマイクロセグメンテーションを正しく区別して使い分けているか(ZTNAはエンドユーザー―アプリ境界、マイクロセグメンテーションはノード間通信)
- **なぜ重要か**: ZTNAはPolicy Enforcement Pointがクラウド側(組織境界の外)にあり、通信がegress方向のみで開始されるため内部ネットワークが外部からの到達可能性を持たなくなる、VPNとは本質的に異なる設計である。
- **出典**: Security Architecture for Hybrid Cloud 第8章

### 16. サーバーへの運用者接続をSSH/RDP直接接続ではなく、IDベースのプロキシ(IAP/Session Manager等)経由にしているか
- **なぜ重要か**: 長期鍵の配布・管理・漏洩リスクを排除し、アクセスを集中管理できる。
- **出典**: Cloud Native Security Cookbook 第5章5.4-5.5(p.207)

### 17. 外部公開エンドポイントについて、まずポートを開けてから認証する設計(「最初のパケット問題」)を避け、SPA(single-packet authorization)等のpre-authenticationでポート自体を未認証の通信相手から隠蔽しているか
- **なぜ重要か**: 通常のファイアウォールは認証の成否にかかわらずポートへの到達可能性自体を露出させてしまう。SPAはこの問題を解消し攻撃対象領域を縮小する。
- **出典**: Zero Trust Networks 2nd Ed Ch8 p.171-173

### 18. ホスト型(エンドポイント上のフィルタ)・bookended型(送受信双方向でフィルタ)・仲介者(ブローカー)型という複数のフィルタリング方式を組み合わせた多層防御になっているか
- **なぜ重要か**: 単一方式のフィルタリングには死角があり、一方の方式が回避・無効化されても他の方式が防御を維持できるよう複数方式を重ねる設計が求められる。
- **出典**: Zero Trust Networks 2nd Ed Ch8 p.187-193

### 19. インターネット公開アプリの前段にWAFを配置し、かつWAF/CDNを経由せずオリジンへ直接到達できる迂回路が残っていないか確認しているか
- **なぜ重要か**: WAFは既知攻撃パターンをエッジで遮断できるが、迂回路が残ればフロント防御全体が無意味になる。
- **出典**: Cloud Native Security Cookbook 第5章5.10-5.12(p.241-242,255-256)

### 20. IT環境とOT(制御システム)環境の間に不要な接続経路(SSHトンネル等)が放置されていないか
- **なぜ重要か**: 2015年ウクライナ電力網攻撃はITネットワーク侵入後、開いたSSHトンネルを通じてOT(遮断器・SCADA)へ横展開した実例である。
- **出典**: Inside Cyber Warfare 3rd Ed 第4章 p.61-62

### 21. ネットワーク機器のファームウェアを定期パッチし、SNMPのデフォルトコミュニティ文字列を変更してSNMPv3のみ許可しているか
- **なぜ重要か**: 「ファームウェアだから安全」という誤解が被害を生み、デフォルトSNMP文字列は構成情報漏洩やDDoS増幅に悪用される。
- **出典**: Defensive Security Handbook 2nd Ed 第16章 p.198,201-202

### 22. IDS/IPSを適切なチョークポイントに配置し、ネットワーク型(NIDS)とホスト型(HIDS)を併用しているか
- **なぜ重要か**: EDRを削除された端末でも、ネットワーク型IDSが唯一の検知手段になった実例がある。
- **出典**: Defensive Security Handbook 2nd Ed 第21章 p.266-270,279-280

### 23. 認証後のセッション・トークンをアプリ側キャッシュのみに委ねず、権限変更(解雇・降格等)後に既存トークンが即座に無効化される継続的な再検証を実装しているか
- **なぜ重要か**: 一定時間有効なトークンが権限剥奪後も有効なままでは不正操作が可能になる。暗黙的信頼でなく明示的・継続的な検証を行うのがゼロトラストの本質である。
- **出典**: Zero Trust Networks 2nd Ed Ch6 p.118-119,124-125; Web Application Security 2nd Ed 第21章

### 24. 全通信をTLS化し、HTTPSへの強制(HSTS)を実装しているか(301リダイレクトのみに依存していないか)
- **なぜ重要か**: 301リダイレクトのみでは初回HTTPリクエストが中間者攻撃に脆弱であり、HTTP許容は平文トラフィックの漏洩経路になる。
- **出典**: Web Application Security 2nd Ed 第21・22章; Cloud Native Security Cookbook 第4章4.8(p.161)

### 25. DNSゾーン転送要求を権限のないホストから拒否する設定になっているか
- **なぜ重要か**: 設定ミス一つで内部サブドメイン・IPが丸ごと漏洩する。
- **出典**: Web Application Security 2nd Ed 第4章; Defensive Security Handbook 2nd Ed 第23章 p.306-308

### 26. 機密性の高いワークロード/モデルについて、クラウド事業者を暗黙に信頼せず、機密コンピューティング(TEE)等で暗号学的に検証可能な保護を適用しているか
- **なぜ重要か**: パブリッククラウド事業者自体も信頼境界の外に置くのがゼロトラストの前提であり、インフラ層の信頼を暗黙的に仮定してはならない。
- **出典**: Zero Trust Networks 2nd Ed Ch7 p.161-163

### 27. 不要になったVPNアクセスを継続的にモニタリングし、速やかに剥奪しているか
- **なぜ重要か**: 使われなくなったリモートアクセス経路の放置は、攻撃対象領域を不必要に拡大する。
- **出典**: Zero Trust Networks 2nd Ed Ch9 p.228(BeyondCorpの実例)

### 28. コントロールプレーンとデータプレーンを論理的・物理的に分離し、ポリシーエンジン等の最重要コンポーネントへの変更に多者承認・監査ログを要求しているか
- **なぜ重要か**: ポリシーエンジンはゼロトラスト全体の信頼の根幹であり、単独の変更権限は構造全体を危険にする。
- **出典**: Zero Trust Networks 2nd Ed Ch2 p.39-40, Ch10 p.244-246

### 29. ネットワークACLルールの規模(アプリ数×層数×環境数×ルール数、例:100アプリ×8層×4環境×20ルール=64,000ルール)を把握し、手動管理ではなくポリシーベースの集中管理・自動化(IaC)で対応しているか
- **なぜ重要か**: ルール数は組合せ的に爆発し、手動管理は規模が大きくなると必ず破綻する。
- **出典**: Security Architecture for Hybrid Cloud 第9章

### 30. ゼロトラストを単体の「製品」として導入するのではなく、データ中心セキュリティ・脅威モデリング(Secure by Design)・コンプライアンス管理と統合した一貫した方法論として適用しているか(ベンダーのマーケティング上の「ゼロトラストネットワークアーキテクチャ」という用語の誤用に注意しているか)
- **なぜ重要か**: 「Never trust, always verify」のスローガン化や特定製品への矮小化はゼロトラストの本質を損なう。ゼロトラストは単独のエンドツーエンド手法ではなく、他の技法と統合すべき方法論である。
- **出典**: Security Architecture for Hybrid Cloud 第1〜2章
