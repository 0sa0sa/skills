# インシデント対応・セキュリティ運用

ログ、検知、フォレンジック、監視、インシデント対応ライフサイクルに関わる設計・運用を見る。

## チェックリスト

### 1. セキュリティログをホスト単体に保持せず、SIEM等の集中ログ基盤へ転送し、侵害時の改ざん・削除から保護しているか
- **なぜ重要か**: ホスト侵害時にローカルログは改ざん・削除されうるため、集中転送がフォレンジックの生命線になる。
- **出典**: Defensive Security Handbook 2nd Ed 6章p.65-66, 22章p.283-286

### 2. 組織レベルの監査ログ・証跡をワークロードチーム自身が無効化・改変できない設定にしているか
- **なぜ重要か**: 証跡の削除・無効化が可能だとフォレンジックとインシデント対応の実効性そのものが失われる。
- **出典**: Cloud Native Security Cookbook 第3章3.4-3.6(p.79,84,90)

### 3. インシデントの定義基準を文書化し、早期エスカレーションを促す文化があるか
- **なぜ重要か**: 定義が曖昧だと過剰反応か見逃しの両極端に陥り、インシデント対応運用の前提そのものが崩れる。
- **出典**: Defensive Security Handbook 2nd Ed 6章p.62

### 4. SOC/SIEMで発せられるアラートが実際の対応プロセスに統合され、「誰も聞いていない警報」になっていないか確認しているか
- **なぜ重要か**: アラート疲れによって重要な検知シグナルが無視され、侵害の発見が遅れる。
- **出典**: Cloud Native Security Cookbook 第3章3.1,3.3(p.70,77)

### 5. 組織レベルの脅威検知自動化(GuardDuty等)が「新規アカウントのみ」適用され、既存アカウントへの遡及適用が漏れていないか確認しているか
- **なぜ重要か**: 自動登録が新規アカウント限定になりやすく、既存アカウントの可視性の穴を放置してしまう。
- **出典**: Cloud Native Security Cookbook 第3章3.7-3.9(p.73-74,101,104)

### 6. CloudTrail等で重要操作(例: セキュリティグループの削除)にイベントルールを設定し、SSM Automation等で自動是正しているか
- **なぜ重要か**: 手動対応に依存すると監視業務だけで工数の半分が奪われた実例があり、自動是正が対応負荷を下げる。
- **出典**: Security as Code p.51-52

### 7. ディスクイメージ・メモリダンプ・PCAP取得等のインシデント対応ツールと手順を、発生前に事前整備しているか
- **なぜ重要か**: 対応の最中に手順を学ぶ余裕はなく、準備不足は初動の遅延に直結する。
- **出典**: Defensive Security Handbook 2nd Ed 6章p.67-68

### 8. NIST SP800-61等のインシデント対応ライフサイクル(準備→検知/分析→封じ込め・根絶→復旧→事後対応)に基づく対応計画を、発生前に策定・演習しているか
- **なぜ重要か**: 事後に計画を作成しても実効性がなく、実際の侵害発生時に初めて対応を学ぶのは最悪のタイミングになる。
- **出典**: Identity Security for Software Development 9章; Security Architecture for Hybrid Cloud 第11章

### 9. RACI/RASCIで各セキュリティサービス(脆弱性管理等)の提供者・消費者の責任を明文化し、契約・内部合意に反映しているか
- **なぜ重要か**: 曖昧な責任分担は実施漏れのリスクになり、一方的な責任共有合意は誤解・サービス障害・契約トラブルを生む。
- **出典**: Security Architecture for Hybrid Cloud 第11章

### 10. インシデント終息後、数日以内にブレームレスなポストモーテム(RCA/AAR)を実施し、再発防止のアクションプランに落とし込んでいるか
- **なぜ重要か**: 時間経過で記憶が薄れ改善点を取りこぼし、原因の深掘りなしでは同種事故が再発する。
- **出典**: Defensive Security Handbook 2nd Ed 6章p.64-65; Security as Code 第6章p.69,78

### 11. RPO/RTOを業務部門主導で定義し、依存先システムのRTOが対象システムの要求を下回っていないか確認しているか
- **なぜ重要か**: 依存関係の見落としがあると、復旧計画が実際には機能しない。
- **出典**: Defensive Security Handbook 2nd Ed 7章p.71-77

### 12. 重要インフラ(電力・通信・決済等)が長期間停止するシナリオを想定した代替手段・冗長性を確保しているか
- **なぜ重要か**: 組織的な攻撃による電力網停止のように、通常のDR想定を超える長期・広範な停止が実際に発生している。
- **出典**: Inside Cyber Warfare 3rd Ed あとがきp.134-135

### 13. DR(災害復旧)訓練を定期実施し、本番への影響なく検証しているか
- **なぜ重要か**: 複雑な依存関係は実際に試すまで気づかないことが多い。
- **出典**: Defensive Security Handbook 2nd Ed 7章p.79

### 14. ゲームデーやカオスエンジニアリング的な障害注入実験(インシデント対応訓練)を定期実施し、監視・アラート・対応手順の実効性を事前検証しているか
- **なぜ重要か**: 実際の侵害発生時に初めて対応を学ぶのは最悪のタイミングであり、オートスケールやアラートの実効性も事前検証できる。
- **出典**: Cloud Native Security Cookbook 第10章10.2(p.485); Security as Code 第6章p.78-84

### 15. 侵害されたアカウントを隔離する専用機構(Quarantine OU等)や、調査用の読み取り専用アクセス経路を事前に用意しているか
- **なぜ重要か**: 平常時の統制を保ちながら緊急対応の速度を確保する必要がある。
- **出典**: Cloud Native Security Cookbook 第2章2.2(p.31)

### 16. バックアップの失敗を検知するログメトリクス・アラートポリシーを設定し、リージョン/アカウント間コピーを行っているか
- **なぜ重要か**: 復元が必要になった瞬間にバックアップ失敗に気づくのは最悪のシナリオである。
- **出典**: Cloud Native Security Cookbook 第8章8.10-8.11(p.449,454)

### 17. EDR/Sysmon等で侵害の兆候(プロセス生成・永続化)を監視し、SIEMの検知ルールが実際にPoCで発火することを検証しているか
- **なぜ重要か**: 検知ルールが存在するだけでは機能保証にならない。
- **出典**: Defensive Security Handbook 2nd Ed 22章p.286-291

### 18. ログ収集パイプライン自体の単一障害点(ロードバランサー未接続等)を監視し、「サイレントなログ欠落」を防いでいるか
- **なぜ重要か**: ログがあっても保存先が壊れていれば無意味であり、1週間分のログが誰にも気づかれず欠落した実例がある。
- **出典**: Security as Code 第6章p.78

### 19. アラーム閾値を短期から長期まで複数のスパンで継続的に見直し、季節変動やノイズを除外しているか
- **なぜ重要か**: 短期データだけで閾値を設定すると誤検知・見逃しが多発する。
- **出典**: Security as Code 第6章p.73-74

### 20. CPU/メモリ使用率・レイテンシ・リクエストパターン等のメトリクスを継続監視し、通常時との異常偏差を自動検知する仕組みがあるか
- **なぜ重要か**: 侵害活動やプロンプトインジェクション・データ抽出攻撃の兆候を早期に検知できる。
- **出典**: Security as Code 第4章p.44-47; Privacy and Security for Large Language Models 第5章

### 21. CI/CDパイプラインの異常(実行回数の急増、実行時間の異常な変化、CPU/メモリ/ネットワークの異常消費)を監視し、SIEM等に統合しているか
- **なぜ重要か**: 検知の遅れが被害拡大の要因になる(CircleCI侵害では検知まで数週間を要した)。
- **出典**: Identity Security for Software Development 8章・9章

### 22. シークレット管理サービス等の重要基盤が停止した場合の代替手段(break-glassプロセス)をテストし、障害時にアプリケーションが機能停止しない設計になっているか
- **なぜ重要か**: シークレット管理原則の「テスト」として明記されており、未テストの代替手段は障害時に機能しない。
- **出典**: Identity Security for Software Development 5章

### 23. 脅威検知ユースケースとインシデントレスポンス・ランブックが、脅威モデリングの結果から直接トレーサブルに作成されているか
- **なぜ重要か**: 検知・対応・テストの網羅性を脅威トレーサビリティマトリクスで保証できる。
- **出典**: Security Architecture for Hybrid Cloud 第11章

### 24. 鍵管理・PAM等のセキュリティサービス自体の可用性(RTO/RPO)が、それを利用するワークロード本体の要求を上回って設計されているか
- **なぜ重要か**: コンテナが数分おきに再起動する現代では、鍵管理サービスの停止が即座に業務影響を及ぼす。
- **出典**: Security Architecture for Hybrid Cloud 第2・4・5章

### 25. 攻撃者の特定・対応方針の決定前に、先入観に頼らず十分な証拠収集プロセスを確立しているか
- **なぜ重要か**: 1998年Solar Sunrise事件は当初イラク政府の犯行と誤認されたが、実際はカリフォルニアとイスラエルの少年たちだった。
- **出典**: Inside Cyber Warfare 3rd Ed 第2章p.19-20

### 26. 侵害調査を外部委託する際、調査会社の利益相反を考慮し、独立したレビューの余地を残しているか
- **なぜ重要か**: 私的フォレンジック企業への委託は依頼主寄りの結論になりがちである。
- **出典**: Inside Cyber Warfare 3rd Ed 第2章p.31

### 27. 内部関係者(インサイダー)による情報漏洩を早期検知する体制があるか
- **なぜ重要か**: インサイダー活動は情報戦等と組み合わさることで被害が深刻化しうる。
- **出典**: Inside Cyber Warfare 3rd Ed 第5章p.73

### 28. ソースコード・秘密鍵・証明書の露出・喪失の兆候を監視・検知する技術的対策を導入しているか
- **なぜ重要か**: Toyota(5年以上露出)やCircleCI(検知まで数週間)のように、検知の遅れが被害を拡大させる。
- **出典**: Software Supply Chain Security 第7章p.117-118

### 29. 開発・ラボ・テスト環境も本番同様にSOC/SIEM/SOARへ統合し、ログ監視の対象にしているか
- **なぜ重要か**: Log4j開示後、パッチ未適用の開発環境等が大量の悪用試行の標的になった実例がある。
- **出典**: Software Supply Chain Security 第3章p.48

### 30. 既知だが未修正の脆弱性に対し、悪用試行を検知する追加のロギング・監視を有効にしているか
- **なぜ重要か**: 修正待ちの間に悪用されたまま気付かず深刻な被害を受けた企業の実例がある。
- **出典**: Web Application Security 2nd Ed 第20章

### 31. 脆弱性報告を本番相当のステージング環境で必ず再現してから対応しているか
- **なぜ重要か**: 誤報・設定ミスによる誤った対応やバウンティ支払いを防ぐ。
- **出典**: Web Application Security 2nd Ed 第27章

### 32. 「侵害を前提(assume breach)」としたフォレンジック対応能力を整備しているか
- **なぜ重要か**: マルウェア防止ソフトは常に不完全であるという前提のもとでは、侵害後の調査能力が不可欠になる。
- **出典**: Zero Trust Networks 2nd Ed Ch5 p.95

### 33. 自動隔離等のアクティブレスポンスを導入する際、クラスタ最小サイズ等のフェイルセーフを設け、過剰な自動対応による自己DoSを防いでいるか
- **なぜ重要か**: 自動化された封じ込めが行き過ぎると、自組織のサービスそのものを止めてしまうリスクがある。
- **出典**: Zero Trust Networks 2nd Ed Ch7 p.159

### 34. サイバー保険を活用し、インシデント発生時の財務リスクを移転する仕組みを整えているか
- **なぜ重要か**: 技術的対策だけでは侵害の財務的インパクトを吸収できず、保険によるリスク移転が事業継続性を補強する。
- **出典**: Zero Trust Networks 2nd Ed Ch10 p.251-252

### 35. デバイス紛失・盗難・フィッシング被害等の報告を非難せず奨励する文化(過剰報告を是とする運用)を構築しているか
- **なぜ重要か**: 懲罰的な文化は報告率を下げ、検知・対応の機会そのものを失わせる。
- **出典**: Zero Trust Networks 2nd Ed Ch6 p.129-130

## 本カテゴリに関する正直な補足
Workflowのグローバル完全性チェックにより、本カテゴリはNIST SP800-61ライフサイクル・SIEM集中化・ポストモーテム・DR/ゲームデー・RACI・GuardDuty等のガバナンス・プロセス・戦略レベルは手厚いものの、本来は『Cybersecurity Ops with Bash』が担うはずの現場実務・スクリプティング層(bash/awk/grepでのログ解析パイプライン、tcpdump/ネットワークキャプチャのCLI解析、プロセス・cron・SUIDバイナリ等のUnix侵害痕跡のコマンドライン調査、証拠収集・トリアージの自動化スクリプト、カスタムIOCハンティングスクリプトの作成)が欠落していると指摘された。この本はClaudeの自動セキュリティセーフガードにより3回読解に失敗し、本スキルの素材には含まれていない。詳細はSKILL.mdの「扱わない観点」を参照。
