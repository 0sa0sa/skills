# セキュリティガバナンス・組織的対策

ポリシー、教育、ベンダーリスク、コンプライアンス、契約条項に関わる組織的な設計・運用を見る。

## チェックリスト

### 1. ポリシー文書で「shall/must」等の断定的な言語を用い、「should」のような推奨止まりの表現を避けているか
- **なぜ重要か**: 「should」は強制力を弱め「推奨」と「義務」の境界を不明瞭にするため、方針の実効性が損なわれる。
- **出典**: Defensive Security Handbook 2nd Edition 第3章 p.44

### 2. ポリシーを「標準(What)」と「手順書(How)」に階層分割して管理しているか
- **なぜ重要か**: 階層化しておけば変更箇所を一か所に限定でき、保守性が高まる。
- **出典**: Defensive Security Handbook 2nd Edition 第4章 p.49-52

### 3. CIO/CISO配下で経営層・リスク管理・セキュリティ・内部監査の各チームを分離設置し、相互牽制が機能する体制になっているか
- **なぜ重要か**: セキュリティ・リスク・監査が同一ラインで一体化していると相互牽制が働かず、ギャップの発見や予算確保が属人的になる。
- **出典**: Defensive Security Handbook 2nd Edition 第1章 p.2-3

### 4. 重要なアーキテクチャ上の意思決定をADR(Architectural Decision Record)として文書化し、後から経緯・根拠を追跡できるようにしているか
- **なぜ重要か**: ADRがなければ過去の判断理由(なぜその設計を選んだか)が失われ、同じ検討を繰り返したり誤った変更を加えるリスクが生じる。
- **出典**: Security Architecture for Hybrid Cloud 第9章

### 5. リスク受容(risk acceptance)に有効期限を設定し無期限受容を禁止しているか、また脆弱性は重大度×公開範囲でSLAを定めて追跡しているか
- **なぜ重要か**: 受容されたリスクは実際には消えておらず、放置すれば「紙の上の修正」に過ぎなくなる。
- **出典**: Defensive Security Handbook 2nd Edition 第18章 p.234-236

### 6. AI/LLM利用について専用のAIポリシーを策定し、既存のデータ分類ポリシーと整合させているか
- **なぜ重要か**: 内部LLMであっても機密データ(給与情報等)から間接的に機密情報が聞き出せた実例があり、ポリシーによる統制が必要。
- **出典**: Software Supply Chain Security 第7章 p.116

### 7. セキュリティ教育を単発の講義ではなく反復・実践型(フィッシング訓練等)で実施し、デバイスの紛失・盗難やフィッシング等のインシデント報告を非難しない文化を明示し、過剰報告を歓迎する姿勢を示しているか
- **なぜ重要か**: 懲罰的な文化は報告率を下げ検知の機会を失わせる。
- **出典**: Defensive Security Handbook 2nd Edition 第5章 p.56-58 / Zero Trust Networks 2nd Edition 第6章 p.129-130

### 8. 高機密エリアへの物理アクセスに二要素以上の制御を実装し、退職・異動時にバッジ・鍵・PINを即時失効しているか
- **なぜ重要か**: 単一の物理制御(バッジのみ等)は迂回・複製されやすく、失効が遅れれば退職者等による不正アクセスの窓口が残る。
- **出典**: Defensive Security Handbook 2nd Edition 第9章 p.92-96

### 9. 職種・役割別(開発者、ビルド管理者、企業メールを持たない製造現場要員等)にセキュリティトレーニングを設計し、受講状況を追跡しているか
- **なぜ重要か**: 企業メールを持たない現場要員には一般的なフィッシング訓練が無意味であり、現場実態に即した訓練設計が必要。
- **出典**: Software Supply Chain Security 第11章 p.182-186

### 10. セキュリティチャンピオン制度を設置し、各開発チーム・部門にセキュリティ推進役を分散配置しているか
- **なぜ重要か**: 数千人規模の開発者に対しセキュリティチームが数名という規模の不一致を解消する手段になる。
- **出典**: Security Architecture for Hybrid Cloud 第10章 / Software Supply Chain Security 第11章 p.180-181

### 11. セキュリティ機能を開発を止める「ゲートキーパー」ではなく、Collaboration/Facilitation/As-a-Serviceなどの形で開発組織を支える「イネーブルメント」として位置づけているか
- **なぜ重要か**: ゲートキーパー型の運用は開発との摩擦を生み、組織の俊敏性と対立する。
- **出典**: Cloud Native Security Cookbook 第1章 p.5-6, 第9章扉 p.461

### 12. 脆弱性管理チームと脅威管理チームなど、セキュリティ機能間のサイロ化を解消し、SIEM等でのログ集約を待たずに連携できる統合的な体制になっているか
- **なぜ重要か**: 機能がサイロ化していると、ログが一か所に集約されるまで脅威情報が共有されず対応が遅れる。
- **出典**: Security Architecture for Hybrid Cloud 第12章

### 13. テーブルトップ演習・インシデント対応ドリルを定期的に実施しているか
- **なぜ重要か**: 机上演習によって実際のインシデント発生前に組織の弱点を発見できる。
- **出典**: Defensive Security Handbook 2nd Edition 第1章 p.9-13

### 14. セキュリティの責任分担をRACI/RASCIで明文化し、ステークホルダーへHighlights/Lowlights/Trends/Upcoming/Blockers等を含む定期的で透明性のある報告を行っているか
- **なぜ重要か**: 責任が不明瞭だとアラートが放置されやすく、悪い情報を隠す報告体制では経営層からの支援を得られない。
- **出典**: Security as Code p.11, 59, 92

### 15. サプライヤー・ベンダー評価で発見された個別のリスクについて、受容する場合はその都度文書化し、年次でレビューしているか
- **なぜ重要か**: 文書化なき受容は放置と区別できない。
- **出典**: Defensive Security Handbook 2nd Edition 第1章 p.5

### 16. サプライヤー評価において、IT統制の評価だけでなく開発・ビルド・ラボ・本番環境へのペネトレーションテスト結果まで要求しているか
- **なぜ重要か**: 多くの組織は開発環境インフラをペンテスト範囲に含めておらず、評価に抜け漏れが生じる。
- **出典**: Software Supply Chain Security 第9章 p.153-154

### 17. サプライヤーのセキュア開発(SDL)評価を、SOC2/ISO27001証明書の提示のみに依存していないか
- **なぜ重要か**: これらの証明書はセキュア開発プラクティスそのものを直接評価するものではない。
- **出典**: Software Supply Chain Security 第9章 p.155, 158

### 18. 重要サプライヤーに対し四半期ごとのレビューとCVE監視、監査権(right to audit)を契約上保持しているか
- **なぜ重要か**: サプライヤーのセキュリティ姿勢は時間とともに悪化しうるため、継続的な監視が必要。
- **出典**: Software Supply Chain Security 第9章 p.163-164

### 19. 主要な依存先ベンダー・サプライヤーが外国政府の管轄下にあり、当局の要求を拒否できない構造になっていないか評価しているか
- **なぜ重要か**: 企業が国家の要求に「ノー」と言えない構造的リスクが存在する事例(TikTok/ByteDance)が指摘されている。
- **出典**: Inside Cyber Warfare 3rd Edition 第5章 p.81-83

### 20. 「secure-by-design/secure-by-default」を標榜する製品・サービスについて、ベンダーの自己宣言だけでなく独立した第三者検証があるか確認しているか
- **なぜ重要か**: テスト対象ベンダー自身が加盟・資金提供する評価団体(AMTSO等)の評価は独立性に構造的欠陥を持つ場合がある。
- **出典**: Inside Cyber Warfare 3rd Edition 第3章 p.45, 47

### 21. セキュリティツール・ベンダーの乱立による非互換(独自データ形式・API欠如・UX不統一)を避けるため、統合的なフレームワークで評価・整理しているか
- **なぜ重要か**: ベンダーごとに異なる形式・インターフェースが分散すると運用が複雑化し管理不能になる。
- **出典**: Zero Trust Networks 2nd Edition 第12章 p.285-286

### 22. 買収・合併(M&A)後、被合併企業側の旧環境のセキュリティ統合を速やかに行っているか
- **なぜ重要か**: Marriott/Starwood侵害は買収から2年間データベースセキュリティを統合できず発生し、最小権限・適時パッチ・PAM・セグメンテーションがあれば防げたと指摘されている。
- **出典**: Defensive Security Handbook 2nd Edition 第13章 p.135-136

### 23. 自組織に適用される業種別(HIPAA/PCI DSS/SOX/GLBA/FERPA等)・地域別(GDPR/CCPA/EU AI Act/EU CRA/NIS2等)の規制要件を特定・一覧化し、継続的に追跡する仕組みがあるか
- **なぜ重要か**: 規制は地域・業種ごとに異なり、把握漏れは法的責任や制裁につながる(EU CRAでは不正確・不完全な情報提供自体が制裁対象になりうる)。
- **出典**: Defensive Security Handbook 2nd Edition 第8章 p.81-82, 90 / Software Supply Chain Security 第1章 Table1-1 p.6-9 / Privacy and Security for Large Language Models 第8・9章

### 24. コンプライアンス遵守を「十分なセキュリティ」と同一視せず、個別法令への場当たり的対応に終始せずNIST CSF/ISO31000/COBIT等の体系的なリスク管理フレームワークを併用しているか。また、コンプライアンス証跡作成(監査対応)にかける予算・人員と、脆弱性対応やセキュア開発等の実質的なセキュリティ対策にかける予算・人員を区分して可視化し、前者が後者を圧迫していないか確認しているか
- **なぜ重要か**: コンプライアンス=セキュアではなく、個別規制は最低要件に過ぎない。多くの組織がコンプライアンス審査・監査に莫大な投資をしながら実質的なセキュリティ投資をしていない実態がある。
- **出典**: Defensive Security Handbook 2nd Edition 第8章 p.81-82 / Software Supply Chain Security 第2章 p.16-25 / Security Architecture for Hybrid Cloud 第1章

### 25. 業界標準の統制枠組み(CSA CCM等)を採用する際、そのカバー範囲のギャップ(脅威モデリング要件やシークレット管理要件の欠落等)を自組織で特定・補強しているか
- **なぜ重要か**: 業界非依存の標準は固有リスクをカバーしきれず、チェックリスト化しただけでは不十分。
- **出典**: Security Architecture for Hybrid Cloud 第2章 / Security as Code p.94

### 26. People・Process・Technologyの3要素をバランスよく整備し、技術導入だけに依存していないか。また、コンプライアンスチームをDevSecOps導入の初期段階から巻き込んでいるか(監査直前のみの関与になっていないか)
- **なぜ重要か**: 技術単独では安全な体制を作れず、コンプライアンスチームの参加が後付けだと監査のたびにスクランブル対応を招く。
- **出典**: Security as Code 第7章 p.87, p.89, p.97

### 27. 自動意思決定システム(採用判断等)を利用する場合、独立したバイアス監査と対象者への通知義務など、既に施行されている規制(NYC Bias Audit Law等)を遵守しているか
- **なぜ重要か**: AIによる差別・バイアスのリスクは既に法規制の対象となっており、違反は現実の法的リスクを伴う。
- **出典**: Privacy and Security for Large Language Models 第8章

### 28. コンプライアンス違反を全アカウント横断で集計・可視化する仕組みを持っているか
- **なぜ重要か**: 問題の集中箇所をデータドリブンに把握しなければ、限られたリソースを適切に配分できない。
- **出典**: Cloud Native Security Cookbook 第7章 p.367-368

### 29. 業界の自主規制のみに依存せず、独立した外部監査(第三者監査)の受け入れや規制当局への自主的な報告・情報開示の仕組みを、検討に留めず実際に導入しているか
- **なぜ重要か**: 鉄道・海運・自動車業界いずれも、壊滅的な人的被害が出るまで自主規制が機能しなかった歴史的パターンがある。
- **出典**: Inside Cyber Warfare 3rd Edition 第3章 p.38-43

### 30. ベンダー・サプライヤー契約に、セキュリティ責任の範囲とインシデント発生時の賠償条項を明記しているか
- **なぜ重要か**: 通常のEULA(使用許諾契約)はベンダー責任を実質ゼロにする内容になっていることが多く、明記しなければ侵害時に責任を問えない。
- **出典**: Inside Cyber Warfare 3rd Edition 第3章 p.46, 49(ニュージャージー州のSaaS契約賠償条項の実例)

### 31. インシデントや脆弱性の報告・公表を妨げる秘密保持条項・ガグ条項がベンダー契約に含まれていないか確認しているか
- **なぜ重要か**: EHR(電子健康記録)ベンダーがガグ条項でソフトウェア障害の公表を妨げていた実例がある。
- **出典**: Inside Cyber Warfare 3rd Edition 第1章 p.9

### 32. 重要なセキュリティ機能(強化ログ等)がベンダーの有償オプション階層に隠れておらず、標準提供されているか契約時に確認しているか
- **なぜ重要か**: Microsoft Exchangeの侵害検知遅延は、強化ログ機能が有償ティアだったことが一因とされている。
- **出典**: Inside Cyber Warfare 3rd Edition 第3章 p.34

### 33. サプライヤー契約にセキュア開発(SDL)要件、脆弱性・パッチ対応のSLA(重大=30日、高=90日等)、および契約終了時のコードエスクロー等の取り決めを明記しているか
- **なぜ重要か**: 契約終了時の対応は「最も見落とされがちな項目」であり、取り決めがないと終了後の保守・脆弱性放置リスクが残る。
- **出典**: Software Supply Chain Security 第9章 p.160-162

### 34. クラウド・サービスの責任共有モデル(プロバイダ/利用者の役割分担)を、契約書やSOWで双方合意のうえ明文化し、一方的(one-sided)な取り決めになっていないか確認しているか
- **なぜ重要か**: 片方のみ責任が明文化され残りを相手が「暗黙に担う」形の合意は誤解・サービス障害・契約紛争の原因になる。
- **出典**: Security Architecture for Hybrid Cloud 第11章 / Software Supply Chain Security 第6章 p.94, Control CLD-01
