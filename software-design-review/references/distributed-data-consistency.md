# 分散データ・一貫性

CAP定理、サガ、分散トランザクション、結果整合性、シャーディング、ロック等の分散データ設計を見る。

## チェックリスト

### 1. CAP定理を理解し、ネットワーク分断時に一貫性か可用性のどちらを優先するかを、システム全体でなく機能・操作単位で明示的に選択しているか
- **なぜ重要か**: 強整合性は書き込みスループットや可用性を犠牲にするため、単一の答えをシステム全体に適用するのではなく操作ごとにトレードオフを判断する必要がある
- **出典**: Building Microservices 2nd Ed 第12章 p.408-413; Designing Distributed Systems 2nd Ed Ch.2 p.14-15

### 2. 複数サービス・複数集約をまたぐ状態変更に分散トランザクション(2相コミット)を安易に使わず、本当に必要か(回避できないか)を先に検討しているか
- **なぜ重要か**: 1ノードの障害がコミット全体を止め、ロック・レイテンシ増大・可用性低下を招く(Pat Helland「全エンジンが必要な飛行機にエンジンを追加すると可用性が下がる」)。サガは複雑でリスクが高く、避けられるなら避けるべきと明言される
- **出典**: Building Microservices 2nd Ed 第6章 p.179-181, p.195; Building Event-Driven Microservices 2nd Ed Ch.10 p.231

### 3. 長時間にわたる処理をサガ(個別ローカルトランザクションの連鎖)として分解し、サガ全体にはACID的アトミック性がなくBASE(基本的可用性・ソフトステート・結果整合性)前提であることを認識しているか
- **なぜ重要か**: サガはACIDトランザクションの代替ではなく、結果整合性を前提とした別モデルであるため、ACIDを期待した設計は矛盾状態を招く
- **出典**: Building Microservices 2nd Ed 第6章 p.182-184; Software Architecture: The Hard Parts Ch.9 p.263-267

### 4. トランザクショナルサガの3軸(同期/非同期・アトミック/結果整合性・オーケストレーション/コレオグラフィ)を識別した上で、オーケストレーション型とコレオグラフィー型のどちらを採るかをチーム境界・ワークフローの複雑さ・エラー条件の頻度に基づいて意識的に選び、全参加者が同期的にブロッキングで待ち合う最悪の組み合わせ(Horror Story Saga)を避けているか
- **なぜ重要か**: 組み合わせごとにリスクプロファイルが大きく異なり、無自覚な選択は最悪のパフォーマンス・信頼性特性を招く。コレオグラフィはハッピーパスでは疎結合に見えるが、エラー条件が増えるたびに通信リンクが増殖し結局オーケストレーションより複雑化しうる一方、オーケストレーションは可視性に優るが密結合(God service化)のリスクを持つ。また「意味的結合は実装(サービス分割)では改善できず悪化させることしかできない」という点も踏まえる必要がある
- **出典**: Software Architecture: The Hard Parts Ch.12 p.323-350(Horror Story Saga, p.343-346), Ch.11 p.299-320(特にFig.11-9/11-10, p.307-314), p.311(意味的結合の警句); Building Microservices 2nd Ed 第6章 p.189-194; Building Event-Driven Microservices 2nd Ed Ch.10 p.222-230

### 5. サガのステップごとの成功/失敗/補償の状態をステートマシンとして明示的に設計・管理しているか
- **なぜ重要か**: サガは複数ステップに渡る非同期処理であり、各ステップの状態遷移を暗黙に扱うと、どこまで進行し何を補償すべきかが不明確になり障害対応が破綻する
- **出典**: Software Architecture: The Hard Parts Ch.12 p.351-356

### 6. サガが扱うのは「ビジネス上の失敗」のみであり、「技術的失敗」(タイムアウト等)はリトライ等のレジリエンシパターンで別途対処する設計になっているか
- **なぜ重要か**: 両者を混同すると補償ロジックが技術的エラーにまで肥大化し、サガの複雑性が不必要に増大する
- **出典**: Building Microservices 2nd Ed 第6章 p.184-185

### 7. 補償トランザクション(compensating transaction)は「意味的ロールバック」であり元に戻せない操作が存在すること、補償自体が失敗した場合は人手介入が必要になること(自動復旧手段は原理的に存在しない)を想定した設計・運用体制になっているか
- **なぜ重要か**: デジタルと物理世界の不一致など巻き戻せない操作があり、補償の失敗を自動で解決する仕組みは存在しないため、代替として補償ワークフロー(forward recovery)や運用側の受け皿が必要
- **出典**: Building Microservices 2nd Ed 第6章 p.185-187; Software Architecture: The Hard Parts Ch.9 p.275-276, Ch.12 p.356-363; Building Event-Driven Microservices 2nd Ed Ch.10 p.237-238

### 8. メッセージ/イベントハンドラ・HTTPメソッド・パイプライン処理(append/merge等)を冪等に設計して重複配信・再実行を安全に許容できるようにした上で、「確実に1回だけ配信(exactly-once)」を前提にせずat-least-once/at-most-onceのいずれで設計するかを明示し、デデュープ機構やTTL等の保存期間制限を設けているか
- **なぜ重要か**: 分散システムでは重複処理・重複配信・リトライによる再実行が常態であり、冪等性がなければエラー処理が破綻する。また分散システムでexactly-onceの完全な実現は非現実的であり(実質はat-least-once配信+アプリ側冪等性でしか達成できない)、無制限のデデュープストアはコスト増を招く。本によってはSCD2のような手法のみが真の冪等性を保証すると明言される
- **出典**: Architecture Patterns with Python エピローグ p.226, 付録E p.262; Building Medallion Architectures 第7章コラム p.209; Designing Distributed Systems 2nd Ed Ch.2 p.12, Ch.12 p.143-144; Learning API Styles 第2章 表2-5 p.169, 第11章 p.352-353, p.371; Building Event-Driven Microservices 2nd Ed Ch.8 p.190-196

### 9. イベントストリームにおけるOut-of-order(順序逆転)・遅延到着イベントの扱いを、watermark/stream timeという技術的な仕組みと、業務上どこまで遅延を待つかという許容度の両面で定義しているか
- **なぜ重要か**: 順序逆転・遅延到着は分散イベントストリームで常態的に発生し、技術的な仕組み(watermark)だけでは解決できず、業務要件としての許容遅延も合わせて定義する必要がある
- **出典**: Building Event-Driven Microservices 2nd Ed Ch.9 p.202-203, p.216-218

### 10. ストリームと歴史データストアなど複数の書き込み先への非原子的な二重書き込み(Dual Write)を避け、CDCまたはトランザクショナルアウトボックスでデータを解放しているか
- **なぜ重要か**: 2系統への非原子的書き込みはデータの乖離(divergence)の温床であり、「大規模運用では管理困難」と明言されている(Lambda Architectureが批判される主因でもある)
- **出典**: Building Event-Driven Microservices 2nd Ed 第2章 p.42-44, 第6章 p.129, p.138-145

### 11. 集約(アグリゲート)の境界をトランザクション境界・一貫性の単位として扱い、境界内は同期的に、境界をまたぐ更新はイベント等による非同期(結果整合性)で処理しているか
- **なぜ重要か**: 複数集約を単一トランザクションで同時更新する強整合性は可用性を損なうため、整合境界を小さく保ち、境界を越えた部分は結果整合性に委ねるべき
- **出典**: DDD Reference II章 Aggregates p.16; Architecture Patterns with Python 第8章 p.130, エピローグ p.216; Building Evolutionary Architectures 2nd Ed Ch.6 p.133-134, 137-138

### 12. 結果整合性(eventual consistency)を、サービス間の直接同期問い合わせに頼らず、ドメインイベント/event-carried state transferによる「収束」として設計しているか
- **なぜ重要か**: 直接参照は結合を再発生させるため、イベントによる状態伝搬の方が疎結合を保てる。分散ノード間では「現在知りうる情報からの一貫したモデル」しか構築できないことを前提にすべき
- **出典**: Building Event-Driven Microservices 2nd Ed 第16章 p.323-331; DDD Reference II章 Domain Events p.13

### 13. 楽観的並行性制御(バージョン番号によるCAS)か悲観的ロック(SELECT FOR UPDATE等)かを明示的に選択し、両者のトレードオフ(失敗モード・性能特性の違い)を検討しているか
- **なぜ重要か**: 両者は衝突検知のタイミングと失敗モード・スループット特性が大きく異なり、無自覚な選択はデータ競合時の挙動やパフォーマンスに悪影響を与える
- **出典**: Architecture Patterns with Python 第7章 p.105-111

### 14. 自前で分散整合性ストア(独自のPaxos/RAFT実装等)を書こうとせず、実績あるミドルウェア(etcd/ZooKeeper/Consul等)に乗っているか
- **なぜ重要か**: 自前実装は複雑でバグの温床であり、「友人に自作の分散整合ストアを書かせるな」と明言されている
- **出典**: Building Microservices 2nd Ed 第12章 p.411; Designing Distributed Systems 2nd Ed Ch.10 p.106-107

### 15. 単一レプリカ(シングルトン)で許容できる可用性要件かどうかを、分散ロック(リーダー選出)導入の前にまず検討しているか
- **なぜ重要か**: 不要な複雑性(分散ロックの運用コストと障害モード)を避けるため、本当に分散ロックが必要かを先に問うべき
- **出典**: Designing Distributed Systems 2nd Ed Ch.10 p.104-106

### 16. 分散ロックにTTL(リース)を設定し、保持者のクラッシュでロックが永久保持されない設計になっているか。また処理がTTLより長くならないよう監視(ウォッチドッグ)しているか
- **なぜ重要か**: TTLがなければ保持者クラッシュ時にシステムが止まり、逆にTTL超過後も処理を続けると二重所有(オーナーシップの衝突)が起きる
- **出典**: Designing Distributed Systems 2nd Ed Ch.10 p.109-110

### 17. 分散ロックにリソースバージョン(compare-and-swapの前提値)を付与し、遅延到着した古いリクエストが別プロセスの新しいロックを誤って解除・上書きしないようにしているか。ワーカー側で「本当に自分がオーナーか」をロックサーバーにダブルチェックしているか
- **なぜ重要か**: TTL失効後にロックを失ったプロセスが処理完了時に「自分のロックを解除した」つもりで実際には別プロセスの新しいロックを誤って解除してしまうバグが起きるため
- **出典**: Designing Distributed Systems 2nd Ed Ch.10 p.109-110, 113-114

### 18. データ所有権が単一所有・共通所有・共同所有のいずれのシナリオかを識別し、それぞれに適した技術(専任所有サービス、テーブル分割、データドメイン、委譲、サービス統合等)を選んでいるか
- **なぜ重要か**: 「書き込みを行うサービスが所有者」という原則は共同所有(複数サービスが同一データを書き込む)のシナリオでは破綻するため、所有権パターンに応じた個別の対処が必要
- **出典**: Software Architecture: The Hard Parts Ch.9 p.250-262

### 19. 他サービスが所有するデータを読み取る方式(Interservice Communication/Column Schema Replication/Replicated Caching/Data Domain)を、データ量・更新頻度・整合性要件に基づいて選定しているか
- **なぜ重要か**: レプリケートキャッシュは大容量・高頻度更新データに不向きであり、Column Schema Replicationは「所有していないのに更新できる」というガバナンス上の穴を生むため
- **出典**: Software Architecture: The Hard Parts Ch.10 p.284-295

### 20. 結果整合性の実現パターン(バックグラウンド同期/オーケストレーテッド・リクエストベース/イベントベース)を、整合までの許容時間・エラーハンドリングの複雑さ・境界づけられたコンテキストの保持という観点で選定しているか
- **なぜ重要か**: バックグラウンド同期は境界づけられたコンテキストを壊すリスクがあり、オーケストレーテッド方式は応答性を犠牲にするなど、方式ごとに異なるトレードオフがある
- **出典**: Software Architecture: The Hard Parts Ch.9 p.267-279

### 21. シャーディング関数が決定性(同じキーは常に同じシャードへ)と均一性(負荷が偏らない)を両立しているか、リシャーディング時にはconsistent hashingで移動キー数を最小化しているか
- **なぜ重要か**: 決定性がないと同じリクエストが別シャードに飛び、均一性がないと負荷偏在が起きる。通常のhash%Nはシャード数変更時に全件再配置になるのに対しconsistent hashingは理論上K/N程度の移動で済む
- **出典**: Designing Distributed Systems 2nd Ed Ch.7 p.77-79

### 22. 特定シャードへの負荷集中(hot shard)を自動検知し、再配置・独立スケールできる仕組みがあるか
- **なぜ重要か**: 均一分散の前提が時間とともに崩れることはよくあり、検知・対処の仕組みがないとシステム全体が特定シャードのボトルネックで詰まる
- **出典**: Designing Distributed Systems 2nd Ed Ch.7 p.81

### 23. scatter/gatherパターンで、leaf数の増加に伴うテイルレイテンシの悪化(ストラグラー問題)を定量的に把握し、各leafをレプリカ化して単一障害点を解消しているか
- **なぜ重要か**: 単体の2秒(1%)レイテンシも5 leafへの分散で約5%、100 leafではほぼ100%の発生率に転化するため「並列化すればするほど速くなる」は誤りで、並列化の効果は漸近的である
- **出典**: Designing Distributed Systems 2nd Ed Ch.8 p.88-90

### 24. ワークキューでのワーカークラッシュ・再試行による「二重処理」を前提に、決済等の真に一貫性が必須な処理と、計算資源の無駄で済むだけの処理とを明確に区別しているか
- **なぜ重要か**: 可用性と一貫性のどちらを優先すべきかは用途依存であり、区別なく設計すると不要に複雑な一貫性保証や、逆に危険な重複実行を許してしまう
- **出典**: Designing Distributed Systems 2nd Ed Ch.10 p.114, Ch.12 p.143-144

### 25. 特定入力で必ず失敗する"poison work"に対し、再処理回数カウントと指数バックオフでワーカー全体の連鎖的クラッシュを防いでいるか
- **なぜ重要か**: 対策なしに放置すると、同じ不良メッセージの再処理が全ワーカーに連鎖的なクラッシュを引き起こしワーカー容量を失う
- **出典**: Designing Distributed Systems 2nd Ed Ch.12 p.144

### 26. バッチ/ストリーム処理において、全データの到着を待つ必要がある場面はjoin(バリア同期)、ストリーミング的な逐次集約で足りる場面はreduceという使い分けができているか
- **なぜ重要か**: joinは並列性を落としレイテンシを増すため乱用すべきでなく、要件に応じた集約方式の選択が性能に直結する
- **出典**: Designing Distributed Systems 2nd Ed Ch.13 p.148-149

### 27. (重要度: 中)障害後にバックログが急増した際、タイムスタンプ/タイムアウトベースのオートスケールや新規リクエスト優先処理などで「陳腐化した作業」を処理し続けない設計になっているか
- **なぜ重要か**: バックログは放置すると自己回復せず悪化し続けるため、陳腐化した古い作業を優先的に処理し続けるとシステム全体が回復不能になる
- **出典**: Designing Distributed Systems 2nd Ed Ch.16 p.187-188

### 28. イベントストリームの不良データ類型(破損・無スキーマ・非互換なスキーマ進化・論理的/意味的不正値・欠落・誤生成重複等)を踏まえた防御設計を行い、Breaking Schema Change時は新旧ストリームの並行書き込みなど移行計画を事前に合意しているか
- **なぜ重要か**: 無計画なスキーマ変更は下流コンシューマ全体を壊し、不良データの類型ごとに有効な対策が異なるため、体系的なタクソノミーに基づく備えが必要
- **出典**: Building Event-Driven Microservices 2nd Ed Ch.18 p.366-369, 376, Ch.21 p.431-435, Ch.4 p.87-90

### 29. GDPR等の削除・訂正要件がある領域では、コンパクション不可能なdelta eventではなく、現在の完全な状態を表すstate eventを採用しているか
- **なぜ重要か**: 差分(delta)だけのイベントは「忘れられる権利」のような法的な削除要件に構造的に対応できない
- **出典**: Building Event-Driven Microservices 2nd Ed Ch.18 p.376, p.379

### 30. (重要度: 低〜中)本番で採用するメッセージブローカーが実際に配信保証を持つかどうかを事前に検証しているか(例: Redis pub/subは配信保証を持たない)
- **なぜ重要か**: 配信保証の有無はブローカー選定によって大きく異なり、保証がないブローカーを前提に冪等性・デデュープ設計をしても根本的な取りこぼしは防げない
- **出典**: Architecture Patterns with Python エピローグ p.226
