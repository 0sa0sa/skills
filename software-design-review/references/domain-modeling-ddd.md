# ドメインモデリング・DDD

境界づけられたコンテキスト、集約、腐敗防止層、ユビキタス言語などDDDの戦略的・戦術的パターンの適用を見る。

## チェックリスト

### 1. 境界づけられたコンテキスト(Bounded Context)を明示的に定義し、チーム組織・コードベース・DBスキーマの境界と一致させているか
- **なぜ重要か**: モデルの意味は文脈依存であり、複数モデルが1つの境界に混在するとバグと混乱を生む。実装詳細が境界外に漏れると「ブリトル」な依存が生まれる。
- **出典**: DDD Reference I章 Bounded Context p.2; Building Evolutionary Architectures 2nd Ed 第5章 p.90,107-111; Building Event-Driven Microservices 2nd Ed Ch1 p.6-8

### 2. サービス/モジュールの境界をビジネスドメイン(境界づけられたコンテキスト)中心に切っているか、技術レイヤー(UI/ロジック/DB等)中心に切っていないか
- **なぜ重要か**: 技術レイヤー別の分割はチーム間依存を生み、1つのドメイン変更が全レイヤーに波及(smear)して保守性を著しく下げる
- **出典**: Building Microservices 2nd Ed 第2章 p.7,10-13; Software Architecture: The Hard Parts Ch.3 p.50-53, Ch.11 p.309-310

### 3. 最初から細粒度を狙わず、粗粒度の境界づけられたコンテキスト単位でサービス/モジュールを切り、必要になってから分割しているか
- **なぜ重要か**: 過度な初期分割はオーケストレーション・通信オーバーヘッドを増大させる
- **出典**: Building Microservices 2nd Ed 第2章 p.58-59; Building Evolutionary Architectures 2nd Ed 第7章 p.161

### 4. 境界分割の判断において、ビジネスドメイン以外の軸(変動性/volatility、データ規制、技術的制約、組織構造)も検討し、ドメイン分割を唯一の教義として固執していないか
- **なぜ重要か**: 単一の教義への固執は現実の制約(規制・技術・組織)を無視した不適切な分割を招く
- **出典**: Building Microservices 2nd Ed 第2章 p.63-68

### 5. Customerのように複数文脈で使われる概念を安易に単一モデル/単一サービスへ統合(canonicalize)せず、コンテキストごとに独自表現を持たせているか
- **なぜ重要か**: 共有は結合を生み、複数文脈を1つの万能モデルに押し込めると概念が曖昧化する。これは「同じ言葉が異なる意味を持つ」という意図しない表記揺れの問題とは逆方向で、本項は“コンテキストをまたぐ意図的なモデル差異”を守る観点である(意図しない表記揺れの解消は別項の用語集チェックで対応する)。全社共通Customerサービスがbrittlenessで失敗した実例もある
- **出典**: Building Evolutionary Architectures 2nd Ed 第5章 p.112-114; Architecture Patterns with Python 第7章 p.102; Software Architecture: The Hard Parts Ch.8 p.242-244

### 6. 集約(Aggregate)を明示的に選定し、ルートエンティティのみを外部から参照可能にして、整合性ルールを集約内で同期的に強制しているか
- **なぜ重要か**: 複雑な関連を持つオブジェクト群の整合性保証は困難であり、集約を唯一のエントリーポイントにすることで変更経路を一本化できる
- **出典**: DDD Reference II章 Aggregates p.16; Architecture Patterns with Python 第7章 p.98-99

### 7. 「1集約=1リポジトリ」の原則を守り、リポジトリが集約ルート以外のオブジェクトを返したり内部オブジェクトへの直接クエリを許していないか
- **なぜ重要か**: この規約を破ると集約が保証する整合性が崩れ、ドメイン層が単なるデータコンテナに貶められる
- **出典**: Architecture Patterns with Python 第7章 p.102; DDD Reference II章 Repositories p.17

### 8. 集約境界をトランザクション境界・分散配置の単位としても使い、境界内は同期的に、境界をまたぐ更新は非同期で処理する設計になっているか
- **なぜ重要か**: 「集約境界=トランザクション境界=分散配置単位」という三位一体の原則は、マイクロサービス時代のサガパターンや結果整合性設計の原型になっている
- **出典**: DDD Reference II章 Aggregates p.16; Architecture Patterns with Python 第8章 p.130, エピローグ p.216

### 9. オブジェクトグラフが双方向参照になっていないか確認しているか
- **なぜ重要か**: 双方向リンクは集約境界が正しく切れていないサインであり、集約設計ミスの実務的な診断基準として使える
- **出典**: Architecture Patterns with Python エピローグ p.218

### 10. エンティティは属性でなく識別子(identity)で区別し、値オブジェクトは不変(immutable)かつ識別子を持たせない設計になっているか
- **なぜ重要か**: 属性一致によるエンティティの取り違えはデータ破損を招き、値オブジェクトへの不要な識別追跡は複雑性とパフォーマンス劣化を招く
- **出典**: DDD Reference II章 Entities p.11, Value Objects p.12

### 11. 複雑な生成ロジックをファクトリに分離し、クライアントに具象クラスへの依存や内部構造の露出を強いていないか
- **なぜ重要か**: 生成責任の混在は被生成物のカプセル化を破る
- **出典**: DDD Reference II章 Factories p.18

### 12. エンティティ/値オブジェクトの属性を定義する際、本質的な属性(Essence)と偶有的な属性(Accident)を区別し、また「取引数量」のような関係に属する属性を関与エンティティ(主体)に誤って帰属させていないか
- **なぜ重要か**: 本質と偶有を混同するとコア概念に不要な属性が混入し、関係性に属する属性を主体に誤帰属させると取引ごとに異なる値が1つのエンティティの状態として固定化され、モデルが歪む
- **出典**: Semantic Software Design 第2章 p.41-43

### 13. 'Type'のような曖昧な列名・概念名や、網羅できない値を押し込める'Other'という逃げ値が使われていないか
- **なぜ重要か**: 曖昧な分類名や「その他」への押し込みは、分類軸の設計がまだ完了していないモデリング失敗の典型的なサインである
- **出典**: Semantic Software Design 第8章 p.185

### 14. 候補となる名前(エンティティ名・サービス名・分類名)の集合が、相互排他的かつ網羅的(MECE)になっているかをテストしているか
- **なぜ重要か**: 名前の集合がMECEでない場合、概念の重複や漏れがモデルに内在していることが多く、命名のテストは構造的な欠陥を検出する実務的な手段になる
- **出典**: Semantic Software Design 第3章 p.65

### 15. ドメインイベントを「起きたこと」として、過去形/命令形のドメイン言語で命名された不変の値オブジェクト(タイムスタンプ・関与エンティティの識別子付き)としてモデル化しているか
- **なぜ重要か**: ビジネス言語と一致させることで仕様のドキュメント性を高め、分散システムでの状態推論と監査を可能にする
- **出典**: DDD Reference II章 Domain Events p.13; Architecture Patterns with Python 第8章 p.121, 第10章 p.151-152

### 16. モジュール/パッケージ名がユビキタス言語の一部となり、技術的分類(レイヤ等)でなくドメイン概念の結合度で分割されているか
- **なぜ重要か**: モジュールは技術メトリクスでなく「概念」の分割であるべき
- **出典**: DDD Reference II章 Modules p.15

### 17. エンティティ/値オブジェクトの自然な責務にならない重要な処理をサービスとして切り出し、その操作の入出力・前提条件をインターフェースとして明示しているか
- **なぜ重要か**: 無理にオブジェクトへ処理を押し込むとモデルの定義が歪む
- **出典**: DDD Reference II章 Services p.14

### 18. サービス・エンティティ・値オブジェクトの事前条件・事後条件・不変条件(アサーション)をコードまたは自動テストとして明文化しているか
- **なぜ重要か**: 暗黙の副作用は実行トレースなしに理解不能な設計を生み、契約を明文化することで安全にモデルを変更・拡張できる
- **出典**: DDD Reference III章 Assertions p.22

### 19. インターフェース名が実装を知らなくても意図を読み取れる(intention-revealing)ものになっており、副作用のあるコマンドと副作用のないクエリを厳格に分離しているか
- **なぜ重要か**: 実装理解を要求する設計はカプセル化の価値を失わせ、コマンド/クエリの混在は組み合わせ爆発を招き予測可能性を損なう
- **出典**: DDD Reference III章 Intention-Revealing Interfaces p.20, Side-Effect-Free Functions p.21

### 20. ユビキタス言語を図・コード・会話すべてで統一的に使い、汎用データモデルで用語を押しつぶさず、言語の変更=モデルの変更として扱っているか
- **なぜ重要か**: 翻訳はコミュニケーションを貧弱化させ、汎用モデルへの押し込みは(IBM銀行モデルの実話のように)概念を曖昧化させる
- **出典**: DDD Reference I章 Ubiquitous Language p.3-4; Building Microservices 2nd Ed 第2章 p.52-53

### 21. チーム横断でドメイン用語集を定義し、user/customer/subscriberのような類似語の表記揺れ・意味の不一致を解消しているか
- **なぜ重要か**: 同じ言葉が人によって全く異なる意味を持つ状態(意図しない表記揺れ)は意思決定のサイロ化やモデルの分裂を招く。これは境界づけられたコンテキストごとに同一概念が意図的に異なるモデルを持つこと(別項参照)とは異なる問題であり、「文脈による意図的な差異」と「文脈を越えた意味の不一致・揺れ」を区別して扱う必要がある
- **出典**: Learning Systems Thinking p.139, 216; Semantic Software Design 第7章 p.146-147, 第8章 p.186

### 22. イベントストーミングやCRCモデリングのような協働技法で、エンジニアとドメインエキスパート/ビジネス側がドメイン語彙を合意しているか
- **なぜ重要か**: 開発者とビジネスのモデル乖離を防ぐ。言語の精緻化は開発者側だけでは成立せず、ドメイン側からも異議を唱えられる文化が必要
- **出典**: Architecture Patterns with Python エピローグ p.215, 221-222; Building Microservices 2nd Ed 第2章 p.60-61; Mastering API Architecture Ch8 p.196-197

### 23. モデルを実装に文字通り反映させる単一のモデル駆動設計を採用し、コードに触れるモデラー(hands-on modelers)を確保しているか(モデリングと実装を分業していないか)
- **なぜ重要か**: 分析と設計の乖離は洞察の往還を止め、モデラーと実装者の分業はモデルが現実から乖離する「半分壊れた制約」を生む
- **出典**: DDD Reference I章 Model-Driven Design p.6, Hands-on Modelers p.7

### 24. 境界づけられたコンテキスト内でも、継続的インテグレーションと自動テストでモデルの断片化を早期に検知する体制を敷いているか
- **なぜ重要か**: 1つのコンテキスト内でも3〜4人規模からモデルが分裂し始めるため、継続的インテグレーションは最も実務的で検証可能な戦術パターンの一つである
- **出典**: DDD Reference I章 Continuous Integration p.5

### 25. コンテキストマップを作成し、各境界づけられたコンテキスト間の関係性(upstream/downstream等)をチーム横断で明示・共有・更新しているか
- **なぜ重要か**: 個々のコンテキストだけでは他モデルとの接点が見えず、他チームが気づかずに境界をにじませるのを防ぐ
- **出典**: DDD Reference IV章 Context Map p.29

### 26. 相互に依存し合うチーム間で、パートナーシップ(共同計画・統合管理プロセス)を結んでいるか
- **なぜ重要か**: 片方の失敗が両方の失敗になる相互依存関係では、場当たり的な調整ではなく共同のプロセスが協調を保証する
- **出典**: DDD Reference IV章 Partnership p.30

### 27. 共有カーネル(Shared Kernel)を設定する場合、共有範囲を小さく保ち、変更の際に相手チームとの合意プロセスを設けているか
- **なぜ重要か**: 無調整な変更は共有カーネルの恩恵(重複排除)を失わせ、むしろ両チームを不意に壊す結合源になる
- **出典**: DDD Reference IV章 Shared Kernel p.31

### 28. 上流-下流(upstream-downstream)関係において、Customer/Supplier・Conformist(盲従)・腐敗防止層(Anticorruption Layer)・Open-host Service・Separate Waysのどの統合戦略が適切かを、無自覚な「なんとなく追従」でなく意識的に選んでいるか
- **なぜ重要か**: 関係の性質により最適な統合戦略は異なり、Conformistも統合コストを劇的に下げる正当な戦略になりうる
- **出典**: DDD Reference IV章 Customer/Supplier〜Separate Ways p.32-37

### 29. 下流として他システム(上流モデル)に依存する場合、腐敗防止層(Anticorruption Layer)を設けて自モデルの語彙に変換しているか
- **なぜ重要か**: 上流モデルの侵食がじわじわ自モデルを歪めるため
- **出典**: DDD Reference IV章 Anticorruption Layer p.34

### 30. 腐敗防止層を早すぎる抽象化・遅すぎる密結合のどちらにも陥らない「最後の責任ある瞬間」で導入しているか
- **なぜ重要か**: 早すぎる抽象化も遅すぎる密結合も進化を阻害する
- **出典**: Building Evolutionary Architectures 2nd Ed 第7章 p.165-167

### 31. 外部連携用の公開言語(Published Language)をドキュメント化し、内部モデルをそのままインターフェースとして漏洩させていないか
- **なぜ重要か**: 内部モデルをそのまま使うと硬直化し進化できなくなる
- **出典**: DDD Reference IV章 Published Language p.36

### 32. サービス境界(Open-host Service)を設ける際、プロトコルを公開・汎用化し、個別チーム固有の要求は一回限りのアダプタで吸収しているか
- **なぜ重要か**: 個別最適化の積み重ねはプロトコル保守を破綻させる
- **出典**: DDD Reference IV章 Open-host Service p.35

### 33. レガシー・無秩序な既存システムを「Big Ball of Mud」として明示的に境界で囲い、そこに洗練されたモデリングを適用しようとしていないか
- **なぜ重要か**: 境界のない混沌に精緻なモデルを適用する試みは不毛であり、境界を引いて隔離する方が実務的
- **出典**: DDD Reference IV章 Big Ball of Mud p.38

### 34. コアドメインを明文化したドメインビジョンステートメント(1ページ程度)を作成し継続的に更新しているか。またコア要素をコードやドキュメント上でハイライトし、「コア/非コア」の判別を開発者の都度の判断に委ねていないか
- **なぜ重要か**: モデル着手前でも価値提案の焦点を明文化する必要があり、コア/非コアの判別作業自体が開発者の集中力を消耗するため、恒常的に見える形にしておくべきである
- **出典**: DDD Reference V章 Domain Vision Statement p.42, Highlighted Core p.43

### 35. コア以外の汎用サブドメインを分離し、既製品や公開モデルの採用を検討しているか
- **なぜ重要か**: 汎用的な部分にコア開発者の時間を割くのは機会損失であり、既製品や外部の公開モデルで代替できる
- **出典**: DDD Reference V章 Generic Subdomains p.41; Learning Systems Thinking p.189(FedExのBuy/Build例)

### 36. 複数サービス/モデルが同一エンティティの状態遷移を共同所有せず、単一の信頼できるソース(集約の所有者)が判断する設計になっているか
- **なぜ重要か**: 状態遷移の共同所有は責任の所在を曖昧にし、整合性保証を崩す
- **出典**: Building Microservices 2nd Ed 第2章 p.47-48; DDD Reference II章 Aggregates p.16

### 37. APIがビジネス/ドメイン中心のエンドポイントのみを公開し、内部データモデルやDBスキーマを境界外に漏洩させていないか
- **なぜ重要か**: 実装詳細の漏洩は「ブリトル」な依存を生み、境界づけられたコンテキストの保護を損なう
- **出典**: Mastering API Architecture Ch8 p.194-195; Building Evolutionary Architectures 2nd Ed 第5章 p.90,107-111; Building Event-Driven Microservices 2nd Ed Ch19 p.388-389(single writer principle)

### 38. サービス/モジュール間の結合を結合の種類(Domain Coupling/Pass-Through Coupling/Common Coupling/Content Coupling)で評価し、特にContent Coupling(内部データ構造への直接アクセス)が存在しないか
- **なぜ重要か**: Content Couplingは病理的結合であり、一方の内部実装変更が他方を直接破壊するため絶対に避けるべきである
- **出典**: Building Microservices 2nd Ed 第2章 p.39-51

### 39. サービス/モジュールの命名が困難であること(例:「Notification→Email/Other」のような曖昧な名前になっていないか、「Email/SMS/Letter」のように明確に命名できるか)を、粒度分割が適切かどうかのシグナルとして扱っているか
- **なぜ重要か**: 命名の困難さは凝集度不足を示す実務的なヒューリスティックであり、良い名前がつけられないサービスはしばしば境界が誤っている
- **出典**: Software Architecture: The Hard Parts Ch.7 p.194

### 40. サービスの機能的凝集度を、独立デプロイ可能性の有無だけでなく、DDDの境界づけられたコンテキストの観点から評価しているか
- **なぜ重要か**: 共有DBや単一オーケストレーター、密結合UIがあると、見た目は独立デプロイ可能でも静的結合上は実質1つのアーキテクチャクアンタムに収束してしまう
- **出典**: Software Architecture: The Hard Parts Ch.2 p.30, 38

### 41. 既存のレイヤードアーキテクチャの内部でも、境界づけられたコンテキストを明示的に切り出し、fitness functionで境界を越えたアクセスを防いでいるか
- **なぜ重要か**: レイヤードアーキテクチャが志向する「再利用促進」とDDDが志向する「局所性」は本質的に矛盾するため、意図的な統治機構(fitness function)なしには境界がにじむ
- **出典**: Building Evolutionary Architectures 2nd Ed 第9章 p.217-220
