# マルチテナント・SaaSアーキテクチャ

テナント分離、サイロ/プール、ノイジーネイバー対策、ティアリングなどマルチテナントSaaS設計を見る。

## チェックリスト

### 1. 「マルチテナント」の判定基準を、インフラ共有の有無ではなく「単一の仕組みでonboard/deploy/manage/operateされているか」で判断しているか
- **なぜ重要か**: 専用インフラ(フルスタックサイロ)であっても運用の仕組みが単一であればマルチテナントとみなすべきであり、この再定義が本書全体の分離・ティアリング論の土台になっている。
- **出典**: Building Multi-Tenant SaaS Architectures 第1章 p.12

### 2. コントロールプレーンとアプリケーションプレーンを明確に分離しているか
- **なぜ重要か**: 分離が曖昧だと、テナント管理・課金などの横断的なSaaS機能がアプリケーションのビジネスロジックに埋め込まれてしまい、保守性・再利用性が損なわれる。
- **出典**: Building Multi-Tenant SaaS Architectures 第2章 p.27-28

### 3. テナントのステータス管理(有効化・停止等)を単一のTenant Management Serviceに一元化しているか
- **なぜ重要か**: 分散して管理すると、課金システムやユーザー管理システムとの同期が崩壊するリスクがある。
- **出典**: Building Multi-Tenant SaaS Architectures 第5章 p.126-127

### 4. テナントの非活性化(deactivation)と廃止(decommissioning)を、復帰容易性や顧客体験への影響の観点で別ポリシーとして区別しているか
- **なぜ重要か**: 両者は復帰容易性や顧客体験への影響が根本的に異なり、同一ポリシーで扱うと誤った運用判断につながる。
- **出典**: Building Multi-Tenant SaaS Architectures 第5章 p.126-129

### 5. ユーザーの設定・ポリシーとテナントの設定・ポリシーを同一視せず、意図的に分離管理しているか(B2C的な1対1マッピングの場合でも)
- **なぜ重要か**: 1対1マッピングに見える場合でも、テナント属性とユーザー属性を混在させると後のモデル変更やマルチユーザー対応で破綻する。
- **出典**: Building Multi-Tenant SaaS Architectures 第5章 p.117

### 6. テナント認証(authentication)の通過を、テナント分離(isolation)の達成と同一視していないか
- **なぜ重要か**: 認証はテナント境界への入口を確認するだけに過ぎず、実際のクロステナントアクセス防止には別レイヤーの技術的な強制メカニズムが必要になる。
- **出典**: Building Multi-Tenant SaaS Architectures 第4章 p.111、第9章 p.220-222

### 7. テナント分離をクエリへのテナントIDフィルタ追加だけに頼らず、スコープ付き認証情報(STS等)で技術的に強制しているか
- **なぜ重要か**: フィルタ漏れのコーディングミス一つでテナント境界を越えるリスクが残るため、分離はデータの物理配置ではなくアクセス制御の強制メカニズムで成立させるべきである。
- **出典**: Building Multi-Tenant SaaS Architectures 第7章 p.178-180、第9章 p.220-222

### 8. アイソレーションモデルをfull-stack/resource-level/item-levelの3段階の粒度で整理し、リソースごとに必要な粒度を意図的に決めているか
- **なぜ重要か**: 分離粒度が細かくなるほど既製の分離機構(IAM等)が乏しくなり、自作のメカニズムが必要になる。
- **出典**: Building Multi-Tenant SaaS Architectures 第9章 p.223-224

### 9. サイロ(専有)リソースにはデプロイ時アイソレーション、プール(共有)リソースにはランタイムアイソレーションを明確に使い分け、特に重量級の処理クラスタ(ストリーミング/バッチ等)では専用クラスタかネームスペース分割かをリソース優先度・予約/コミット比率・スケーリング速度まで含めたコストと分離性のトレードオフで選んでいるか
- **なぜ重要か**: サイロとプールは前提とする分離メカニズムが根本的に異なり、混同すると実効性のある分離設計にならない。特に重量級ワークロードではリソース優先度や予約比率、スケーリング速度を誤ると新規ジョブが他アプリのSLOを侵害する恐れがある。
- **出典**: Building Multi-Tenant SaaS Architectures 第9章 p.228-231、Building Event-Driven Microservices 第2版 第12章 p.274-275

### 10. テナント単位の暗号化キー所有権を要求される場合、それが実質的にサイロ型データ保存を前提とすることを理解しているか
- **なぜ重要か**: テナント自身にキー管理を求める要件は、技術的にはサイロでのデータ保存を強いることになり、プール型での実現は困難である。
- **出典**: Building Multi-Tenant SaaS Architectures 第8章 p.217

### 11. クロステナントアクセスを意図的に試みるアイソレーションテスト(侵入テスト的な検証)を実施しているか
- **なぜ重要か**: ハッピーパスのテストだけでは、テナント境界を越えられてしまう分離不備を検出できない。
- **出典**: Building Multi-Tenant SaaS Architectures 第9章 p.241-242

### 12. マルチテナント固有のロジック(テナントコンテキスト抽出・分離強制)を各サービスに重複実装せず、共通ライブラリ/サイドカー/ミドルウェアに外出ししているか
- **なぜ重要か**: 重複実装していると、分離ポリシーの変更のたびに全サービスの改修が必要になり、変更漏れによる分離不備のリスクも増える。
- **出典**: Building Multi-Tenant SaaS Architectures 第7章 p.181-186、第17章 p.442-443

### 13. サーバーレス関数の実装で、リクエスト間に前テナントの情報が残る「状態残留(state residue)」を避けているか
- **なぜ重要か**: 実行インスタンスの使い回しにより、前のテナントのリクエスト情報が次の別テナントのリクエスト処理に漏れるリスクがある。
- **出典**: Building Multi-Tenant SaaS Architectures 第11章 p.286

### 14. Kubernetes等オーケストレータの標準機能だけでマルチテナント分離が完結すると思い込んでいないか(組織横断のアクセス制御は標準機能の範囲外であることを認識しているか)
- **なぜ重要か**: 標準機能の限界を超える分離要件がある場合、フェデレーションや専用プラットフォーム(OpenShift等)の追加検討が必要になる。
- **出典**: Building Microservices 第2版 第8章 p.262-265

### 15. APIゲートウェイ層でテナント・ティアごとに許可するルート/操作を制御し、テナント境界強制の一部として設計しているか
- **なぜ重要か**: ゲートウェイ段階での粗い分離が、下流サービス側の分離実装負担を減らす。
- **出典**: Building Multi-Tenant SaaS Architectures 第9章 p.227、第11章 p.301

### 16. マルチテナントAPI基盤で、テナント間のリソース分離の粒度と権限モデル(read/write/configure等)を明確に設計しているか
- **なぜ重要か**: RabbitMQのvirtual host実例のように、分離粒度の設計そのものがAPIセキュリティの土台になる。
- **出典**: Learning API Styles 第11章 p.362

### 17. マルチテナントAPI基盤で、デフォルト認証情報を本番導入前に変更する運用プロセスがあるか
- **なぜ重要か**: デフォルト資格情報の放置はOWASP API Security Top10でも既知の具体的なセキュリティリスクである。
- **出典**: Learning API Styles 第11章 p.362

### 18. ドメイン/ワークスペースを組織単位・リージョン・規制要件で分離し、データ主権やコンプライアンス要件を満たしているか
- **なぜ重要か**: グローバル企業では地域ごとにデータ分離義務があり、ワークスペース等の分割単位で対応する必要がある。
- **出典**: Building Medallion Architectures 第4章 p.106、第11章 p.304-305

### 19. 消費者向けワークスペース/テナントにショートカット(参照)のみを提供し、直接のデータ書き込み・物理アクセスを許さない「読み取り専用テナント」構成を検討しているか
- **なぜ重要か**: データを物理コピーせずに安全にマルチテナント公開でき、物理コピーの増加に伴うデータ鮮度・一貫性管理コストの増大を避けられる。
- **出典**: Building Medallion Architectures 第7章 p.237、第8章 p.257-258

### 20. リモート/顧客環境へのリソース導入時、所有権を「誰が払うか」でなく「誰が制御・管理するか」で判断しているか
- **なぜ重要か**: 所有権の本質は支払いではなく制御にあり、この基準を誤るとBYOC等のリモート環境での責任分界・分離設計を誤る。
- **出典**: Building Multi-Tenant SaaS Architectures 第15章 p.387-389

### 21. サイロ/プールの選択を全社一律の方針ではなく、サービス・リソース単位で個別に意思決定しているか
- **なぜ重要か**: ワークロード特性・コンプライアンス要件・ノイジーネイバーリスクは粒度ごとに異なり、画一的な選択では最適化できない。
- **出典**: Building Multi-Tenant SaaS Architectures 第3章 p.75-76

### 22. 明確な要件がない限りプール型をデフォルトとし、サイロは正当化された場合のみ採用する方針になっているか
- **なぜ重要か**: サイロは効率性・俊敏性のコストを伴うため、安易に選ばず「勝ち取るもの」として扱うべきである。
- **出典**: Building Multi-Tenant SaaS Architectures 第8章 p.195、第17章 p.439

### 23. データパーティショニング方式をシステム全体で一律に決めず、ストレージ技術・ワークロード単位で選定しているか
- **なぜ重要か**: データパーティショニングは「オール・オア・ナッシングの決定ではない」ため、技術・ワークロードごとに最適な方式が異なる。
- **出典**: Building Multi-Tenant SaaS Architectures 第8章 p.195

### 24. 専用インスタンスではなく、需要パターンの異なるテナントを混在させるマルチテナント/バースト可能インスタンスやサーバーレスを優先的に選択しているか
- **なぜ重要か**: マルチテナンシーはピーク負荷を均してハードウェア利用率を60-80%超に高められる一方、専用インスタンスは利用率が低くなりがちである。
- **出典**: Building Green Software 第4章 p.65, 71

### 25. マルチテナンシー導入時、分離(isolation)を緩めることで他テナントの問題(ノイジーネイバーや障害)が波及するリスクと、分離を維持するオーバーヘッド(コスト・効率)とのトレードオフを具体的に評価しているか
- **なぜ重要か**: 分離を緩めると他テナントの問題が波及するリスクが生じるため、どの程度の分離レベルで何を許容するかを明示的に判断する必要がある。
- **出典**: Building Green Software 第4章 p.70

### 26. ノイジーネイバー対策を、サービス単位ではなく「オペレーション(個別エンドポイント)単位」で特定しているか
- **なぜ重要か**: 問題を起こすのはサービス全体ではなく特定の操作・エンドポイントのみというケースが多く、粒度が粗いと対策が過剰または不十分になる。
- **出典**: Building Multi-Tenant SaaS Architectures 第7章 p.162-163

### 27. API/コンピュート/ストレージなどレイヤーごとに、ティア別のスループット・同時実行数・クォータを個別に設定しているか
- **なぜ重要か**: 1箇所の制御だけではシステム全体としてノイジーネイバーを防ぎきれない。
- **出典**: Building Multi-Tenant SaaS Architectures 第14章 p.373-380

### 28. クラスタスケジューラ導入時、ワークロードのCPU/メモリのrequests/limitsを正確にラベリングしているか
- **なぜ重要か**: リソース要求情報が不十分だと最適なbin packingができず、結果的にノイジーネイバーやリソース浪費を招く。
- **出典**: Building Green Software 第4章 p.62

### 29. SaaS型プラットフォームのキャパシティ(Capacity Unit等)をワークロードの重要度・時間帯特性に応じて複数用意し、テナント間でブロッキングが起きないよう設計しているか
- **なぜ重要か**: 単一キャパシティでは重いバッチ処理とアドホッククエリが競合し、片方が他方のノイジーネイバーになる。
- **出典**: Building Medallion Architectures 第4章 p.105、第8章 p.258-259

### 30. 共有の恒久的なマルチテナントテスト環境のサービスアカウント・権限を事前整備し、「共有地の悲劇」化してダンピング場になるリスクを管理しているか
- **なぜ重要か**: 放置すると信頼できない環境になり、テスト結果自体が信用できなくなる。
- **出典**: Building Event-Driven Microservices 第2版 第20章 p.417, 421-422

### 31. GenAI機能(RAG・推論等)のノイジーネイバーを、リクエスト数ではなくトークンの複雑性等で測定・スロットリングしているか
- **なぜ重要か**: リクエスト数だけでは測れない負荷特性があり、従来のレート制限では不十分である。
- **出典**: Building Multi-Tenant SaaS Architectures 第16章 p.422, 426-428

### 32. GenAI機能(RAG・ファインチューニング等)にも通常のテナント分離原則(サイロ/プールの使い分け)を適用し、特にRAGデータストアはテナント特性に応じてサイロ/プールを選択しているか
- **なぜ重要か**: 新しいデータ・モデルにも既存のテナントリソースと同じ分離ポリシーが必要であり、RAGデータにも通常のデータパーティショニング原則が適用できる。
- **出典**: Building Multi-Tenant SaaS Architectures 第16章 p.416、p.421-423

### 33. テナント単位・リソース単位の消費量とコスト(cost-per-tenant)を可視化し、ティア・価格設定の妥当性を継続的に検証しているか
- **なぜ重要か**: 収益貢献が最小のテナントが、カタログサイズ等の要因でインフラコスト負担が最大になる逆転現象が起こりうる。
- **出典**: Building Multi-Tenant SaaS Architectures 第12章 p.315-321

### 34. フィーチャーフラグをティア単位のグローバルな仕組みとして運用し、テナント個別カスタマイズの抜け道にしていないか
- **なぜ重要か**: 安易な個別対応の積み重ねは「滑りやすい坂道」であり、SaaSの俊敏性を損なうアンチパターンに陥りやすい。
- **出典**: Building Multi-Tenant SaaS Architectures 第12章 p.332

### 35. ティアリングを単なる価格パッケージングではなく、デプロイモデル・分離レベル等のアーキテクチャ境界に基づいて設計しているか
- **なぜ重要か**: 安易な価格差別化だけの設計は、ビジネス・テナント双方にとって意味のある境界にならない。
- **出典**: Building Multi-Tenant SaaS Architectures 第14章 p.363-365

### 36. テナント・ティア・デプロイ方式を紐づけるマッピングテーブルを一元管理し、更新ロールアウトの基盤にしているか
- **なぜ重要か**: このマッピングなしには、ティアごとの段階的なロールアウトを一括して適用することができない。
- **出典**: Building Multi-Tenant SaaS Architectures 第11章 p.293-295

### 37. テナントコンテキストをJWT等の単一トークンとして全サービスに伝搬し、集中的なテナント解決サービスへの都度問い合わせを避けているか
- **なぜ重要か**: 集中解決サービス(Tenant Mapping Service)は全リクエストが通過するボトルネック・単一障害点になりやすい。
- **出典**: Building Multi-Tenant SaaS Architectures 第4章 p.105-107、第6章 p.139, 146

### 38. 本番投入前に、オンボーディング・スロットリング・分離戦略をカオス/負荷テストで検証しているか(例:多数テナントの短時間オンボードを模擬)
- **なぜ重要か**: 分離・ティアリング・ノイジーネイバー対策は、実際の負荷がかかるまで不備が発覚しないことが多い。
- **出典**: Building Multi-Tenant SaaS Architectures 第17章 p.445-446
