# アーキテクチャ策定プロセス・ファシリテーション

ADR作成、ワークショップ、助言プロセス、合意形成、トレードオフ分析などアーキテクチャ策定プロセスを見る。

## チェックリスト

### 1. その決定が構造・CFR・依存関係・インターフェース・構築技術に影響する「アーキテクチャ上重要な決定」かどうかを判別する基準を持ち、すべての技術決定を同列に扱っていないか
- **なぜ重要か**: 全技術決定をアーキテクチャ扱いすると優先順位付けができなくなる
- **出典**: Facilitating Software Architecture 第2章 p.33-45

### 2. 決定前に「影響を受ける関係者」と「専門知識を持つ人」の両方に助言を求めているか(アドバイスプロセスの一行ルール)
- **なぜ重要か**: これが権限分散と意思決定の速度を両立させる唯一のルールとされる
- **出典**: Facilitating Software Architecture 第4章 p.70-75

### 3. 受け取った発言が理由付きの「助言」か、理由のない単なる「意見」(助言のニアエネミー)かを見分け、「なぜ」と問い返しているか
- **なぜ重要か**: 理由を伴わない発言は権力を手放したくない無意識の表れであることがあり、見過ごすと助言プロセスが実質機能しない
- **出典**: Facilitating Software Architecture 第4章 p.92-95

### 4. ADRがDecision/Context/Options/Consequences/Adviceの構造で書かれ、採用案だけでなく却下案についても「selected because/despite」「rejected because/despite」の形で理由を明記しているか
- **なぜ重要か**: 理由のない記録は後から意思決定の妥当性を検証できず、組織学習に繋がらない
- **出典**: Facilitating Software Architecture 第6章 p.117-125, 146-148

### 5. ADRのOptionsに2つ以上(目安3-5)の選択肢が挙げられているか
- **なぜ重要か**: 選択肢が1つしかないのは「想像力の欠如」という設計上の悪臭(code smell)とされる
- **出典**: Facilitating Software Architecture 第6章 p.121, 131-132

### 6. ADRのAdviceセクションに、誰が・いつ・何を助言したかを(要約でなく)生の言葉(verbatim)で記録し、助言者自身がその記録内容の正確性を検証しているか
- **なぜ重要か**: 要約や言い換えは助言の文脈とニュアンスを失わせ、後から『なぜその助言が採用/不採用になったか』を検証できなくする。本人検証を欠くと記録の信頼性そのものが崩れる
- **出典**: Facilitating Software Architecture 第6章 p.124-125, 136-146

### 7. ADRのステータス遷移(Draft→Proposed→Accepted→Superseded/Expired/Retired等)を運用し、Accepted後は不変として扱い、変更は新ADRで記録しているか
- **なぜ重要か**: 監査可能性とトレーサビリティを確保し、決定が後から静かに書き換えられることを防ぐ
- **出典**: Facilitating Software Architecture 第6章 p.150-153; Fundamentals of Enterprise Architecture 第14章 p.224-225

### 8. ADRを開発者が日常使うツール(ソースリポジトリ/wiki/チケット管理)に置き、「アーキテクトの聖域」に隔離していないか
- **なぜ重要か**: 隔離されたADRは読まれず、組織学習やオンボーディングに活用されない
- **出典**: Facilitating Software Architecture 第6章 p.153-156

### 9. ADR群から変更ログ/ハイライトページをキュレーションしてオンボーディングに活用し、さらにレガシー改善の経緯を組織的な知見・ケーススタディとして記録・共有しているか
- **なぜ重要か**: ADRを書くだけで終わらせず、決定の蓄積を組織学習とオンボーディングの資産に転換しなければ、記録は書き手以外に使われず埋もれる
- **出典**: Facilitating Software Architecture 第6章 p.156-157; Architecture Patterns with Python エピローグ p.213-214, 220

### 10. アーキテクチャの議論・レビュー会議を「承認の場」でなく「助言の場」として運営し、「全員合意ですか?」のような承認的な言い回しを戒めているか
- **なぜ重要か**: 承認会議化(ARB的運用)は階層的思考の残滓であり、分散的な意思決定の速度を損なう
- **出典**: Facilitating Software Architecture 第8章 p.179-186

### 11. フォーラムに影響を受けるチームの代表・専門家に加え、学習目的の傍聴者も招いているか
- **なぜ重要か**: 傍聴による暗黙の組織学習がフォーラムの価値を参加者以外にも広げる
- **出典**: Facilitating Software Architecture 第8章 p.182, 190-198

### 12. ファシリテーターが『賛成ですか』でなく『このアプローチのどこに最も強く反対すべきか』と明示的に問いかけ、合意点の確認で終わらせず異論を積極的に引き出す建設的な対立(coalescent argumentation)の形になっているか
- **なぜ重要か**: 賛成点の確認だけに終始すると本質的なリスクが見過ごされる。『何にこそ反対すべきか』を具体的に問う行動に落とさないと、理念だけでは実行されない
- **出典**: Facilitating Software Architecture 第8章 p.186-190

### 13. 組織のCFR・技術戦略・原則・技術レーダーからなる「ミニマム・バイアブル・アグリーメント」が存在し、個々の決定を見て『驚き(surprise)』が生じるかどうかで、取り決めの過不足を点検しているか
- **なぜ重要か**: 暗黙の前提のまま放置すると、各決定者が何を確認すべきかの基準が揃わず、助言プロセスの土台が崩れる。『驚きの有無』という具体的な点検基準が過不足を可視化する
- **出典**: Facilitating Software Architecture 第9章 p.209-220

### 14. アーキテクチャ原則を開発チームも交えたワークショップ(例:3テーマのVenn図+ドット投票2回+ブラックハット思考)で共創し、多すぎず少なすぎない個数(目安として、Facilitating Software Architectureは8-15個のSMART原則、Building Microservices 2nd Editionは10個未満を提示しており、両書で推奨数は異なる)に絞っているか、またCFR(何をすべきか)やプラクティス(どうやるか)と混同していないか
- **なぜ重要か**: 原則は多すぎれば形骸化し少なすぎれば判断基準にならず、CFRやプラクティスと混同すると『どう作るか』の共有コミットメントが純化されない。両書の数値は異なるため、どちらか一方の目安を無批判に両書の総意として扱わないことが重要
- **出典**: Facilitating Software Architecture 第10章 p.239-246, 250-264; Building Microservices 2nd Ed 第16章 p.536-538

### 15. 決定からのフィードバックで原則・CFR・技術戦略そのものを見直す仕組み(改廃をADRとして記録する運用)があるか
- **なぜ重要か**: 原則やCFRを一度定めたまま固定すると実態と乖離する。決定の積み重ねから土台側へフィードバックするループがなければ、組織の取り決めが陳腐化しても誰も気づかない
- **出典**: Facilitating Software Architecture 第10章 p.267-272

### 16. 社内版テクノロジーレーダー(Trial/Adopt/Hold/Retire)を定期スイープで更新し、組織の集合知を可視化しているか
- **なぜ重要か**: 個々のADRに閉じた技術判断を組織全体の技術選定の文脈に接続し、同じ技術評価の重複議論を防ぐ
- **出典**: Facilitating Software Architecture 第11章 p.273-298

### 17. 重要かつ不確実性の高い決定の前に、時間制限付きの使い捨てコード調査(スパイク)を行い、決定の裏付けにしているか
- **なぜ重要か**: 「コードが議論を解決する」とされ、推測だけの議論より実証的な判断材料が得られる
- **出典**: Facilitating Software Architecture 第14章 p.352-360

### 18. アーキテクトが『最後の責任ある瞬間(last responsible moment)』まで意思決定を遅らせつつ、同時に早すぎる一般化(オーバーエンジニアリング)に陥っていないか
- **なぜ重要か**: 早すぎる決定は情報不足のまま過剰設計に向かい、遅すぎる決定は目標達成を阻害する。両極を避けるタイミング感覚が決定の質を左右する
- **出典**: Building Evolutionary Architectures 2nd Ed 第7章 p.147-148

### 19. 権限を分散した決定者が実際に動けるよう、所属感・貢献できる感覚・挑戦できる感覚といった心理的安全性を意図的に育て、旧来の決定権者自身が過去の失敗を公に総括する(サンシャイニング)などの脆弱性の開示を行い、『リーダー・リーダー』型の軽量宣言(例:「I intend to…」)で権限分散を進めているか
- **なぜ重要か**: アドバイスプロセスという権限分散の仕組みを用意しても、心理的安全性と権力者側の具体的な行動(脆弱性の開示、宣言的なコミュニケーション)が伴わなければ、現場は実際には決定を下さず機能しない
- **出典**: Facilitating Software Architecture 第15章 p.395-408, 396-397, 409-412; 第16章 p.427-434

### 20. 新規アーキテクチャ/データモデル設計時、業務担当者を集めたワークショップ(イベントストーミング、スタースキーマのグレイン合意等)でドメイン語彙・構造の合意形成を行っているか
- **なぜ重要か**: データモデルや境界は「公開インターフェース」であり、業務側のメンタルモデルと一致しなければ実用性を欠く
- **出典**: Building Medallion Architectures 第3章 p.79, 第4章 p.92; Building Microservices 2nd Ed 第2章 p.60-61; Architecture Patterns with Python エピローグ p.221-222

### 21. アーキテクチャ決定の際に「何を得て何を失うか」を明示するPros/Cons比較表を作成し、チームで共有しているか(簡易ADR的実践)
- **なぜ重要か**: トレードオフの明示を怠ると過剰設計や後からの後悔につながる
- **出典**: Architecture Patterns with Python 各章末Table(第2章 p.33の総論、例として第6章 p.93 Table 6-1)

### 22. トレードオフ議論を「It depends」のような抽象論で終わらせず、仮説を立てて実データ(コミット履歴等)で検証し、具体的コンテキスト(スケール・チームスキル・ユースケース)に基づく分析に落とし込んでいるか。他社事例やベンダー主張を文脈を無視してそのまま適用していないか(Out-of-Contextの罠・スネークオイル警戒)
- **なぜ重要か**: 文脈を欠いた情報の鵜呑みや抽象論のままの議論は、実務上の判断材料にならずトレードオフ判断を誤らせる
- **出典**: Software Architecture: The Hard Parts 第8章 p.245-247, 第15章 p.405-412; Building Green Software 第3章

### 23. 議論が実装レベル(「マイクロサービスが必要」)でなく、概念レベル(「ポータビリティが重要だから」)で行われているか(Strong vs Weak Feedback Loops)
- **なぜ重要か**: 実装レベルの議論に終始すると、その実装が解決すべき本来の価値・制約が共有されず、代替案の比較が成立しない
- **出典**: Learning Systems Thinking p.153

### 24. 意思決定前にRFCプロセスやタイムボックスを設け、議論の無限ループ(「The Never-Ending Debate」)を防いでいるか
- **なぜ重要か**: 大規模組織では全員対話は非現実的であり、スケールする合意形成の仕組みが必要
- **出典**: Fundamentals of Enterprise Architecture 第3章 p.65-66, 79

### 25. ステークホルダーとの対立時、複数のリスニング手法(識別的・情報的・選択的・共感的・包括的・批判的など)を使い分け、言葉の表面だけでなく非言語的シグナルも読み取っているか
- **なぜ重要か**: 言葉だけに頼ると真の懸念を見落とし、合意形成が形式的なものに終わる
- **出典**: Fundamentals of Enterprise Architecture 第6章 p.147-148

### 26. 標準・原則の遵守を促す際、罰則(負の条件付け)よりも「なぜその標準が必要か」の理解形成(内発的動機づけ)を優先しているか
- **なぜ重要か**: 恐怖による強制は内発的動機そのものを破壊する
- **出典**: Fundamentals of Enterprise Architecture 第10章 p.188-189

### 27. アーキテクチャ提案をStorytelling(対立→解決への道筋→解決策)の形式、あるいはコスト・性能・セキュリティとの共通点のフレーミングで伝え、危機感訴求だけに頼っていないか
- **なぜ重要か**: 論理だけでなく感情的な接続・共通価値への翻訳が合意形成を加速する
- **出典**: Fundamentals of Enterprise Architecture 第6章 p.151-152; Building Green Software 第11章 p.177-178

### 28. 解決策の議論に入る前に、問題とその価値を関係者全員が合意しているか
- **なぜ重要か**: 問題認識がずれたまま解決策を議論すると、対立する要求を安易に足し合わせた誰も使わない妥協案(「carboat」)になりかねない
- **出典**: Learning Systems Thinking p.141, 150, 163-164, 193-194

### 29. レビュー参加者が、要約して返す積極的傾聴・自分の考えを変える意思・理由への関与という3つの基本姿勢(Four Core Skillsの一部)を実践しているか
- **なぜ重要か**: これらを欠くと、議論が立場の表明の往復に終始し、理由に基づいた合意形成が成立しない
- **出典**: Learning Systems Thinking p.146-151

### 30. 議論に9種の論理的誤謬(ストローマン・権威への訴え・バンドワゴン・白黒思考・中間点・証明責任の転嫁・人身攻撃・感情への訴え・滑りやすい坂論法)が紛れ込んでいないかを具体的に点検しているか
- **なぜ重要か**: 誤謬の混入は議論の質を損ない、誤った合意形成につながる。何を指すか具体的に列挙しておかないと検知されずに通り過ぎる
- **出典**: Learning Systems Thinking p.148-151

### 31. フィードバックは「賛成/反対」でなく「何が足りないか」を問う形で求め、必要なものだけを受け取る(Golden Rule)運用になっているか
- **なぜ重要か**: フィードバックの無条件受容はフィードバックへの同意(consent)の感覚を損なう
- **出典**: Learning Systems Thinking p.142-146

### 32. 新規着手の優先順位(簡単な場所から/価値の高い場所から)を組織状況に応じて意図的に選んでいるか
- **なぜ重要か**: どちらの優先順位にも異なるリスク/説得力のトレードオフがあり、無意識に一方を選ぶと組織に合わない進め方になる
- **出典**: Building Evolutionary Architectures 2nd Ed 第9章 p.220-221

### 33. モデル・用語を声に出して「プレイ」しながら代替表現を実験し、ドメインエキスパートと開発者が同じ場で議論し、使いにくい用語には異議を唱えられる文化があるか
- **なぜ重要か**: モデルの本質的洞察は書き留められない一過性の会話に現れやすく、言語の精緻化は開発者側だけでは成立しない
- **出典**: DDD Reference I章 Ubiquitous Language p.3
