# サステナビリティ・グリーンソフトウェア

カーボン効率、運用効率優先、ハードウェア長寿命化、SCI計測などサステナビリティを見る。

## チェックリスト

### 1. マイクロサービス化やサービスメッシュ(sidecar)導入時、サービス間呼び出しの頻度・ペイロードサイズ・通信オーバーヘッドを事前に設計し、過剰な分割になっていないか確認しているか
- **なぜ重要か**: サービス間通信はローカル呼び出しより約100倍遅く電力消費も大きく、性能とエネルギー効率は強く相関する
- **出典**: Building Green Software 第3章 p.42-43

### 2. REST/JSONではなくgRPC等のバイナリRPCの採用を検討し、開発生産性とのトレードオフも含めて評価しているか
- **なぜ重要か**: バイナリRPCはRESTより約20倍高速・低電力という具体的な根拠があり、サービス間通信のグリーン化において呼び出し頻度・ペイロード設計(前項)と並ぶ重要な観点である一方、開発コストが上がるトレードオフがある
- **出典**: Building Green Software 第3章 p.42

### 3. API/ライブラリ呼び出しの回数そのものを設計レベルで減らせないか見直し、パフォーマンスプロファイリングによって過剰なAPI呼び出しや非効率なライブラリ呼び出しをボトルネックとして特定する仕組みを持っているか
- **なぜ重要か**: 汎用APIは個別最適化されたコードより多くの処理を要求するため呼び出し回数自体の削減が有効であり、プロファイリングなしでは非効率な呼び出しパターンが放置されやすい
- **出典**: Building Green Software 第3章 p.32-33, p.40

### 4. 常時起動のモノリスでなく、低優先度・遅延可能タスクを認識できるサーバーレス/非同期アーキテクチャを選び需要シフト/シェイピング(非同期ジョブ分離・グレースフルデグレード)を組み込める設計にしているか。さらに、その設計上の対応力を実際のワークロード運用(例: ML訓練を低炭素な時間帯/地域にシフトする等)に適用しているか
- **なぜ重要か**: アーキテクチャがシフト対応力を持つことは高いマシン利用率とカーボンアウェアネスを両立しやすくする前提であり、実際に適用すればML訓練の時間シフトで45-99%の削減例もある。『設計の対応力』と『実践での適用』は別の確認ポイントであり、片方だけでは不十分
- **出典**: Building Green Software 第1章 p.9-10, 第4章 p.69-71, 第5章 p.80-81, p.88

### 5. カーボンアウェア機能を各アプリ・サービスやSDKに個別実装させるのではなく、ロードバランサ/DNSレベルや集中ネットワークチームで一括実装できないか検討しているか
- **なぜ重要か**: 個々のサービスに実装を任せると重複投資と実装の不整合が生じやすく、集中実装の方が効率的にカーボンアウェアネスを組織全体に広げられる
- **出典**: Building Green Software 第5章 p.88, GSF Carbon Hack 22

### 6. コード効率化(言語書き換え等)への投資よりも先に運用効率(マシン利用率向上)を優先し、「運用効率→需要シフト/シェイピング→コード効率」の順でロードマップを組んでいるか
- **なぜ重要か**: 運用効率は低コストで5-10倍の削減効果を持ち商用ツールも既存する一方、運用最適化前のコード最適化は同じサーバー上では排出削減効果がほぼ出ない
- **出典**: Building Green Software 第1章 p.4-9, 第4章 p.55, 第13章 p.199

### 7. ゾンビワークロード(使われていないのに起動し続けているVM/サーバー)を定期的に特定・停止する仕組み(LightSwitchOps等)があるか
- **なぜ重要か**: DC移行時にサーバーの66%がゾンビだった実例があり、停止するだけで排出を大幅削減できる上セキュリティ面の利点もある
- **出典**: Building Green Software 第4章 p.67-68

### 8. 専用インスタンスでなくマルチテナント/バースト可能インスタンス・サーバーレスを優先し、需要パターンの異なるテナントを混在させてピーク負荷を均し、ハードウェア利用率を上げる設計にしているか
- **なぜ重要か**: マルチテナンシーは利用率を60-80%超に高められる一方、専用インスタンスは利用率が低くカーボンアウェアでない
- **出典**: Building Green Software 第4章 p.65, p.71

### 9. マルチテナンシー導入時、テナント間の分離(isolation)オーバーヘッドと、他テナントの問題が波及するセキュリティ/プライバシーリスクとのトレードオフを評価しているか
- **なぜ重要か**: マルチテナンシーは利用率向上という利点がある一方、分離が不十分だと他テナントの問題が波及するリスクがあり、利用率向上の利点だけでなくリスク面も採用判断に含める必要がある
- **出典**: Building Green Software 第4章 p.70

### 10. クラスタスケジューラ導入時、ワークロードのCPU/メモリのrequests/limitsを正確にラベリングしているか
- **なぜ重要か**: 情報が不十分だと最適なbin packingができず、機械利用率(運用効率)が上がらない
- **出典**: Building Green Software 第4章 p.62

### 11. ワークロードやデータを地域間で移動(ロケーションシフティング)してグリッドの低炭素な時間・場所を使う際、データレジデンシー/プライバシー法規制の制約を事前に確認しているか
- **なぜ重要か**: カーボンアウェアな地理的シフトは有効な削減手法だが法規制との衝突リスクがある
- **出典**: Building Green Software 第5章 p.84-85

### 12. 「電力は100%いつでも使える」という前提を見直し、動的電力料金やグレースフルデグレードへの対応を設計に組み込んでいるか
- **なぜ重要か**: インターネット業界の帯域可変性対応ノウハウを電力にも適用すべきという考え方で、カーボンアウェアコンピューティングの前提となる
- **出典**: Building Green Software 第7章 p.121-122

### 13. 新APIやハードウェア機能に依存する際、古いAPIの抽象化層・プロキシ・バージョン対応コンポーネントを用意して後方互換性を保ち、ハードウェアの早期陳腐化(software-defined obsolescence)を避ける取り組みをしているか
- **なぜ重要か**: 後方互換性を保たないと動作するハードウェアを陳腐化させ、製造時に発生したエンボディドカーボンを無駄にする。スマートフォン等の末端デバイスではライフタイム排出の82-95%が製造・輸送・廃棄段階で発生するため、省電力より長寿命化の方がインパクトが大きい
- **出典**: Building Green Software 第6章 p.93-96, 第2章 p.26

### 14. カーボン計測のための「ソフトウェア境界」を明確に定義しているか(SCI仕様: SCI = (E×I + M) / R)
- **なぜ重要か**: 境界が曖昧だと機能単位あたりの炭素強度(SCIスコア)を正しく算出できない
- **出典**: Building Green Software 第9章 p.149-150

### 15. カーボン計測において、GHGプロトコル・SCI(Software Carbon Intensity)・ISO14064等の既存標準を採用し、独自の指標を再発明していないか
- **なぜ重要か**: 標準化された指標を使うことで比較可能性と信頼性が確保され、独自指標は検証不能になりやすい
- **出典**: Building Green Software 第9章 p.145-151

### 16. カーボンメトリクスを、既存のSREにおける主要運用指標(いわゆる4大信号)と同様に、リアルタイムかつ標準化された形で収集・可視化する計画があるか
- **なぜ重要か**: カーボンを他の運用メトリクスと同列に扱うことで初めて継続的な改善サイクルに組み込める
- **出典**: Building Green Software 第9章 p.142-143, 第10章 p.161-162

### 17. マーケットベースの排出削減(カーボンオフセット・PPA購入等)を、自システムの「実際の」カーボン強度メトリクスの算定に混入させていないか
- **なぜ重要か**: SCI仕様はオフセット等のマーケットベース削減を明確に除外しており、混入させると実際の排出強度の改善が隠れ、グリーンウォッシングにつながる
- **出典**: Building Green Software 第9章 p.139-141, p.149

### 18. クラウド/オンプレ/ハイブリッド環境で、エネルギー使用とエンボディドカーボンがGHGプロトコルのどのスコープ(1/2/3)に属するか把握しているか
- **なぜ重要か**: スコープを正確に把握しないと組織全体の排出責任の切り分けができず、規制報告も不正確になる
- **出典**: Building Green Software 第9章 p.147-148

### 19. システム全体(ネットワーク・クライアントデバイス含む)での排出影響を考慮してアーキテクチャの境界・処理配置を決めているか
- **なぜ重要か**: サーバー側の計算をクライアントデバイスに移すと、サーバー側の排出が減っても全体の排出は増える可能性がある
- **出典**: Building Green Software 第9章 p.144

### 20. MLモデルの学習/運用において、サイズ縮小(量子化・プルーニング・蒸留)・転移学習・フェデレーテッドラーニングを検討したか
- **なぜ重要か**: Transformerモデル1回の学習が自動車5台分のライフタイム排出に相当する例があり、フェデレーテッドラーニングは集中学習よりCO2排出が少なくなる場合がある(収束速度とのトレードオフあり)
- **出典**: Building Green Software 第8章 p.127, 130-132

### 21. データ保存ポリシーを簡素化し、不要なデータをデフォルトで自動削除またはアクセス頻度に応じた低電力の長期保存媒体(テープ/Glacier等のストレージ階層)へ移行しているか
- **なぜ重要か**: 過剰なデータ保存はクエリを遅くし電力消費を増やす
- **出典**: Building Green Software 第3章 p.45, 第11章 p.173

### 22. まだ必要になっていない機能やデータを先行して実装・保存しない(Leanマインドセット)運用になっているか
- **なぜ重要か**: 過剰な先行実装・先行保存はリソースを無駄にするだけでなく、未使用コードやデータはセキュリティホールにもなりうる
- **出典**: Building Green Software 第3章 p.45

### 23. GSMM(Green Software Maturity Matrix)のような段階的成熟度チェックリストで現状レベルと次のアクションを定期的に評価し、「気候コミットメント」「CO2計測粒度」「運用効率」「電力利用」等の軸ごとに別々の成熟度計画を立てているか
- **なぜ重要か**: 測定データが揃っていなくてもレベル1→2に進める確実な手があり、ほぼ全組織がレベル1にいる現状では低コストな第一歩(例: ゾンビサーバー停止)から始められる
- **出典**: Building Green Software 第12章 p.184-185, p.188-191

### 24. GSMMのような成熟度フレームワークを、グリーンウォッシングでないことを示すシニア層向けの共通言語・進捗報告ツールとして使っているか
- **なぜ重要か**: 成熟度フレームワークを対外的な説明責任のツールとして使うことで、恣意的な自己評価ではなく体系的な進捗報告が可能になり、グリーンウォッシングの疑いを払拭しやすくなる
- **出典**: Building Green Software 第12章 p.184

### 25. アーキテクチャを一度決めたら放置せず、定期的なアーキテクチャレビュー(ADR見直し等)の議題に「このアーキテクチャ決定はカーボン効率/排出にどう影響するか」を公式な確認項目として含めているか
- **なぜ重要か**: グリーン化は一度の設計判断でなく継続的な見直しが必要であり、定期レビューの議題に明示的に含めなければ見直しが実行されないまま放置されやすい
- **出典**: Building Green Software 第3章 p.31

### 26. 自社のScope1/2/3排出量を把握し、ホスティング事業者やOSSメンテナ等のサプライヤーにグリーン化コミットメントを要求しているか
- **なぜ重要か**: SDK/インフラ提供者側の排出は顧客側のScope2/3に乗るため、サプライヤーへの圧力が最も効果的なレバーになりうる
- **出典**: Building Green Software 第9章 p.147, 第3章 p.44

### 27. EUのCBAM等の将来規制を見据え、Scope1/2/3の正確な排出報告体制整備を計画しているか
- **なぜ重要か**: 対応しないとEU市場アクセスに支障が出る可能性がある
- **出典**: Building Green Software 第13章 p.194-195

### 28. FinOps(コスト最適化)とGreenOps(カーボン最適化)の取り組みを統合し、財務・プロダクト・エンジニアリング横断で推進する組織体制になっているか
- **なぜ重要か**: コストとカーボンの最適化を別チーム・別プロセスで進めると重複や非効率が生じやすく、統合することで両方の投資判断を一体的に進められる
- **出典**: Building Green Software 第4章 p.59, 第11章 p.169

### 29. ホスティング費用削減を、カーボン削減の実用的な代理指標として経営層への説得材料に使っているか
- **なぜ重要か**: カーボン計測ツールが未成熟な現状でも、コスト削減=排出削減として示すことで投資を得やすい
- **出典**: Building Green Software 第9章 p.144, 第13章 p.196

### 30. サステナビリティを単独の訴求ではなく、信頼性・性能・セキュリティ・コストと並列または基盤として組織に説明しているか
- **なぜ重要か**: 景況が悪い時期は環境訴求単独では投資判断を動かしにくく、他の価値と結びつけることで採用が進む
- **出典**: Building Green Software 第11章 p.177-178

### 31. プロジェクト企画の初期段階で「このシステムの気候影響は?」「どう測定するか?」をステークホルダーに問いかけているか
- **なぜ重要か**: 設計がまだ紙の段階であれば変更コストが低く、後工程での手戻りを避けられる
- **出典**: Building Green Software 第8章 p.128

### 32. モバイル/IoTクライアントのバッテリー消費やネットワーク効率を設計要件として評価しているか
- **なぜ重要か**: バッテリー・ネットワーク効率はエンドユーザーデバイス側のエネルギー消費に直結する具体的なサステナビリティ要件
- **出典**: Learning API Styles 第6章 p.200

### 33. WebSocket等の常時接続がサーバーリソース(メモリ・コネクション数)に与える継続的コストを容量計画に織り込んでいるか
- **なぜ重要か**: ステートフル接続はスケーリングコストと間接的なエネルギー消費に直結する
- **出典**: Learning API Styles 第10章 p.332

### 34. アーキテクチャの意思決定記録(ADR)の比較評価軸にサステナビリティ(環境負荷・資源効率)をコストやスケーラビリティと並ぶ正式な軸として明示的に含めているか
- **なぜ重要か**: 単一軸(コスト等)だけでの意思決定を避け、環境負荷を最初から意思決定プロセスに組み込むため
- **出典**: Fundamentals of Enterprise Architecture 第1章 p.25-26
