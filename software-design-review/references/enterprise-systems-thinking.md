# エンタープライズアーキテクチャ・システム思考

組織とアーキテクチャの整合(コンウェイの法則)、ガバナンス、フィードバックループ、全体最適を見る。

## チェックリスト

### 1. 組織のコミュニケーション構造(コンウェイの法則)を自覚し、目指すアーキテクチャに合わせてチーム構造も意図的に再編しているか(逆コンウェイ戦略)
- **なぜ重要か**: 組織構造はそのままシステム構造に反映されることが実証研究(Windows Vistaのコード品質分析)でも裏付けられており、放置すると目指すアーキテクチャとチーム構造がずれ続ける
- **出典**: Building Microservices 2nd Ed 第15章 p.492-494; Building Evolutionary Architectures 2nd Ed 第9章 p.193-196; Facilitating Software Architecture 第1章 p.12-16

### 2. サービス/マイクロサービスごとのチーム・オーナーシップを明示的に追跡し、トポロジー可視化でチーム間の相互接続度を定量測定しているか
- **なぜ重要か**: 可視化しないと、ビジネス構造とのズレ(組織とアーキテクチャの不整合)が静かに蓄積する
- **出典**: Building Event-Driven Microservices 2nd Ed 第19章 p.384-385, p.397-400

### 3. 「4チームでマイクロサービスを作ると4層のAPIになる」ように、組織のコミュニケーション構造(コンウェイの法則)がAPI・サービス境界の設計にそのまま反映されてしまっていないか自覚しているか
- **なぜ重要か**: コンウェイの法則はAPI設計にも作用し、無自覚だと組織の都合がユーザー向けの境界に漏れ出す
- **出典**: Mastering API Architecture 第10章 p.232-233

### 4. チームサイズを5〜10人程度に抑えているか(Brooks's Lawの理解)
- **なぜ重要か**: 人員追加はコミュニケーションコストを増大させ、むしろ開発を遅延させる
- **出典**: Building Microservices 2nd Ed 第15章 p.494-499

### 5. マルチチーム組織では強い所有権(strong ownership)モデルをデフォルトとし、集合的所有権は小規模限定に留めているか
- **なぜ重要か**: 所有権モデルの選択がチームの責任分界とアーキテクチャの境界を一致させる
- **出典**: Building Microservices 2nd Ed 第15章 p.501-504

### 6. ガバナンスの適用メカニズム(どう守らせるか)として、ルールの「強制」でなく「最も楽な道(paved road)」を用意し、現場が自然に従う設計になっているか
- **なぜ重要か**: 強制されたルールはバイパスされ、組織の実際の行動は最も楽な経路に従う(「Kubernetesを使いたくて組織を変えたのではなく、組織を変えたくてKubernetesを使った」)
- **出典**: Building Microservices 2nd Ed 第15章 p.510-512

### 7. エンタープライズアーキテクトが個別技術選定でなくプラットフォームAPIレベルでガバナンス可能な単位(fitness function)の定義に注力し、現場チームの技術選択の自由度を守っているか(過去のトラウマへの固執=Frozen Caveman antipatternを避けているか)
- **なぜ重要か**: 個別技術まで統制すると画一的すぎる過剰設計になる
- **出典**: Building Evolutionary Architectures 2nd Ed 第4章 p.73-76

### 8. 全社共通のガバナンス要件(セキュリティパッチ適用等)をfitness functionとして自動化し、各チームのパイプラインへ即座に展開できる仕組みがあるか
- **なぜ重要か**: 手動プロセスへの依存は適用の遅延を招き重大インシデントにつながる(Equifaxゼロデイ事件)
- **出典**: Building Evolutionary Architectures 2nd Ed 第9章 p.216-217; Software Architecture: The Hard Parts 第1章 p.12

### 9. ガバナンスの適用範囲(どこまで課すか)として、画一的な「全項目チェックシート」ではなく、サービス/ドメインごとにリスクに応じて必要なガバナンス項目を選べる仕組みになっているか
- **なぜ重要か**: 一律適用は過剰設計を招き組織全体の速度を落とす
- **出典**: Building Evolutionary Architectures 2nd Ed 第9章 p.223

### 10. ガバナンスの力学(「Enable=やりやすくする」と「Enforce=強制する」のバランス)を両面で設計し、どちらか一方に偏っていないか
- **なぜ重要か**: enable偏重はカオスを招き("The Free-for-All")、enforce偏重は学習ループを止める("The Reporter")
- **出典**: Fundamentals of Enterprise Architecture 第5章 p.134-137

### 11. アーキテクチャ決定の承認権限(誰が決めるか)を、決定の頻度(Volume)と影響範囲(Impact)の2軸でチーム/事業部/エンタープライズの階層に適切に分散しているか
- **なぜ重要か**: 全決定をエンタープライズレベルでレビューするとボトルネック化し、逆に放任すると全社的リスクを見落とす
- **出典**: Fundamentals of Enterprise Architecture 第14章 p.226-229

### 12. ガバナンスの全体構造として、中央チームが標準・ガイドラインを設定し、各ドメインがそれに従って自律的に実行する「govern centrally but empower locally」の役割分担になっているか
- **なぜ重要か**: 連合型ガバナンスは中央統制とドメイン裁量のバランスを取る(実企業2社の実例)
- **出典**: Building Medallion Architectures 第9章 p.280-281, 第10章 p.284, 第11章 p.318

### 13. EA組織にStrategy(戦略)・Enablement(実現支援)・Oversight(ガバナンス・リスク・コンプライアンス)の3機能全てが揃っているか
- **なぜ重要か**: どれか1つを欠くと「戦略はあるが実行されない」「実行はあるが検証されない」状態になる
- **出典**: Fundamentals of Enterprise Architecture 第1章 p.8-10

### 14. 組織モデル(中央集権/連邦型/ハイブリッド)を、画一的な正解を前提とせず自社の規模・文化に合わせて意図的に選択しているか
- **なぜ重要か**: どのモデルにもトレードオフがあり万能解は存在しない
- **出典**: Fundamentals of Enterprise Architecture 第1章 p.17-20

### 15. データ・プラットフォーム等に関わる複数チーム/ドメインの決定や統合要件がサイロ化して重複・分断しないよう、集約ドメインや「コンシューマ・プロバイダ」パターンで整理・統合する仕組みがあるか(各ビジネスユニットが同じ統合作業を繰り返していないか)
- **なぜ重要か**: サイロ化した意思決定は統合されずに終わり組織全体のアライメント失敗を生み("The Silo"の実例)、重複した個別最適は全体最適を損なう
- **出典**: Fundamentals of Enterprise Architecture 第3章 p.78; Building Medallion Architectures 第11章 p.309-310, p.313-315

### 16. バックエンド集約層(BFF/集約サービス等)をチーム境界に応じて比較選定し、集約層が「共有地の悲劇」としてビジネスロジックの漏れ込み場所になっていないか監視しているか
- **なぜ重要か**: 複数チームが共有する集約層は責任の所在が曖昧になりやすい
- **出典**: Building Event-Driven Microservices 2nd Ed 第17章 p.357-358

### 17. 全社横断で使われるコアエンティティ(例: Customer)を安易に単一の統合サービスへ集約していないか、brittleness(変更波及)のリスクを評価しているか
- **なぜ重要か**: 保険会社6事業部がCustomerを統合サービス化し失敗した実例があり、再利用性は抽象化の美しさでなく変更頻度の低さで決まる
- **出典**: Software Architecture: The Hard Parts 第8章 p.242-244

### 18. データ消費側にコストを配分し、データ提供者には共有・品質向上のインセンティブを与える仕組み(virtual P&L等)を検討しているか
- **なぜ重要か**: 提供者側だけにコストを負わせる設計はデータ共有という全体最適行動を阻害する
- **出典**: Building Medallion Architectures 第9章 p.275-276

### 19. CFO/予算編成の責任者が、アーキテクチャ量子(サービス)の数とコーディネーションコストの関係(スイートスポット)を理解した上で予算計画をしているか
- **なぜ重要か**: 量子を増やしすぎるとコーディネーションコストが支配的になり、過剰分割がコストに跳ね返る
- **出典**: Building Evolutionary Architectures 2nd Ed 第9章 p.207-208

### 20. 変更を本番投入した後、その意図した効果を実際に測定するフィードバックループを設計しているか
- **なぜ重要か**: フィードバックがなければ変更が組織学習に繋がらない
- **出典**: Learning Systems Thinking p.146

### 21. 提案されている対策が表面的な対症療法(Band-Aid)に留まらず、氷山モデル(イベント→パターン→構造→メンタルモデル)で根本原因に対処しているか検証しているか
- **なぜ重要か**: リンター追加のような対策はバグを減らしても「恐怖に基づく文化」のような根本原因を解決しない
- **出典**: Learning Systems Thinking p.43-50, p.157-159, p.223-225

### 22. 意思決定の過程に構造化された透明性があるか、情報の非対称な「密室」からトップダウンで降りてくる構造になっていないか
- **なぜ重要か**: 構造化された透明性の欠如はフィードバックループを機能不全にする
- **出典**: Learning Systems Thinking p.140

### 23. 最小の変更で最大の効果を生む介入点(レバレッジポイント)を探しているか、場当たり的な対処で終わっていないか
- **なぜ重要か**: 場当たり的な対処は局所最適に留まり、システム全体を変えない
- **出典**: Learning Systems Thinking p.209-211

### 24. 成功指標が単一の数値(収益等)に偏らず、システム全体・影響を受ける人々への影響を含んでいるか
- **なぜ重要か**: 利益のみで成功を測ると環境・社会等への悪影響を見逃す(全体最適の欠如)
- **出典**: Learning Systems Thinking p.222-224

### 25. 意思決定の権限が役職や階層上の地位でなく、情報・専門性への近さに基づいて与えられているか(現場に最も近いチームが一次的な決定権を持ち、上位階層はマネジメント権限の行使でなく情報の集約・伝達の役割に限定されているか、を具体的な決裁フローで確認する)
- **なぜ重要か**: 権力構造として運用される階層は意思決定の集中とフィードバック遮断を招く。コンウェイの法則が示すように、システムリーダーシップはマネジメント職位と無関係である
- **出典**: Learning Systems Thinking p.206, p.241

### 26. 個々には正しく動作するコンポーネント(別チーム所有)同士の相互作用が破局的な障害を生まないか、システム横断で検証しているか。また、エラー率が「低すぎる/ゼロである」ことも処理停止等の異常のシグナルとして監視しているか(ambient error rate)
- **なぜ重要か**: 個々には正しいコンポーネントでも相互作用次第で破局的障害が起きる(あるチームの404処理が別チームのガベージコレクション処理と結合し、全ユーザーの写真を誤って全削除した実例)。また「エラーが出せない」障害は低エラー閾値のアラートでは検知できない
- **出典**: Designing Distributed Systems 2nd Ed 第16章 p.179-185

### 27. TOGAF等の「ビッグフレームワーク」を最初から全社規模で導入せず、小さなモデリングから始めているか
- **なぜ重要か**: 重量級フレームワークの一括導入は「大抵間違い」であり、小さく始めて段階的に拡張する方が組織の実情に適応できる
- **出典**: Learning Systems Thinking p.183

### 28. 「重複する非差別化作業」「同じ論点の反復議論」「技術論優先」のような組織不整合のシグナルを継続的に監視しているか
- **なぜ重要か**: これらは技術的なチーム間整合だけでなく組織のビジョン・ゴールへの有効性整合が崩れている初期シグナルである
- **出典**: Facilitating Software Architecture 第9章 p.213-215

### 29. EAが「象牙の塔(Ivory tower)」や「障害物(Blocker)」と見なされていないかを、現場チームからのフィードバック(満足度調査、EAへの相談・レビュー依頼件数の増減など)で定期的に確認し、Enabler/Technology leaderとして実際に認知されているかを検証しているか
- **なぜ重要か**: 権威はあるが実行可能性のない勧告は価値を生まず、過剰な統制はアーキテクチャを敵にする。自己評価だけでは現場との乖離に気づけない
- **出典**: Fundamentals of Enterprise Architecture 第1章 p.6, 第11章 p.199

### 30. 「イベントブローカー/プラットフォームをsingle source of truthとして受け入れる組織文化」が技術導入成功の前提条件であるという認識を組織内で共有しているか
- **なぜ重要か**: 技術だけでなく組織文化の合意形成が必要
- **出典**: Building Event-Driven Microservices 2nd Ed 第6章 p.155, 第22章 p.445-446

### 31. インシデント後に「犯人探し文化」を避け、blameless postmortemで学習する文化を醸成しているか
- **なぜ重要か**: 犯人探しは学習を止め再発を防げない(Telstra社の大規模障害でCOOが「一人の人為的ミス」と公表した後も障害が続き、COO自身が辞任した実話)
- **出典**: Building Microservices 2nd Ed 第12章 p.415-417

### 32. EA組織の成熟度評価に静的な「成熟度モデル(5段階)」をそのまま使わず、ビジネスアウトカムベースのケーパビリティギャップ分析(アウトカム定義→ケーパビリティ特定→ギャップのマッピング)を用いているか
- **なぜ重要か**: 成熟度モデルは「静的・文脈欠如・線形前提・用語がネガティブで防御的反応を招く」と明確に批判されており、アウトカム起点の分析の方が実情に即した評価ができる
- **出典**: Fundamentals of Enterprise Architecture 第12章 p.205-212

### 33. 技術戦略が「何をするか」だけでなく「何をしないか」まで明示しているか(「反対のことが馬鹿げて聞こえなければ戦略ではない」)
- **なぜ重要か**: 何をしないかが書かれていない戦略は誰も反対しようのない当たり障りのない文書になり、実質的な意思決定の指針にならない
- **出典**: Facilitating Software Architecture 第9章 p.231-233

### 34. チーム間の技術的な整合(重複作業や反復議論の有無)だけでなく、組織のビジョン・ゴールに対する「有効性」そのものの整合を測っているか(全員が同じ方向を向いて漕いでいるか、というドラゴンボートの比喩)
- **なぜ重要か**: 技術的に整合していても向かっている方向(ビジョン・ゴール)がずれていれば組織全体としては非効率になる
- **出典**: Facilitating Software Architecture 第9章 p.209-213

### 35. レジリエンシーを、タイムアウト・リトライ・サーキットブレーカー等の技術パターンだけでなく、人・プロセス・組織を含むシステム全体の性質として捉えているか
- **なぜ重要か**: 技術パターンのみに頼ると組織的な障害対応力(エンタープライズ・システム思考)が育たず、技術的対策だけでは防ぎきれない障害に対応できない
- **出典**: Building Microservices 2nd Ed 第12章 p.388-391, p.397-405
