# データアーキテクチャ

メダリオン/レイクハウス層構造、データパイプライン、スキーマ管理、キャッシュなどデータアーキテクチャを見る。

## チェックリスト

### 1. メダリオン(Bronze/Silver/Gold)を固定的な物理層ではなく論理層として捉え、組織の成熟度や要件変化に応じてサブレイヤー分割(ランディング/ステージング/アーカイブ等)やレイヤー数自体を増減できる柔軟性を持たせているか
- **なぜ重要か**: 業界標準の3層構成が常に正解とは限らず、実企業も教科書的な3層構造から大きく逸脱している。固定的に扱うと組織固有の要件に対応できなくなる
- **出典**: Building Medallion Architectures 第3章p.51、第8章p.248、第11章p.305-312

### 2. Bronze層のスキーマ管理方針(schema-on-read/schema-on-write)を明示的に決定し、フォーマット・完全性チェックなどの技術的検証をゲートとして機能させているか
- **なぜ重要か**: schema-on-readは「データモデリング不要」という誤解を生みやすく、適切な検証なしでは品質劣化が下流に伝播する
- **出典**: Building Medallion Architectures 第3章p.56-61

### 3. データクレンジング(業務知識が必要)をSilver層の責務、構文・フォーマット等の技術的検証をBronze層の責務として明確に役割分離しているか
- **なぜ重要か**: クレンジングルールの作成にはビジネスロジックの深い理解が必要であり、技術検証と混在させると責任境界が崩れる
- **出典**: Building Medallion Architectures 第3章p.64-66

### 4. Silver層ではソースシステムとの1対1整合を基本方針とし、複数ソースの統合をGold層に意図的に遅らせているか(Silver層で統合する場合はその理由が明確か)
- **なぜ重要か**: 早期統合はアプリケーション間の不要な結合を生むため。参照データのみ例外的にSilver層で統合する場合も理由付きで判断すべき
- **出典**: Building Medallion Architectures 第3章p.71、第9章p.271、第10章p.290

### 5. Gold層のモデリング手法(スタースキーマ/One-Big-Table/Galaxy schema)を、想定利用者(SQLが苦手な業務ユーザーかデータサイエンティストか)に応じて選択しているか
- **なぜ重要か**: スタースキーマは高性能だが業務ユーザーには理解しづらく、OBTは単純だが更新コストが高いなどトレードオフが異なる
- **出典**: Building Medallion Architectures 第3章p.78, 82-84

### 6. データストアの種類(Relational/Key-Value/Document/Column-Family/Graph/NewSQL/Cloud Native/Time-Series)を、学習容易性・モデリング容易性・スケーラビリティ/スループット・可用性/分断耐性・一貫性・言語サポート・読み書き優先度の7基準で比較評価しているか
- **なぜ重要か**: 『選択のパラドックス』が示す通り各データベース種類は異なるトレードオフに最適化されており、この評価を欠くとポリグロット永続化やGold層モデリングの選択が場当たり的になる
- **出典**: Software Architecture: The Hard Parts 第6章p.161-179

### 7. 分析データ基盤をデータウェアハウス/データレイク/データメッシュのいずれにするか、スキーマ変更容易性・ガバナンス・スケーラビリティ・所有権の観点で比較評価しているか
- **なぜ重要か**: 各アーキテクチャは特定の課題を解決するために生まれた歴史があり、データメッシュも常に適切とは限らず組織の成熟度・チーム数に依存する
- **出典**: Software Architecture: The Hard Parts 第14章p.382-394、Building Medallion Architectures 第1章p.7-30

### 8. Data Meshの4原則(ドメインオーナーシップ、データのプロダクト化、セルフサーブ基盤、連合ガバナンス)を踏まえ、分析データの所有権をドメインチームに委譲しているか
- **なぜ重要か**: 中央集権的データ基盤のボトルネックを避けられる
- **出典**: Building Evolutionary Architectures 2nd Ed 第5章p.119-123

### 9. Bronze/Silver/Gold全層でDelta Lake等のACID対応テーブル形式を用い、並行読み書き時の整合性と復旧をトランザクションログで保証しているか
- **なぜ重要か**: Parquet単体ではトランザクション保証がなく、整合性と復旧の基盤を欠く
- **出典**: Building Medallion Architectures 第1章p.26-27、第2章p.46-47

### 10. パイプラインの各処理(append/merge/overwrite)が再実行しても同じ結果になる冪等性を満たす設計になっているか
- **なぜ重要か**: 冪等性のないパイプラインは再実行時にデータ不整合を招く。著者はSCD2のみが真の冪等性を保証する手法だと明言し、これを「鍵となる設計原則」と位置づけている
- **出典**: Building Medallion Architectures 第7章コラムp.209

### 11. ストリーム処理でexactly-once/effectively-once処理を実現するため、トランザクション対応ブローカーかデデュープ機構を明示的に選び、デデュープストアにTTL等の制限を設けているか
- **なぜ重要か**: at-least-once/at-most-onceのみでは不正確な結果を生み、一方で無制限のデデュープストアはコスト増大を招くため、明示的な設計判断が必要
- **出典**: Building Event-Driven Microservices 2nd Ed 第8章p.190-196

### 12. フルロード/増分ロード(append/merge)を区別し、各ソースの配信特性(全件抽出か差分か)に応じた処理パターンを選んでいるか
- **なぜ重要か**: 誤った戦略(例: 差分配信にdrop&overwriteを使う)はデータ損失を招く
- **出典**: Building Medallion Architectures 第3章p.52-54

### 13. MERGE/UPSERT操作を導入する前に、ソースデータの重複や非クリーン性を検証し、競合時の挙動(whenMatched/whenNotMatched等)を明示的に設計しているか
- **なぜ重要か**: 複雑なMERGE条件は検証不足だと失敗しやすい
- **出典**: Building Medallion Architectures 第3章p.53-54、第5章p.131-132

### 14. Dual Write Antipatternを避け、CDC(Change Data Capture)かトランザクショナルアウトボックスパターンでデータを解放しているか
- **なぜ重要か**: 2系統への非原子的書き込みは不整合の温床になる
- **出典**: Building Event-Driven Microservices 2nd Ed 第6章p.129, 138-145

### 15. 冪等かつメタデータ駆動のパイプライン(汎用スクリプト+メタデータリポジトリ)を採用し、ソースごとに個別パイプラインを重複実装していないか
- **なぜ重要か**: コード削減・保守性・スケーラビリティの観点で有利
- **出典**: Building Medallion Architectures 第5-6章p.124, 151, 160

### 16. データ品質エラーをquarantine(検疫)テーブルに隔離し、ダウンストリームへの波及を防ぐ基準(厳格停止/柔軟継続)を定義しているか
- **なぜ重要か**: 不整合データの無制限な伝播を防ぐため
- **出典**: Building Medallion Architectures 第6章p.167

### 17. PII/機密データをパイプライン入口(Bronze層)で検知・暗号化・分離(例: 個人ごとの対称鍵)し、「忘れられる権利」への対応(鍵破棄による匿名化)を組み込んでいるか
- **なぜ重要か**: GDPR等の法的要件に対応するための実務的設計
- **出典**: Building Medallion Architectures 第8章p.248

### 18. データマイグレーションに頼らず、状態ストア/テーブルの再構築(rebuild)を優先する方針になっているか
- **なぜ重要か**: マイグレーションは危険で不整合の温床になると明記されている
- **出典**: Building Event-Driven Microservices 2nd Ed 第8章p.189

### 19. ストリーム処理の状態ストアを内部(embedded)か外部(external)か、レイテンシ・耐久性・コストの観点で選定しているか
- **なぜ重要か**: 内部状態ストアは高速だがブローカーへの依存が強く、外部状態ストアはデータ局所性に優れる一方でレイテンシが増すというトレードオフがあるため
- **出典**: Building Event-Driven Microservices 2nd Ed 第8章p.179-186

### 20. 複数ストリームを結合する際、パーティション数とパーティショナーを揃える(copartition)設計になっているか
- **なぜ重要か**: 揃っていないと結合が正しく行えない
- **出典**: Building Event-Driven Microservices 2nd Ed 第2章p.33-34、第8章p.172-174

### 21. イベントに何を含め何を含めないかを「頻度」と「サイズ」の両面で判断しているか(高頻度×大サイズのイベントは配信・処理コストを爆発させる)
- **なぜ重要か**: イベントのペイロード設計を誤ると、配信基盤・コンシューマ側の処理コストが指数的に増大するため
- **出典**: Building Event-Driven Microservices 2nd Ed 第7章p.164-165

### 22. GDPR等の削除・訂正要件がある場合、コンパクション不可なdeltaイベントではなくstate eventを採用しているか
- **なぜ重要か**: deltaイベントは法的要件(忘れられる権利)に対応不能
- **出典**: Building Event-Driven Microservices 2nd Ed 第18章p.376, 379

### 23. スキーマ変更時にExpand/Contractパターンを用い、移行期間中は新旧両方のスキーマをサポートしているか
- **なぜ重要か**: 統合先を壊さず段階的に移行できる
- **出典**: Building Evolutionary Architectures 2nd Ed 第6章p.128-132

### 24. ソーススキーマは必ず変化するという前提に立ち、スキーマ進化(mergeSchema、Auto Loaderのスキーマ進化モード等)を前提とした設計と、破壊的変更時のロールバック手順(Delta time travel等)を用意しているか
- **なぜ重要か**: ソーススキーマは時間とともに必ず変化するため
- **出典**: Building Medallion Architectures 第2章p.58-59、第3章p.56-59

### 25. SCD(Slowly Changing Dimension)をType1(上書き)かType2(追記)か、履歴アクセスの業務要件に基づいて意図的に判断し、どの層(Silver/Gold)に実装するか決めているか
- **なぜ重要か**: デフォルトのType1は履歴を失う。配置論争は業界内でも未解決であり意図的な判断が必要
- **出典**: Building Event-Driven Microservices 2nd Ed 第7章p.166-168、Building Medallion Architectures 第3章p.69、第6章p.175

### 26. ビジネスキー(自然キー)とサロゲートキーの役割を区別し、どの層でサロゲートキーを生成するかを意図的に決定しているか
- **なぜ重要か**: 混在させると履歴管理や結合の整合性が崩れる
- **出典**: Building Medallion Architectures 第3章p.69-70

### 27. 複数ドメインで共通利用されるマスターデータ/参照データについて、MDM(マスターデータ管理)等で一元管理しているか
- **なぜ重要か**: ドメインごとに異なる解釈のモデルが量産されると分析モデル・ETL・データプロダクトに矛盾が蓄積する
- **出典**: Building Medallion Architectures 第1章p.30-31、第11章p.313-318

### 28. NoSQLの「スキーマレス」という表現を誤解せず、暗黙のスキーマは常に存在するという前提で集約境界(aggregate orientation)を設計しているか
- **なぜ重要か**: 「スキーマレス」は誤解を招く表現であり、適切な集約境界決定の難しさを過小評価すると分析・保守が困難になる
- **出典**: Software Architecture: The Hard Parts 第6章p.165, 169

### 29. すべての列をNOT NULL前提で設計し、NULL許容は意図的な例外として明示的に扱っているか
- **なぜ重要か**: NULL許容の多用はモデリング失敗の典型的なサインになる
- **出典**: Semantic Software Design 第8章p.185

### 30. 単一のデータ技術に固執せず、ワークロードに応じたポリグロット永続化を検討し、その正当化を技術的理由だけでなくビジネス課題に翻訳してADR化しているか
- **なぜ重要か**: 画一的なリレーショナルDB固執は機会損失になる一方、採用の正当化を関係者に伝えるには技術論だけでは不十分
- **出典**: Building Evolutionary Architectures 2nd Ed 第6章p.142-143、Software Architecture: The Hard Parts 第6章p.179-184

### 31. サービング層(Power BI, Cosmos DB, Azure SQL等への複製)を導入する場合、単一サービスで全要件(一貫性・可用性・キャッシュ・鮮度)を満たせないことを前提に、複数サービスを組み合わせているか
- **なぜ重要か**: 「全てを完璧にこなすサービスは存在しない」と明言されており、単一サービスへの過度な期待は要件の取りこぼしを招く
- **出典**: Building Medallion Architectures 第3章p.84-85、第7章p.219

### 32. キャッシュの配置場所と無効化戦略(TTL/通知ベース/write-through等)を目的(レイテンシ/一貫性/堅牢性)に応じて選定してキャッシュ層を増やしすぎない「黄金律」を守るとともに、ローカル(アプリ内メモリ)キャッシュとグローバル(共有)キャッシュを用途に応じて使い分け、ローカルキャッシュのメモリ使用量が無制限に増大しない設計になっているか
- **なぜ重要か**: キャッシュ層が増えるほど無効化の複雑さと不整合リスクが増す一方、ローカルキャッシュはヒット率最適化に弱く各インスタンスでの重複保持がメモリを圧迫するため、両者を併せてトレードオフ判断する必要がある
- **出典**: Building Microservices 2nd Ed 第13章p.437-447、Designing Distributed Systems 2nd Ed 第16章p.183

### 33. キャッシュ層をWebサーバー/アプリケーション層と分離した独立のレプリケートサービング層として構築しているか(サイドカー方式を採る場合は、アプリとキャッシュで最適なレプリカ数・サイズの特性が異なることによるスケールのミスマッチに注意しているか)
- **なぜ重要か**: キャッシュとアプリケーションでは最適なレプリカ数・サイズの特性が異なる(少数巨大 vs 多数小型)ため
- **出典**: Designing Distributed Systems 2nd Ed 第6章p.59-60

### 34. 「オプション」として追加したキャッシュ等のコンポーネントが、時間とともに実質的に必須コンポーネント化していないか定期的に再評価し、信頼性・監視の重要度評価がそれに追いついているか確認しているか
- **なぜ重要か**: 性能改善のための任意追加要素は、システムがその存在に依存して成長するうちに事実上の必須コンポーネントへ変質するが、設計上の重要度評価が追いついていないことが多い
- **出典**: Designing Distributed Systems 2nd Ed 第16章p.182-183

### 35. 『データプロダクト』を自組織内で明確に定義し(どの層のデータが対象か、再利用性の基準は何か)、業界標準の不在を認識した上で独自ガイドラインを策定しているか
- **なぜ重要か**: データプロダクトやデータコントラクトには業界標準のタクソノミーが存在せず、他社の標準を待つのではなく自社の標準を今すぐ作る必要があるため
- **出典**: Building Medallion Architectures 第7章p.222

### 36. データ分解を、データ統合要因(外部キー・ビュー・トリガー、単一トランザクション単位の必要性)とデータ分離要因(変更管理・接続管理・スケーラビリティ・障害耐性・アーキテクチャクアンタム・DB最適化)の両面でバランスさせているか
- **なぜ重要か**: 統合要因のみ、あるいは分離要因のみに偏ると、過度な結合または過度な分散のいずれかに陥るため
- **出典**: Software Architecture: The Hard Parts 第6章p.132-150
