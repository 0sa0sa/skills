# API設計

REST/GraphQL/gRPC、バージョニング、契約、破壊的変更管理などAPI設計を見る。

## チェックリスト

### 1. 同期/非同期、リクエスト-レスポンス/イベント駆動などの通信スタイルを、具体的な技術選定より先に意識的に決めているか
- **なぜ重要か**: 通信スタイルの選択が後続のAPI実装・一貫性モデル全体の前提を規定するため、技術選定を先行させると設計の軸がぶれる
- **出典**: Building Microservices 2nd Edition 第4章 p.93-95

### 2. サービス間(east-west)通信と外部(north-south)通信を区別し、east-westには高性能なgRPC/HTTP2、north-southには互換性重視のRESTなど適した方式を選んでいるか
- **なぜ重要か**: east-westは自社管理下で性能最適化できるが、north-southは制御の効かない外部消費者向けのため互換性を優先すべき
- **出典**: Mastering API Architecture 第1章 p.20-22

### 3. REST・gRPC・GraphQLを「どちらが優れているか」でなく、用途(リソースモデル中心/サービス間性能/複数サービス集約とクライアント主導フィールド選択)で選定しているか
- **なぜ重要か**: 各スタイルは異なる課題の解決を意図して設計されており、優劣論に基づく選択は誤った適用を招く
- **出典**: Mastering API Architecture 第1章 p.7-8; Learning API Styles 第1章 表1-1 p.18

### 4. REST表現とgRPC/protoの定義を無理に単一の「ゴールデンスペック」へ統合しようとしていないか
- **なぜ重要か**: 両者間の変換はロスが多く、フィールド順序など細部の違いで互換性が壊れやすい
- **出典**: Mastering API Architecture 第1章 p.22-24

### 5. 自称「REST API」がRichardson Maturity Model上どのレベル(HATEOAS有無)にあるかをチームで認識・合意しているか
- **なぜ重要か**: 用語の誤解はドキュメントやクライアント設計の齟齬を生み、業界の大半の「RESTful API」はHATEOASを実装していない現実がある
- **出典**: Learning API Styles 第5章 p.159-163

### 6. イベント駆動通信において送信元が受信者の存在を知らない疎結合設計になっているか、またイベントの内容設計(IDのみの薄いイベント/完全な詳細を含む厚いイベント)を意識的に選んでいるか
- **なぜ重要か**: 送信元が受信者を意識する設計は結合を生み、イベント粒度の選択はペイロードサイズ・結合度・再取得コストのトレードオフを左右する
- **出典**: Building Microservices 2nd Edition 第4章 p.108-115

### 7. APIゲートウェイとサービスメッシュの責務を混同せず、ゲートウェイにビジネスロジックやプロトコル変換を詰め込みすぎていないか(Gateway-as-ESBアンチパターン)
- **なぜ重要か**: 業務ロジックの混入はリリースのロックステップ化を招き、ESB全盛期の失敗を繰り返す
- **出典**: Building Microservices 2nd Edition 第5章 p.162-166; Mastering API Architecture 第3章 p.81-83

### 8. 全east-westトラフィックをエッジのAPIゲートウェイ経由にする「Gateway Loopback」に陥っていないか
- **なぜ重要か**: ボトルネック・単一障害点・コスト増を招くため、サービス間通信にはサービスメッシュの方が適切な場合が多い
- **出典**: Mastering API Architecture 第3章 p.81-82

### 9. 明示的スキーマを採用し、構造的破壊的変更をCI上で自動検知する仕組み(Protolock、openapi-diff等)を組み込んでいるか
- **なぜ重要か**: 人手レビューに頼ると破壊的変更の検知が遅れ下流コンシューマを壊す
- **出典**: Building Microservices 2nd Edition 第5章 p.141-144,148; Mastering API Architecture 第1章 p.16-17

### 10. 構造的破壊的変更とセマンティック(意味論的)破壊的変更を区別し、後者をコンシューマ駆動契約テスト(CDC)で検知する体制があるか
- **なぜ重要か**: スキーマ上は互換でも振る舞いが変わる変更は構造チェックだけでは検知できない
- **出典**: Building Microservices 2nd Edition 第5章 p.142-143,148、第9章 p.292-295; Mastering API Architecture 第2章 p.34-40

### 11. Tolerant Reader(Postelの法則)としてコンシューマを実装し、送信は保守的に・受信は寛容に、不要なフィールド変化で壊れない設計になっているか
- **なぜ重要か**: 過剰な検証は他システムの変更のたびに不要な結合を生む
- **出典**: Building Microservices 2nd Edition 第5章 p.145-146; Architecture Patterns with Python 付録E p.257-258; Building Evolutionary Architectures 2nd Edition 第7章 p.148-149

### 12. 破壊的変更が避けられない場合、新旧インターフェースの共存または旧インターフェースのエミュレーションという明確な方針を選び、ロックステップデプロイ(全サービス同時デプロイ)を避けているか
- **なぜ重要か**: ロックステップデプロイは独立デプロイ可能性を破壊し、複数チームの同時停止を強いる
- **出典**: Building Microservices 2nd Edition 第5章 p.149-152

### 13. 契約には必要最小限の情報のみを含めているか(「念のため全部含める」契約=Stamp Couplingを避けているか)
- **なぜ重要か**: 過剰な情報を含む契約は不要な結合を生み、変更のたびに広範囲に影響する
- **出典**: Building Evolutionary Architectures 2nd Edition 第5章 p.106; Software Architecture: The Hard Parts 第13章 p.365-379

### 14. バージョニング方式(path/query/header/payload)を1つに統一しているか
- **なぜ重要か**: 複数方式の併用はキャッシュ戦略や優先順位づけを複雑化させる
- **出典**: Learning API Styles 第2章 p.48-49

### 15. バージョニングそのものを本当に避けられないか検討し、採用する場合も同時サポートバージョン数を2つ程度に制限しているか
- **なぜ重要か**: Fielding自身が「バージョニングはデプロイ済みアプリケーションを殺す丁寧な方法」と述べており、バージョン数の増加はテスト・運用負荷を指数的に増大させる
- **出典**: Learning API Styles 第2章 p.48; Building Evolutionary Architectures 2nd Edition 第7章 p.171-172

### 16. メジャー/マイナーバージョンの区切りを、開発コストではなく「顧客への破壊的影響」の有無で定義しているか(Deconstructed Versioning)
- **なぜ重要か**: 開発視点の区切りは顧客が実際に受ける影響と一致しないことが多い
- **出典**: Semantic Software Design 第7章 p.148-149

### 17. 共有サービスのバージョニング戦略をREST経由のみを前提に設計せず、gRPC/メッセージング経由のアクセスも考慮しているか
- **なぜ重要か**: RESTのみを想定したバージョニング設計は、異なるプロトコルで同じサービスにアクセスするコンシューマへの互換性を見落とす
- **出典**: Software Architecture: The Hard Parts 第8章 p.230

### 18. スキーマレジストリとデータコントラクトを使い、破壊的スキーマ変更時に「新スキーマ設計→既存コンシューマ合意→移行計画→実行」の手順を踏んでいるか
- **なぜ重要か**: 無計画な変更は下流コンシューマを壊す
- **出典**: Building Event-Driven Microservices 2nd Edition 第4章 p.87-90

### 19. protobuf等のメッセージスキーマの進化ルール(フィールド追加は非破壊、削除はdeprecated化+番号reserved)を明文化し、後方互換性だけでなく前方互換性(新旧producer/consumer混在)も考慮しているか
- **なぜ重要か**: ルール違反は互換性破壊を招き、メッセージング系では複数バージョンが同時稼働しうる
- **出典**: Learning API Styles 第8章 p.247、第2章 p.47

### 20. Deprecation(非推奨化)とRetirement(廃止)を区別し、Sunset/Deprecationヘッダー(RFC8594)等で明示しているか
- **なぜ重要か**: 曖昧な廃止プロセスは誰も使われなくなったのに残り続ける「Zombie API」を生む
- **出典**: Learning API Styles 第1章

### 21. クライアントの特性(モバイル/Web/サードパーティ)ごとにBFF(Backend for Frontend)を分離しているか(「one experience, one BFF」)
- **なぜ重要か**: 単一APIで多様なクライアントの要求を満たそうとすると、どのクライアントにも最適化されない汎用APIになる
- **出典**: Building Microservices 2nd Edition 第14章 p.475-483

### 22. サービス間呼び出しで認可判定を1箇所に集中させず、confused deputy problemを認識してダウンストリームサービス自身に権限委譲しているか
- **なぜ重要か**: 中継者が代理で過大な権限を行使してしまう構造的な脆弱性を避けるため
- **出典**: Building Microservices 2nd Edition 第11章 p.380-382

### 23. OAuth2のスコープ(クライアントに許可された操作)とエンドユーザーの実際の権限を別物として両方検証しているか、またAPIキーによる認証とユーザー認証を混同し、第三者システムのAPIキーだけでエンドユーザーの代理権限を主張させていないか
- **なぜ重要か**: スコープを持つクライアントでも代理するユーザー自身がその権限を持たない場合があり、APIキーとユーザー認証の混同はエンドユーザーの代理権限の不当な主張を許してしまう
- **出典**: Mastering API Architecture 第7章 p.171, p.185-186

### 24. JWTのクレームに機密情報を含めていないか(JWSは署名のみで内容は可読であり、秘匿が必要ならJWEを使う)、またIDトークンをアクセストークンの代わりに使っていないか
- **なぜ重要か**: JWSのクレームは誰でも復号なしに読めるため機密情報の格納は漏洩に直結し、IDトークンはクライアント向けの身元情報でリソースアクセスの認可には使えない
- **出典**: Mastering API Architecture 第7章 p.174-175, p.187

### 25. マスアサインメント脆弱性(クライアント入力をDBエンティティに無検証でバインドすること)への対策として、APIゲートウェイでは防げず実装側で更新可能フィールドの明示的な許可リストを用意しているか
- **なぜ重要か**: 入力検証をAPIゲートウェイで行っても、ORMのActive Recordパターン等によるマスアサインメントはAPI実装自体で明示的に対処する必要があり、ゲートウェイ任せでは防げない
- **出典**: Mastering API Architecture 第6章 p.155-156

### 26. 外部連携用の公開インターフェース(Open-host Service)を汎用化・標準化し、個別チーム固有の要求は使い捨てのアダプタで吸収しているか
- **なぜ重要か**: 個別最適化の積み重ねはプロトコル保守を破綻させる
- **出典**: DDD Reference IV章 Open-host Service p.35

### 27. 公開言語(Published Language)を文書化し、内部モデルをそのまま外部に漏洩させていないか
- **なぜ重要か**: 内部モデルの直接露出は進化を止める
- **出典**: DDD Reference IV章 Published Language p.36

### 28. 下流として他システムに依存する場合、腐敗防止層(Anticorruption Layer)を設け、上流モデルの語彙をそのまま取り込まず自モデルの語彙に変換しているか
- **なぜ重要か**: 上流モデルの侵食がじわじわ自モデルを歪めるため
- **出典**: DDD Reference IV章 Anticorruption Layer p.34

### 29. GraphQL採用時、Introspection乱用・過大/再帰クエリ・バッチ攻撃への対策(深さ制限・allowlist・バッチ数上限)を講じ、単一エンドポイント構造ゆえのキャッシュ・レート制限の困難性に代替策を用意しているか
- **なぜ重要か**: GraphQL固有の攻撃面と運用制約は標準的なHTTPキャッシュ/エンドポイント単位レート制限では対応できない
- **出典**: Learning API Styles 第6章 p.216-218, 224

### 30. gRPC採用時、reflection機能を本番環境で無効化しているか
- **なぜ重要か**: サービス/メソッド/メッセージ型を列挙できてしまい攻撃の足がかりになる
- **出典**: Learning API Styles 第8章 p.277

### 31. Webhook配信の署名検証(HMAC)・タイムスタンプ検証(リプレイ対策)・ペイロードサイズ制限を実装しているか
- **なぜ重要か**: Webhookは改竄・リプレイ・DoSのリスクを負いやすい配信形態であるため
- **出典**: Learning API Styles 第9章 p.291-293

### 32. WebSocketのOrigin検証・Trusted Host検証を実装しているか
- **なぜ重要か**: ハンドシェイク後は全メッセージが信頼される設計が一般的だが、Originヘッダーは悪意あるクライアントに偽装されうるという弱点がある
- **出典**: Learning API Styles 第10章 p.321-332

### 33. 内部データ表現(ストレージ/インメモリ)と外部公開APIを明確に分離しているか
- **なぜ重要か**: 片方の変更がもう片方の破壊的変更に直結しないようにするため
- **出典**: Designing Distributed Systems 2nd Edition 第16章 p.182; Software Architecture: The Hard Parts 第6章 p.136-138

### 34. サイドカー/アダプタ等のコンテナ間APIのパラメータ名・単位(秒⇔文字列表記等)の変更を、気づかれにくい破壊的変更として慎重に管理しているか
- **なぜ重要か**: パラメータの型・単位変更はエラーを出さずに動作を変えてしまうことがある
- **出典**: Designing Distributed Systems 2nd Edition 第3章 p.28-29

### 35. 公開APIに最初からバージョン(v1など)を付与し、SLO(レイテンシ・信頼性・スループット)をクライアントとの契約として明文化しているか
- **なぜ重要か**: 後からのバージョニング追加は極めてコストが高く、SLOはクライアント側の期待値形成の基盤になる
- **出典**: Designing Distributed Systems 2nd Edition 第11章 p.121、第2章 p.9-10

### 36. 外部向けエラーレスポンスでスタックトレースや内部実装詳細を漏らさず、内部デバッグ情報を別構造(InnerErrorパターン)に分離しているか
- **なぜ重要か**: 実装詳細の露出は攻撃面になるため
- **出典**: Mastering API Architecture 第1章 p.11

### 37. エラーレスポンスに標準化されたエラーコードと人間が読めるメッセージの両方を含めているか
- **なぜ重要か**: 標準コード+人間可読メッセージは利用者側のデバッグを助ける
- **出典**: Learning API Styles 第2章 p.73-74

### 38. PIIなどの機微情報をAPIのURL/パスに含めていないか
- **なぜ重要か**: ログやキャッシュ、アクセスログに残存し漏洩リスクを生むため
- **出典**: Mastering API Architecture 第1章 p.9

### 39. OWASP API Security Top 10の3分類(認証/認可、インベントリ管理、リソース管理)でAPIをレビューしているか
- **なぜ重要か**: API特有の脅威はWebセキュリティ一般と観点が異なるため、API専用の分類でのレビューが必要
- **出典**: Learning API Styles 第2章 p.69

### 40. 出力データにも最小権限の原則を適用し、入力検証だけでなく過剰なデータ露出(excessive data exposure)を防いでいるか
- **なぜ重要か**: 入力だけでなく出力側の検査も必要であり、不要なフィールドの露出は情報漏洩につながる
- **出典**: Learning API Styles 第2章 p.73

### 41. レート制限が単一クライアントのDoSにしか効かずDDoSには不十分であると認識しているか
- **なぜ重要か**: 脅威モデルの誤解を避け、DDoS対策には別の手段(CDN/専用防御層等)が必要であることを認識するため
- **出典**: Learning API Styles 第2章 p.65

### 42. ページネーション設計として、カーソルベースページネーションの採用を検討し、オフセットベースの欠点(大規模・動的データでの破綻)を許容できるか評価したか
- **なぜ重要か**: 大規模・動的データでoffsetベースのページネーションは破綻しやすい
- **出典**: Learning API Styles 第2章 p.59-61

### 43. コレクション応答を配列直返しでなく `@nextLink` 等でラップし、将来のページネーション追加に備えているか
- **なぜ重要か**: 配列を直接返す設計は後からページネーションを追加する際に破壊的変更となる
- **出典**: Mastering API Architecture 第1章 p.10
