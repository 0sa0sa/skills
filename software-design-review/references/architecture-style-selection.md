# アーキテクチャスタイル選定

モノリス/マイクロサービス/イベント駆動/ヘキサゴナル等のアーキテクチャスタイル選定とその根拠を見る。

## チェックリスト

### 1. モノリスを「分別ある既定の選択肢」として先に検討し、マイクロサービス化が消極的な「選ばない理由」でなく積極的な理由(独立デプロイ可能性の必要性等)に基づいているか確認しているか。モノリス自体を「ビッグボールオブマッド」と同一視していないか。
- **なぜ重要か**: マイクロサービスは目的でなく独立デプロイ可能性というゴールのための選択肢の一つであり、流行追従での安易な選定は失敗を招く。モノリスが悪いのではなく内部設計(凝集度・DDD)の問題であることが多い。
- **出典**: Building Microservices 2nd Ed 第1章 p.18; Mastering API Architecture 第8章 p.195-197

### 2. 独立デプロイ可能性(independent deployability)をアーキテクチャ選定の最優先指標に据えているか。
- **なぜ重要か**: 著者が「本書から一つだけ持ち帰るなら」と明言する核心概念であり、これを欠くとマイクロサービス化の利点の大半が失われる。
- **出典**: Building Microservices 2nd Ed 第1章 p.6

### 3. ドメインモデルが安定する前に、新規プロダクトやスタートアップで尚早にマイクロサービス化していないか。
- **なぜ重要か**: ドメインが固まっていない段階での分割は境界設定を誤りやすく、手戻りコストを増大させる。DDD/依存性逆転などの設計技法自体はマイクロサービス前提ではない。
- **出典**: Building Microservices 2nd Ed 第1章 p.31-32; Architecture Patterns with Python エピローグ p.225

### 4. 顧客環境にデプロイ・運用されるソフトウェア(オンプレ配布製品等)にマイクロサービスを採用していないか。
- **なぜ重要か**: 分散システムの運用複雑性(サービスディスカバリ・モニタリング・オーケストレーション等)を顧客環境に押し付けることになり、自社運用のSaaS/クラウドサービスとは前提が異なる。
- **出典**: Building Microservices 2nd Ed 第1章 p.32

### 5. コスト削減を主目的にマイクロサービス化/分散化を選んでいないか。
- **なぜ重要か**: マイクロサービス化は短期的にはむしろ運用・通信コストを増やすことが多く、収益拡大など別の目的の方が適合しやすい。
- **出典**: Building Microservices 2nd Ed 第1章 p.28

### 6. 「マイクロサービスを持つこと」自体が目的化しておらず、組織固有の制約・トレードオフ(デリバリー競合の解消等)に基づいて選んでいるか。
- **なぜ重要か**: 明確なゴールなしの採用はコストだけを増やす。組織がマイクロサービスを採用する実質的な最大の理由は、チーム間のデリバリー競合の解消であることが多い。
- **出典**: Building Microservices 2nd Ed 第3章 p.71; 第1章 p.17-18, 33

### 7. 流行への同調(バンドワゴン)や、Netflix/Spotifyなど他社の成功事例の盲目的な移植になっていないか。ベストプラクティスが成立する前提条件は組織ごとに異なることを踏まえているか。
- **なぜ重要か**: 「Netflix/Spotifyで機能したものが自社で機能する保証はない」という警告が複数書籍で一致して示されており、技術選定の前提条件(規模・成熟度・技術進化段階)は組織ごとに異なる。
- **出典**: Software Architecture: The Hard Parts 第1章 p.1-3; Learning Systems Thinking p.150, p.163

### 8. 対立する2チーム・部門の要求を機械的に足し合わせた「妥協案」(著者の言う"carboat": 車が欲しいチームと船が欲しいチームの妥協で誰も使わない成果物ができるという比喩)になっていないか。
- **なぜ重要か**: バンドワゴンや他社事例の盲目移植とは異なる、組織内の意思決定プロセスに起因する独立した失敗パターンであり、要求を足し合わせただけのアーキテクチャは誰の要求も満たさない。
- **出典**: Learning Systems Thinking p.150, p.164, p.193-194

### 9. 移行を一気に全面分割(ビッグバン)せず、段階的(ダイヤルを回すように/Strangler Fig)に進めているか。
- **なぜ重要か**: 一括リライトは高リスクであり、段階的移行の方が安全であることが複数書籍で一致して推奨されている。
- **出典**: Building Microservices 2nd Ed 第1章 p.13,27、第3章 p.71-72; Architecture Patterns with Python エピローグ p.218-220; Mastering API Architecture 第8章 p.203-205

### 10. マイクロサービス化(分割)より簡単な代替策(モノリスの垂直/水平スケール等)を先に検討したか。
- **なぜ重要か**: 分割は不可逆性の高い決定であり、より単純にスケールやパフォーマンス要件を満たせる手段があるなら、それを先に試す方がリスクが低い。
- **出典**: Building Microservices 2nd Ed 第3章 p.71-72

### 11. マイクロサービスへ一気に飛躍する前に、サービスベースアーキテクチャのような「踏み台」を検討したか。
- **なぜ重要か**: DB分割を伴わず組織変更コストを抑えて段階的に移行できる中間選択肢になる。
- **出典**: Software Architecture: The Hard Parts 第4章 p.71-72, 第5章 p.126-130

### 12. 最初の分割対象は「容易な部分」から選び早期の成功体験を積む計画になっており、モノリスを敵視せず必要な部分だけ残して新サービスと共存させる設計を許容しているか。
- **なぜ重要か**: 完璧主義や全面分割志向は挫折を招きやすく、小さく始める方が現実的に成功しやすい。
- **出典**: Building Microservices 2nd Ed 第3章 p.73,75

### 13. 分割する前提のもとで、「マイクロサービスは可能な限り小さく」という思い込みを捨て、境界づけられたコンテキストやサービス粒度の客観的ドライバー(凝集度・ボラティリティ・スケーラビリティ・耐障害性・セキュリティ・拡張性等)に沿って各サービスの大きさを決めているか。
- **なぜ重要か**: 過度な分割はオーケストレーションと通信オーバーヘッド(microservice tax)を増大させるだけで、粒度判断を主観的な議論に委ねると対立が解決しない。
- **出典**: Building Event-Driven Microservices 2nd Ed 第3章 p.61, 第22章 p.443; Software Architecture: The Hard Parts 第7章 p.187-197; Building Evolutionary Architectures 2nd Ed 第7章 p.161

### 14. マイクロサービス化がチーム規模に見合っているか(エンジニア数よりサービス数が多いなど過剰分割のサインがないか)を検討しているか。
- **なぜ重要か**: 過剰な分割はネットワークオーバーヘッドとコストを積み上げるだけで、チームが把握できる規模を超えると認知負荷が増す。
- **出典**: Designing Distributed Systems 2nd Ed Part III冒頭 p.70

### 15. サービス間の協調方式として、オーケストレーション型とコレオグラフィー型を、ワークフローの複雑さ・変更頻度・チーム境界に基づき意識的に選んでいるか。
- **なぜ重要か**: コレオグラフィは疎結合だが可視性に劣り、オーケストレーションは可視性に優るが密結合を生むため、無自覚な選択は後戻りが困難になる。
- **出典**: Building Event-Driven Microservices 2nd Ed 第10章 p.222-230; Building Microservices 2nd Ed 第6章 p.189-194

### 16. 分散トランザクション(サガ)が本当に必要か、回避できないかを検討しているか。特に同期通信+アトミック整合性+コレオグラフィの組み合わせ("Horror Story Saga")のような最悪の組み合わせを避けているか。
- **なぜ重要か**: サガは複雑でリスクが高く、避けられるなら避けるべきと明記されている。特定の組み合わせは全参加者がブロッキング待ちし合う最悪のパターンになる。
- **出典**: Building Event-Driven Microservices 2nd Ed 第10章 p.231; Software Architecture: The Hard Parts 第12章 p.343-346; Building Microservices 2nd Ed 第6章 p.179-181

### 17. そもそも分解に着手する価値があるかを、コードベースの求心性/遠心性結合・不安定度・主系列からの距離等の定量指標で評価し、分解の労力が報われるか("zone of pain"等に陥っていないか)を判断しているか。
- **なぜ重要か**: 抽象的な「疎結合が正義」論ではなく定量評価がないと、分解コストが利益を上回るケースを見逃す。
- **出典**: Software Architecture: The Hard Parts 第4章 p.66-70

### 18. 高結合で基本構造がないコードベースの分解に際し、段階的なコンポーネントベース分解と、即着手できるが重複コードを招くTactical Forkingのどちらが適切かをトレードオフ評価したか。
- **なぜ重要か**: 両者は時間軸と技術的負債のトレードオフが異なり、状況に応じた選択が必要になる。
- **出典**: Software Architecture: The Hard Parts 第4章 p.73-79

### 19. スケーラビリティ・弾力性・保守性・テスト容易性・デプロイ容易性などモジュール性ドライバーごとに具体的なトレードオフ表で比較しているか(サービス分割が必ずテスト/デプロイ容易性を改善するわけではない逆説を認識しているか)。
- **なぜ重要か**: サービス間通信の増加によりテスト・デプロイ容易性がむしろ悪化しうるため、抽象的な「疎結合が正義」論は危険。
- **出典**: Software Architecture: The Hard Parts 第3章 p.49-58

### 20. 要求されるスケール軸(リクエスト数/データサイズ/処理時間のどれを増やしたいか)に応じて、レプリケーション/シャーディング/scatter-gatherのいずれを選ぶべきか切り分けているか。
- **なぜ重要か**: パターンごとに最適化対象が異なり、誤った選択は性能問題を生む。
- **出典**: Designing Distributed Systems 2nd Ed 第6〜8章

### 21. 単一レプリカ(シングルトン)で許容できる可用性要件かを、分散ロックを導入する前にまず検討しているか。
- **なぜ重要か**: 不要な複雑性(分散ロック)を避けるため、まず簡単な選択肢を検討すべき。
- **出典**: Designing Distributed Systems 2nd Ed 第10章 p.104-106

### 22. 通信方式を決める前に、まず「同期/非同期」というコミュニケーションスタイルをユースケースごとに判断しているか(ハイブリッドが常態であることを前提にしているか)。
- **なぜ重要か**: 誤った選択はUXやレイテンシ蓄積の問題を招く。多くの実システムは純粋なイベント駆動/同期どちらか一方ではなく、ハイブリッドが常態である。
- **出典**: Building Microservices 2nd Ed 第4章 p.93-95; Learning API Styles 第11章 p.371-372; Building Event-Driven Microservices 2nd Ed 第1章 p.20, 第17章 p.333

### 23. 東西(サービス間)/南北(外部)通信を区別し、それぞれに適した通信方式を選んでいるか。
- **なぜ重要か**: east-westは自社管理下で性能最適化でき(高頻度・大ペイロードに強いgRPC等)、north-southは制御できない外部消費者向けの互換性重視(REST等)が適する。
- **出典**: Mastering API Architecture 第1章 p.20-22; Learning API Styles 第5章 p.195

### 24. REST/gRPC/GraphQL/イベント駆動といったAPIスタイルを「どちらが優れているか」でなく用途(リソースモデル中心か、性能最優先か、複数サービス集約とクライアント主導フィールド選択か等)で選んでいるか。
- **なぜ重要か**: 各方式は異なる課題解決のために生まれており、一方的な優劣論は誤った選択を招く。
- **出典**: Mastering API Architecture 第1章 p.7-8; Learning API Styles 第1章 表1-1 p.18

### 25. モノリシック/マイクロサービス/マイクロフロントエンドといったバックエンド集約(アグリゲーション)パターンの選定を、チーム境界に応じて比較しているか。集約層にビジネスロジックが漏れ込む「共有地の悲劇」に陥っていないか。
- **なぜ重要か**: 集約層は複数チームが共有するため責務が曖昧になりやすく、放置するとビジネスロジックが無秩序に漏れ込む。
- **出典**: Building Event-Driven Microservices 2nd Ed 第17章 p.357-358

### 26. APIゲートウェイ/サービスメッシュ等の導入前に、各コンポーネントの機能差・性能トレードオフ(サイドカーの通信オーバーヘッド、データプレーン実装方式〈サイドカー/ライブラリ/eBPF〉ごとの性能・運用トレードオフ等)を理解した上で導入規模を決めているか(過剰機能の早期導入を避けているか)。
- **なぜ重要か**: 過剰な機能を持つコンポーネントを早期導入するとコストと複雑性が増し、性能とエネルギー効率にも影響する。
- **出典**: Mastering API Architecture 第3章 Table3-2, 第4章 Table4-1, Table4-4 p.111; Building Green Software 第3章 p.42-43

### 27. 重量級ストリーミング/分散処理フレームワーク導入前に、専用クラスタ運用のオーバーヘッドに見合うか評価しているか。
- **なぜ重要か**: 独自クラスタ管理が必要になり複雑性が増すため、軽量な代替手段との比較が必要。
- **出典**: Building Event-Driven Microservices 2nd Ed 第12章 p.262-265

### 28. ベンダー製品/ERPをアーキテクチャの中心(Vendor King)に据えず、単なる統合ポイントとして扱っているか。
- **なぜ重要か**: Vendor King化すると技術・業務プロセス両面で柔軟性を失う。
- **出典**: Building Evolutionary Architectures 2nd Ed 第8章 p.179-181

### 29. MVP用途のアーキテクチャには意図的にSacrificial Architecture(捨てる前提の設計)を採用し、本番規模への移行計画を持っているか。
- **なぜ重要か**: 初期の犠牲アーキテクチャが市場投入速度を担保する一方、移行計画なしでは技術的負債化する。
- **出典**: Building Evolutionary Architectures 2nd Ed 第7章 p.167-169

### 30. 低コード/ノーコードツールの選定時、最も簡単なユースケースでなく最も難しいユースケースを先に評価しているか。
- **なぜ重要か**: Last 10% Trap(最後の10%が実現不能)を早期発見できる。
- **出典**: Building Evolutionary Architectures 2nd Ed 第8章 p.177-178

### 31. アーキテクチャ選定時、ドメイン要求とアーキテクチャ特性(-ilities)を明示的に切り分けて定義しているか。
- **なぜ重要か**: 両者がアーキテクチャの全スコープを構成し、混同すると要求の見落としや過剰設計を招く。
- **出典**: Building Evolutionary Architectures 2nd Ed 第1章 p.3-4

### 32. その決定がOne-way door(やり直し困難)かTwo-way door(変更容易)かを事前に見極め、One-way doorの場合はより慎重な検討をしているか。
- **なぜ重要か**: アーキテクチャ能力は有限資源であり、やり直しコストの高い決定に重点的にリソースを配分すべき。
- **出典**: Fundamentals of Enterprise Architecture 第6章 p.139-140

### 33. 常時起動のモノリスでなく、低優先度・遅延可能タスクを認識できるサーバーレス/非同期/マイクロサービス型アーキテクチャを選び、需要シフト/シェイピングを組み込める設計にしているか。
- **なぜ重要か**: 高いマシン利用率とカーボンアウェアネスを両立しやすく、将来のカーボンアウェア化にも必須の前提となる。
- **出典**: Building Green Software 第1章 p.9-10, 第4章 p.69-71, 第5章 p.80-81

### 34. ドメインの複雑さに見合わないのに、単純なCRUDアプリにリポジトリ/Unit of Workなどの抽象化(ヘキサゴナルアーキテクチャ等)を導入していないか。
- **なぜ重要か**: 複雑さに比例しない抽象化導入は、学習・保守コストだけを増やす過剰設計(オーバーエンジニアリング)になる。「アーキテクチャスタイル選定」の核心は複雑さに見合った選択をすることにある。
- **出典**: Architecture Patterns with Python 第2章 p.38-39

### 35. データソースの特性(スキーマ変動・配信パターン・リアルタイム要否)に応じてバッチ/Structured Streaming/CDC/ミラーリングを使い分けているか。
- **なぜ重要か**: 「データ統合に銀の弾丸はない」ため、ソースごとの個別対応が必要になる。
- **出典**: Building Medallion Architectures 第2章 p.38-42, 第5章 p.123

### 36. データウェアハウス(Inmon/Kimball)・データレイク・レイクハウスそれぞれの歴史的経緯・長所と限界を理解した上でレイクハウス/メダリオンを選択しているか。
- **なぜ重要か**: 各アーキテクチャは特定の課題を解決するために生まれた経緯があり、歴史を知らずに選ぶと既知の失敗を繰り返す。
- **出典**: Building Medallion Architectures 第1章 p.7-30

### 37. 各ドメイン/プラットフォームインスタンスに同一の技術スタックを強制せず、要件に応じて複数の選択肢(レイクハウス/ウェアハウス等)を残しているか。
- **なぜ重要か**: 画一的な技術スタック強制は要件とのミスマッチを生む。実企業の事例でも要件次第で別技術を検討する余地が残されている。
- **出典**: Building Medallion Architectures 第8章 p.247-248, 第10章 p.287

### 38. デプロイモデル(サイロ/プール/ハイブリッド等)の選定を技術的な「とりあえず」でなく、コンプライアンス・コスト等の業務要因から逆算して決めているか。
- **なぜ重要か**: 「ワンサイズフィットオール」は存在せず、業務要因を無視した技術選定はビジネス要件とのズレを生む。
- **出典**: Building Multi-Tenant SaaS Architectures 第3章 p.50-51

### 39. マルチテナント環境の実装スタックとして、コンテナ(EKS等)とサーバーレスのどちらが必要な分離粒度・コスト効率に合うか比較評価しているか。
- **なぜ重要か**: 両者は同じゴール(テナント分離)への異なる経路であり、優劣は一概に決まらない。
- **出典**: Building Multi-Tenant SaaS Architectures 第10章 p.275, 第11章 p.277-281

### 40. 「マイクロサービス」と呼ぶ各サービスが本当に専用のデータストア(Database per Service)を持っており、他サービスのテーブルへ直接アクセスしていないか。
- **なぜ重要か**: 複数サービスが同一DBを共有すると、見た目は別サービスでも実質1つのアーキテクチャクアンタムに収束し、独立デプロイ可能性(#2)が失われる。DBスキーマの共有は境界づけられたコンテキストの侵食にも直結する。
- **出典**: Building Microservices 2nd Ed 第1章 p.8-9; Software Architecture: The Hard Parts 第2章 p.31-37
