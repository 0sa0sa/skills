# ツール利用・コード実行・MCP

関数呼び出し/ツール定義、コード実行のサンドボックス化、MCPの設計など、エージェントが外部とやり取りする手段の実装を見る。

## チェックリスト

### 1. ツール内で発生したエラーを文字列や曖昧な戻り値ではなく例外として送出し、オーケストレーション層がそれを検知して分岐処理(リトライ/フォールバック等)できる設計になっているか
- **なぜ重要か**: エラーを通常の戻り値と同じ形で返すと、呼び出し側(エージェントやLLM)がそれを正常な結果と誤認し、誤った処理を継続してしまう。例外として送出することで制御フローが明確になり、検知→ハンドリングの仕組みに確実に乗せられる。
- **出典**: Agentic Design Patterns 第5章 Tool Use

### 2. ツールのdescriptionおよびパラメータ定義に、(a)必須/任意パラメータの区別、(b)型・値の制約(enumや範囲等)、(c)代表的な入力例、(d)想定されるエラー条件、の4点が明記されており、LLMがそれを読むだけで正しい引数を構成できる具体性になっているか
- **なぜ重要か**: ツール定義が曖昧だとLLMが誤った引数・誤ったツールを選択しやすくなり、呼び出し失敗や意図しない実行につながる。『曖昧でない』という主観的な基準だけではレビュアーごとに判定がぶれるため、必須/任意・型制約・例・エラー条件という具体的な確認観点に分解することで判定基準を一定にできる。
- **出典**: Agentic Design Patterns 第5章 Tool Use

### 3. LLMに与えるツールの数は3〜10個程度の目安に絞られているか(ツールを無制限に増やしていないか)
- **なぜ重要か**: ツール数が多すぎるとLLMがどのツールを使うべきか判断を誤りやすくなり、呼び出し精度が低下する。業界的な目安として3〜10個程度への絞り込みが推奨されている。
- **出典**: 生成AIデザインパターン 7章 P21

### 4. LLMはツール呼び出しのためのトークンを生成するだけで、実際の実行はクライアント/アプリケーション側のコードが担う構造になっているか(LLM自身に実行権限を持たせていないか)
- **なぜ重要か**: LLMがツールを直接実行する構造にすると、権限管理や検証を挟む余地がなくなり危険な操作がそのまま実行されてしまう。生成と実行を分離することで検証・承認ステップを挿入できる。
- **出典**: 生成AIデザインパターン 7章 P21 / Agentic Design Patterns 第5章 Tool Use

### 5. 精密計算やLLMが生成したコードの実行は、ホスト環境で直接実行せずサンドボックス化された実行環境で行っているか
- **なぜ重要か**: LLM生成コードは信頼できない入力として扱う必要があり、ホスト環境で直接実行すると任意コード実行やシステム破壊のリスクがある。サンドボックス化で被害範囲を限定できる。
- **出典**: Agentic Design Patterns 第5章 Tool Use / 生成AIデザインパターン 7章 P22

### 6. 生成されたコードは実行前に構文チェック・静的解析を通しているか
- **なぜ重要か**: 構文エラーや危険な呼び出しパターンを実行前に検出できれば、サンドボックス内であっても不要な実行コストや予期しない副作用を減らせる。
- **出典**: 生成AIデザインパターン 7章 P22

### 7. サンドボックスの基盤となるOS/コンテナランタイムについて、既知脆弱性の定期スキャンとベースイメージの更新プロセスが運用として存在し、サンドボックス導入自体をセキュリティ対策の終着点にしていないか
- **なぜ重要か**: サンドボックスは万能ではなく、基盤となるOSやコンテナランタイムに脆弱性があればエスケープされホストに影響が及ぶ。『考慮しているか』という意識レベルでなく、脆弱性スキャンの運用やベースイメージ更新プロセスの有無という具体的な運用実態で確認する。
- **出典**: 生成AIデザインパターン 7章 P22

### 8. LLMが生成したコードを実際に実行・テストする工程が組み込まれているか(生成しただけで検証せずに終わっていないか)
- **なぜ重要か**: コード生成は構文的に正しくても意図通りに動く保証がなく、実行・テストの工程を経なければ欠陥のあるコードがそのまま採用されるリスクがある。
- **出典**: Agentic Design Patterns 第11章 Goal Setting and Monitoring

### 9. 副作用のあるツール実行(書き込み・送信・決済等)について、実行者が誰か・どの権限で実行されるかが明確に設計されているか
- **なぜ重要か**: 副作用を持つ操作の実行者・権限が曖昧だと、意図しないユーザーの操作権限でアクションが実行される、あるいは誰の責任で実行されたか追跡できなくなる。
- **出典**: Agentic Design Patterns 第5章 Tool Use

### 10. ツール呼び出しやコード実行に付与される権限が最小権限の原則に従い、被害範囲(blast radius)を限定する設計になっているか(過剰な権限を持つ汎用クレデンシャルを使っていないか)
- **なぜ重要か**: 権限範囲が広すぎると、ツールの誤動作やプロンプトインジェクション等により想定外の操作まで実行されてしまう。権限スコープを必要最小限に絞ることで、何か問題が起きた際の被害範囲を限定できる。
- **出典**: Agentic Design Patterns 第18章 Guardrails/Safety Patterns

### 11. ツール呼び出しの引数に含まれるユーザーID等を現在のセッション状態と突き合わせ、なりすまし・ハイジャックを防いでいるか
- **なぜ重要か**: LLMが生成した引数をそのまま信用すると、攻撃的な入力によって別ユーザーのIDを引数に含めるなどのなりすましが成立しうる。セッション状態との整合性チェックが必要。
- **出典**: Agentic Design Patterns 第18章 Guardrails/Safety Patterns

### 12. ユーザーIDの突き合わせに限らず、ツール呼び出しの引数(パラメータ値)全般に対する妥当性検証(型・範囲・許可リスト等)が、入力・出力・検索と並ぶガードレールの対象として実装されているか
- **なぜ重要か**: LLMが生成した引数をそのまま信用すると、ユーザーIDのなりすまし以外にも、想定外の値や攻撃的な入力がそのままツール実行に渡ってしまう。入力・出力・検索・ツール呼び出しパラメータの4箇所すべてにガードレールを置くことで、より広い範囲の不正な引数を防げる。
- **出典**: 生成AIデザインパターン 7章 P32

### 13. MCPサーバはレガシーAPIを単純ラップするだけでなく、フィルタ・ソート等の決定論的な処理を加えて提供しているか
- **なぜ重要か**: 単純なAPIラップだけではLLM側に余計な後処理負担を強いることになり、誤動作や無駄なトークン消費を招く。決定論的な前処理をサーバ側に持たせることで信頼性が上がる。
- **出典**: Agentic Design Patterns 第10章 MCP

### 14. MCPサーバが返すデータは、エージェント(LLM)が解釈しやすい形式(Markdown等)になっているか検証したか
- **なぜ重要か**: 生のJSONやバイナリなど機械向けの形式のままではLLMが正しく解釈できず、誤った応答や幻覚を招きやすい。LLMが読みやすい形式への変換がMCP設計の要となる。
- **出典**: Agentic Design Patterns 第10章 MCP

### 15. MCPのクライアント・サーバ間の認証・認可(必要に応じたロール分離)を明示的に実装しているか
- **なぜ重要か**: 認証・認可が暗黙的・未実装だと、権限のないクライアントが機密データやツールにアクセスできてしまう。MCP特有の接続形態では明示的な認証設計が欠かせない。
- **出典**: Agentic Design Patterns 第10章 MCP / 生成AIデザインパターン 7章 P21

### 16. ツールの失敗・MCPサーバの利用不可・不正リクエストを、LLMが理解できる形式のエラーとして返却しているか
- **なぜ重要か**: エラーが生のスタックトレースやHTTPステータスのままだと、LLMがそれを正しく解釈できず、適切なリトライやユーザーへの説明ができない。LLMが理解できる言語化されたエラー返却が必要。
- **出典**: Agentic Design Patterns 第10章 MCP

### 17. MCPサーバ呼び出し等、30〜60秒規模の遅延が想定されるツール呼び出しについて、ストリーミングや非同期通知によりTTFT(最初の応答までの時間)を改善する設計になっているか
- **なぜ重要か**: MCP経由のツール呼び出しは同期的に長時間ブロックしやすく、何も返らないまま待たされるとユーザー体験が大きく損なわれる。ストリーミングや進捗通知を挟むことで、処理中であることをすぐに伝えられる。
- **出典**: 生成AIデザインパターン 7章 P21

### 18. ツール呼び出し失敗時のリトライ回数が、想定される拒否率や許容できる遅延(ユーザーが待てる時間)といった具体的根拠に基づいて設定されているか(当てずっぽうの固定回数になっていないか)
- **なぜ重要か**: 成功率が低い状態でリトライ回数だけを増やすとp99遅延が指数的に悪化する。拒否率と遅延許容範囲という定量的根拠に基づいてリトライ回数を設計することで、過剰に待たせたり逆に早すぎる諦めを招くことを防げる。
- **出典**: 生成AIデザインパターン 10章

### 19. 外部コンテンツを経由したプロンプトインジェクションに対し、アクションセレクター・実行計画の固定化・Map-Reduce分離・デュアルLLM・サンドボックス化されたコード実行・コンテキスト最小化のうち、単一の対策に頼らず複数を組み合わせて多層防御しているか
- **なぜ重要か**: ツールを呼び出すエージェントは外部コンテンツ経由のプロンプトインジェクションに晒されやすく、単一の対策では突破されるリスクが残る。『どれか1つ実装していればOK』という曖昧な判定ではなく、複数技法の組み合わせを多層防御として求めることで合否基準を明確にする。
- **出典**: 生成AIデザインパターン 7章 P21

### 20. LLMが生成したコンテンツ(HTML/JS等を含み得る出力)をUIに表示する前にサニタイズし、ブラウザ側で意図しないコードが実行されるのを防いでいるか
- **なぜ重要か**: LLM生成コンテンツをそのままレンダリングすると、埋め込まれた悪意あるスクリプトがユーザーのブラウザ上で実行され、XSS等の被害につながる。表示前のサニタイズは、クライアント側で起こるコード実行リスクへの対策として欠かせない。
- **出典**: Agentic Design Patterns 第18章 Guardrails/Safety Patterns
