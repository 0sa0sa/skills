# エージェントアーキテクチャ・マルチエージェント設計

マルチエージェントのトポロジ選定、責務分離、プランニング、Reflection、メモリ管理など、エージェントそのものの構造設計を見る。

## チェックリスト

### 1. 採用したマルチエージェントトポロジ(Single/Network/Supervisor/Supervisor-as-Tool/Hierarchical/Custom)固有の弱点(Network=調整オーバーヘッド、Supervisor=単一障害点等)を認識し、緩和策を講じているか。
- **なぜ重要か**: トポロジごとに既知の構造的弱点(調整オーバーヘッドや単一障害点など)があり、選定時にそれを認識して緩和策を組み込まなければ、その弱点がそのまま運用時のシステムの弱点として残ってしまう。
- **出典**: Agentic Design Patterns 7章(Multi-Agent Collaboration) 項目24, 特徴的な知見

### 2. マルチエージェント化が本当に必要か検討し、単純な単一エージェント/固定ワークフローで足りる場合はそちらを優先しているか。
- **なぜ重要か**: 複雑なマルチエージェント構成の導入は通信・調整コストとデバッグ難度を増すため、導入前に必要性の検証を行うことが前提になる。
- **出典**: 生成AIデザインパターン 10章/P23 項目6

### 3. 採用アーキテクチャ(階層型/ピアツーピア/市場ベース等)がタスクの調整要件(どのエージェントが誰といつ連携する必要があるか)に合っているか検討したか。
- **なぜ重要か**: 構造とタスクの調整要件が不一致だと、過剰な通信オーバーヘッドや連携不足といった非効率を生む。
- **出典**: 生成AIデザインパターン 10章/P23 項目7

### 4. 各構成要素(エージェント/モジュール)を依存性注入等で疎結合にし、独立して開発・テスト・デプロイ・スケール・障害分離できる設計になっているか。
- **なぜ重要か**: 結合度の高い設計は1箇所の変更・障害がシステム全体に波及しやすく、個別のテストやスケーリングも困難になる。
- **出典**: 生成AIデザインパターン P19 項目12; 10章/P23 項目15

### 5. プランニングとツール実行の責務を同一エージェントに混在させず分離しているか。
- **なぜ重要か**: 計画立案と実行の役割が混在すると責務が不明確になり、デバッグやエージェント単体の評価が困難になる。
- **出典**: Agentic Design Patterns 7章(Multi-Agent Collaboration) 項目23

### 6. モノリシックな「何でも屋」エージェントでなく、責務ごとに専門化・分割されたエージェント/モジュール構成になっているか。
- **なぜ重要か**: 専門化により権限の最小化(最小権限の原則)、障害の影響範囲(blast radius)限定、保守性の向上が得られる。
- **出典**: Agentic Design Patterns 18章(Guardrails) 項目69

### 7. エージェント間の通信プロトコルと共有オントロジー(用語・データ形式の共通理解)を明示的に設計しているか。単に分業させるだけで効果が出ると考えていないか。
- **なぜ重要か**: 標準化された通信プロトコルと共有オントロジーがなければ分業の効果が発揮されず、エージェント間の誤解や非効率な連携を招く。
- **出典**: Agentic Design Patterns 7章(Multi-Agent Collaboration) 項目25, 特徴的な知見

### 8. カスタムエージェント(Custom Agentパターン)を実装する際、フレームワークが提供する基底クラスを正しく拡張しているか(独自実装がライフサイクル管理やイベント記録の仕組みを壊していないか)。
- **なぜ重要か**: 基底クラスの拡張を誤ると、フレームワークが前提とする状態管理・イベント記録・実行ライフサイクルと整合しなくなり、デバッグや他エージェントとの連携が困難になる。
- **出典**: Agentic Design Patterns 7章(Multi-Agent Collaboration) 項目21

### 9. エージェント間のハンドオフで自由形式の文字列でなく、スキーマ検証済みの構造化出力を使っているか(parse, don't validate)。
- **なぜ重要か**: 自由文字列によるハンドオフは受け手側での解釈ミスや壊れやすい連携を生みやすく、スキーマ検証を通すことで契約違反を早期に検出できる。
- **出典**: Agentic Design Patterns 横断項目85

### 10. マルチエージェント設計において、個別エージェントのプロンプト最適化→トポロジ最適化→全体ワークフロー調整という順序を守っているか。
- **なぜ重要か**: この順序を誤ると各段階の最適化が噛み合わず、設計不備が複合的に悪化する(MASSフレームワークの知見)。
- **出典**: Agentic Design Patterns 17章(Reasoning) 項目60, 特徴的な知見

### 11. Reflection(自己改善)において生成(Producer)と批評(Critic)を別エージェント・別ペルソナ(可能なら別モデル)に分離しているか。生成LLMと評価LLMを同一にしていないか。
- **なぜ重要か**: 同一モデル・同一エージェントによる自己評価は自分自身の誤りに気づきにくく、認知バイアスを回避できない。
- **出典**: Agentic Design Patterns 4章(Reflection)項目10・11章(Goal Setting)項目37; 生成AIデザインパターン 6章/P17,P18 項目63

### 12. リフレクション/自己評価ループおよびループ型エージェントに、明確な終了条件と最大反復回数(max_iterations)の両方を設定しているか。
- **なぜ重要か**: 終了条件のみ、または上限のみでは想定外の無限ループや早期終了が起こり得るため、両方の設定が必要になる。
- **出典**: Agentic Design Patterns 4章(Reflection)項目11・7章(Multi-Agent)項目22・11章(Goal Setting)項目38

### 13. リフレクション/自律ループの繰り返しによる会話履歴の肥大化、コンテキスト超過、レート制限リスクを評価しているか。
- **なぜ重要か**: 反復ごとに履歴が蓄積し、コンテキストウィンドウやAPIレート制限を超過してコスト・レイテンシが制御不能に増大するリスクがある。
- **出典**: Agentic Design Patterns 4章(Reflection) 項目12

### 14. やり方が既知で再現可能なタスクについては、あえて自律的プランニングを使わず固定ワークフローに制約しているか。
- **なぜ重要か**: 不要な自律性は予測不能な挙動とデバッグ困難さを増すだけでコスト対効果が悪い。
- **出典**: Agentic Design Patterns 6章(Planning) 項目18

### 15. 長時間に及ぶプラン実行を非同期・再開可能な設計にし、単一障害点(プロセスダウン等)でタスク全体の進行が失われないようにしているか。
- **なぜ重要か**: 長時間タスクが単一プロセスに依存していると、障害時にそれまでの進行がすべて失われる。
- **出典**: Agentic Design Patterns 6章(Planning) 項目19

### 16. エージェントの状態(session.state等)を直接書き換えず、output_key/EventActions.state_delta等の仕組み経由で更新しているか。
- **なぜ重要か**: 状態の直接書き換えは変更履歴(イベント)として記録されない禁止パターンであり、デバッグ・再現性・一貫性を損なう。
- **出典**: Agentic Design Patterns 8章(Memory Management) 項目26

### 17. ステートのスコープ接頭辞(user:/app:/temp:等)を正しく使い分け、短期(セッション内)記憶と長期(ユーザー/アプリ横断)記憶を混同していないか。
- **なぜ重要か**: スコープの混同はセッション間でのデータ漏洩や、意図しない永続化・揮発を招く。
- **出典**: Agentic Design Patterns 8章(Memory Management) 項目27

### 18. 本番環境でInMemorySessionService等のインメモリ実装をそのまま使っていないか(永続ストレージへの置き換えを検討したか)。
- **なぜ重要か**: インメモリ実装は再起動やスケールアウト(複数インスタンス化)で状態が失われ、本番運用に耐えない。
- **出典**: Agentic Design Patterns 8章(Memory Management) 項目28

### 19. 毎回全履歴をコンテキストに詰め込むのでなく、必要な情報を要約・選別してメモリ(短期/長期)に保持しているか。
- **なぜ重要か**: 全履歴の保持はコンテキスト超過・コスト増を招き、Attention計算コストは系列長の2次関数で増大するため非効率になる。
- **出典**: Agentic Design Patterns 8章(Memory Management) 項目29; 生成AIデザインパターン 8章/P28 項目27,28

### 20. エージェントの役割・入出力・成功基準を検証可能な契約(インターフェース仕様)として明文化し、調整ロジック(オーケストレーション)自体に対するテストを用意しているか。曖昧な自然言語の指示だけで分業させていないか。
- **なぜ重要か**: 2025年の実証分析ではマルチエージェントの失敗の40〜80%が技術そのものでなく仕様策定・調整・検証の不備に起因するとされ、曖昧な指示から検証可能な契約を結ぶ関係への進化(Contractorパターン:形式化された契約・動的交渉・品質重視反復・階層的下請け分解)が対策として示されている。
- **出典**: 生成AIデザインパターン 7章/P23, 特徴的な知見; Agentic Design Patterns 特徴的な知見(Agent Companion論文: AgentからContractorへの進化)

### 21. エージェント間通信(A2A)のAgent CardエンドポイントをmTLS・アクセス制御で保護し、エージェント間通信・実行アクションを監査ログに記録しているか。
- **なぜ重要か**: エージェント間通信の認証・認可・監査がなければ、なりすましや不正なエージェントとの連携、インシデント発生時の追跡不能といったリスクを招く。
- **出典**: Agentic Design Patterns 15章(A2A) 項目54,55

### 22. マルチエージェント間通信のオーバーヘッドを考慮し、独立したサブタスクをエージェント間で並列実行しているか。
- **なぜ重要か**: エージェント間通信のオーバーヘッドを放置すると、エージェント数の増加に比例してレイテンシ・コストが膨らみスケーラビリティを損なう。
- **出典**: 生成AIデザインパターン 8章/P23 項目38

### 23. マルチエージェント構成でエラーが発生した際、どの構成要素(どのエージェント/ツール)が失敗したかを具体的に示せる可観測性を備えているか。
- **なぜ重要か**: 失敗箇所が不明なままでは診断・復旧が困難になり、ユーザー・運用者双方が次に何をすべきか判断できない。
- **出典**: AIインターフェースデザイン 6章 項目39

### 24. エージェントがコパイロット(人間主導・提案型)と自律エージェント(自律実行型)のどちらの利用形態を前提とするか明確に設計上決めているか、あるいは両対応にしているか。
- **なぜ重要か**: 自律度のモード選択は権限設計やHITLの要否など他のアーキテクチャ上の前提と直結するため、設計時に明確化しておく必要がある。
- **出典**: 生成AIデザインパターン 10章 項目11
