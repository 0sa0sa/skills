# プロンプト設計・コンテキスト管理

プロンプトの構造化、コンテキストウィンドウ/トークン管理、確信度の扱いなど、LLM呼び出しの「入力設計」そのものを見る。プロンプトチェーンの分割、Lost in the Middle対策、迎合性対策などが対象。

## チェックリスト

### 1. 重要な情報をプロンプトの先頭または末尾に配置し、Lost in the Middle(中央埋没)問題を踏まえた構成にしているか。また「プロンプトを長くする/詳細を詰め込むほど精度が上がる」という前提で冗長に埋めすぎていないか
- **なぜ重要か**: LLMはコンテキスト中央に置かれた情報を見落としやすく、プロンプト長と精度は比例しない。詰め込みすぎるとむしろ悪循環に陥り、重要情報が無視されるリスクがある。
- **出典**: 実践LLMアプリケーション開発 12.4.5(Liu et al.); AIインターフェースデザイン 3章 p.89

### 2. タスクの詳細・制約・出力形式を曖昧な自然文表現に頼らず、明示的な仕様(DSPy Signature等)として定義しているか
- **なぜ重要か**: 曖昧な指示は出力のばらつき(再現性の低さ)を増大させる。
- **出典**: 実践LLMアプリケーション開発 13.2.1

### 3. ゼロショット→フューショット→ファインチューニングの順で段階的に複雑化し、シンプルな手法から試しているか
- **なぜ重要か**: 不要に複雑な手法(ファインチューニング等)から始めると開発コスト・時間を浪費する。
- **出典**: 実践LLMアプリケーション開発 13.2.1

### 4. システムプロンプト/ユーザー入力(クエリ)/指示(作業手順)/会話履歴/スクラッチパッドを、それぞれ別フィールド・別変数・別セクションとして保持し、文字列結合で無秩序に混在させていないか。特にクエリと指示が同じ文字列内に混在していないか
- **なぜ重要か**: 要素が無秩序に混在するとコンテキスト予算の浪費とプロンプトの混乱を招き、指示がユーザー入力に埋もれて従われなくなるリスクがある。これはプロンプトインジェクションの土台にもなる。
- **出典**: 実践LLMアプリケーション開発 12.4.1, 12.5

### 5. 巨大な1つのプロンプトに全工程を詰め込まず、意味のある単位でステップに分割(プロンプトチェイニング)しているか
- **なぜ重要か**: 単一の巨大プロンプトは精度が落ちデバッグが困難になる。
- **出典**: Agentic Design Patterns Ch1 Prompt Chaining #1

### 6. プロンプトチェイニングの各ステップに明確な役割(ペルソナ)を与え、責務を限定しているか
- **なぜ重要か**: 責務が曖昧だと各ステップの出力品質・検証可能性が下がる。
- **出典**: Agentic Design Patterns Ch1 Prompt Chaining #3

### 7. ステップ間・エージェント間の中間出力を自由文字列でなくJSON/XML等の構造化形式で受け渡し、かつそのスキーマを検証(validate)しているか(parse, don't validate)
- **なぜ重要か**: 自由文字列の受け渡しはパースエラーや意味のズレを生みやすく、スキーマ検証を欠くと形式が整っていても内容の不整合(必須フィールド欠落や型不一致)を検出できない。
- **出典**: Agentic Design Patterns Ch1 Prompt Chaining #2; 横断 #85

### 8. CoT(思考の連鎖)の出力順序が「推論→最終回答」になっているか。また推論用プロンプトと最終回答生成用プロンプトを分離し、内部の推論指示がユーザーに漏出(プロンプトリーク)しないようにしているか
- **なぜ重要か**: 順序が逆だと結論が先に固定され推論が後付けの正当化になりやすい。分離しないと内部プロンプトの漏出リスクがある。
- **出典**: Agentic Design Patterns 横断 #86, #88

### 9. few-shot例の提示順序がクラス/カテゴリごとに固まらずシャッフルされているか
- **なぜ重要か**: 同種の例が連続すると出力がその傾向に偏るバイアスを生む。
- **出典**: Agentic Design Patterns 横断 #87

### 10. CoT/ReAct等の推論手法をタスクの複雑さに応じて使い分け、固定的なCoTのみに頼らず推論にかける時間・計算量を調整しているか
- **なぜ重要か**: 単純なタスクに重い推論手法を固定適用するとコスト・レイテンシが無駄になり、複雑なタスクに軽い手法だけで対応すると精度不足に陥る。
- **出典**: 実践LLMアプリケーション開発 8章・10章; Agentic Design Patterns Ch17 Reasoning #59

### 11. 会話履歴を毎ターン無条件に全文追加せず、必要な情報だけを要約・選別して渡しているか。要約による圧縮が不可逆な情報欠落を生むリスクを評価しているか
- **なぜ重要か**: Attentionの計算量は系列長の2次関数で増大するためコスト・レイテンシが悪化し、圧縮で失われた情報は後から復元できず後続タスクに悪影響を与えうる。
- **出典**: 実践LLMアプリケーション開発 12.5/12.5コラム; 生成AIデザインパターン P28; Agentic Design Patterns Memory Management #29

### 12. 複数文書/情報の挿入順序最適化が主に約5000トークン以上の長いコンテキストで効果を持つと理解し、短いコンテキストで過剰に最適化していないか
- **なぜ重要か**: 短文脈では順序効果が小さく、効果が出る状況を見極めずに適用するのは労力の無駄になりうる。
- **出典**: 実践LLMアプリケーション開発 12.4.5

### 13. ルーティング層やプロキシ層が、ユーザーに見えない形で暗黙にコンテキストを切り詰めていないか確認したか
- **なぜ重要か**: 暗黙の切り詰めは原因不明の性能劣化を招き、デバッグを困難にする。
- **出典**: Agentic Design Patterns 横断 #89

### 14. LLMの自己申告による確信度(「80%確信しています」等)をそのまま信頼し、意思決定の根拠やカスケード/ルーターの閾値判断に使っていないか。確信度が必要な場合、確率スコアやSelf-Consistency等の検証済み手法を使い、自己申告のみに依存していないか
- **アンチパターン名**: 自己申告確信度への過信(Unverified Self-Reported Confidence)
- **なぜ重要か**: 自己申告確信度の有効性は未確証であり、根拠の薄い数値を閾値判断等に使うと誤判定のリスクを抱える。検証されていない自己申告だけに頼ると、確信度の値自体が意思決定に使える信頼できる指標にならない。
- **出典**: 実践LLMアプリケーション開発 13.1.1, 13.1.1コラム

### 15. ユーザー向けに確信度を見せる場合、単一のパーセンテージ表示だけで済ませていないか
- **なぜ重要か**: パーセンテージ表示は次トークン確率分布由来の副産物に過ぎず検証不可能であり、数値のもっともらしさが過信を誘発する。
- **出典**: AIインターフェースデザイン 5章 p.155

### 16. 迎合性(sycophancy)に対して、別の視点を提示する等の意図的な摩擦をプロンプト/対話設計に入れているか
- **なぜ重要か**: RLHF最適化自体がユーザーへの同意方向に強いインセンティブを生むため、放置すると誤った同意・追従が増える。
- **出典**: AIインターフェースデザイン 3章 p.87

### 17. スタータープロンプト/テンプレートがプロダクトの能力・位置づけを示す手段として設計されているか。汎用的すぎるプレースホルダーで差別化を曖昧にしていないか
- **なぜ重要か**: スターターは最初の体験でプロダクトの価値と使い方を伝える重要な接点であり、汎用的すぎると差別化が失われ能力も伝わらない。
- **出典**: AIインターフェースデザイン 3章 p.105-106

### 18. CoTのFew-shot実例がモデルの世代交代によって不要・陳腐化していないか、定期的に再検証しているか
- **なぜ重要か**: 新しいモデルでは不要になった例示が残り続けるとノイズとして悪影響を及ぼす可能性があり、メンテナンス負債化する。
- **出典**: 生成AIデザインパターン P13

### 19. エージェントの状態(session.state等)を直接書き換えず、正規の更新経路(output_key/EventActions.state_delta等)を経由して更新しているか。また user:/app:/temp: 等のステートスコープ接頭辞を正しく使い分けているか
- **なぜ重要か**: 状態を直接書き換えると更新がイベント履歴に記録されない禁止パターンとなり、スコープ接頭辞を誤用すると状態の永続性・共有範囲(ユーザー間/アプリ全体/一時的)を誤って設計してしまう。
- **出典**: Agentic Design Patterns Ch8 Memory Management #26, #27
