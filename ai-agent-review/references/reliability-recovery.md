# 信頼性・エラーハンドリング・リカバリ

リトライ戦略、フォールバック、段階的縮退、チェックポイント/ロールバックなど、障害時にシステムがどう振る舞うかを見る。

## チェックリスト

### 1. LLMカスケード/ルーターにおいて、確信度が閾値未満の場合に上位(より高性能・高コスト)モデルへフォールバックする仕組みが「定義されているだけ」でなく実際の制御フロー上で呼び出されることを確認しているか(フォールバックハンドラが実行パスに繋がっていないバグがないか)
- **なぜ重要か**: フォールバック処理を定義しても制御フローに組み込まれていなければ、障害/低確信度ケースで誰も救済されず静かに劣化した結果がそのまま返ってしまう。実際にこの種のバグが報告されている。
- **出典**: 実践LLMアプリケーション開発 13.1.1/13.1.2; Agentic Design Patterns Ch2 Routing(本に明示されたバグ実例)

### 2. 生成→検証→再生成というリトライ方式を使う場合、成功率とp99等のテイル遅延の数理的関係を定量評価しているか(成功率が低いと再試行回数の分布が重くなり尾部遅延が急増することを理解しているか)
- **なぜ重要か**: 成功率pの幾何分布から遅延が導出され、例えば成功率30%では99パーセンタイル遅延を満たすために約13回の再試行が必要になるなど、感覚的な想定を大きく外れる。リトライ設計を誤るとコストとUXが同時に崩壊する。
- **出典**: 生成AIデザインパターン A.アーキテクチャ1/特徴的知見(同書内では『P1』という表記が2章のロジットマスキングパターンと、本項が参照する再試行遅延の数理モデルの両方に使われているため、ここでは後者を指す点に注意)

### 3. リトライ回数の上限を、具体的な「拒否率」や「遅延許容範囲」の根拠に基づいて設定しているか(感覚的な固定回数になっていないか)
- **なぜ重要か**: 根拠のないリトライ回数設定は、過剰な再試行によるコスト膨張か、不足による不要な失敗応答のいずれかを招く。
- **出典**: 生成AIデザインパターン 10章(H.その他78番)

### 4. 例外処理が「検知→ハンドリング(ログ/リトライ/フォールバック/縮退/通知)→リカバリ(ロールバック/診断/自己修正/エスカレーション)」という体系的な3段階モデルに沿って設計されているか
- **なぜ重要か**: 場当たり的なtry-exceptでは検知・対処・復旧の責務が混在し、部分的な障害が想定外の形で全体に連鎖するリスクがある。
- **出典**: Agentic Design Patterns Ch12 Exception Handling and Recovery

### 5. 一次処理が失敗した際、フラグベースのフォールバック処理層、さらに常に安全に提示できる最終層という段階的縮退(graceful degradation)のパイプラインになっているか。また一部機能が使えない場合に全体を停止させず部分的に機能を縮退させているか
- **なぜ重要か**: 一部の失敗で全体を止めると可用性が損なわれる。品質を落としてでも継続できる縮退パイプラインがあれば、ユーザに完全な機能停止を見せずに済む。なお本項は『現在の状態のまま機能範囲を縮小して継続できるか』を問う軸であり、後述の『システムの状態を過去に戻せるか(チェックポイント/ロールバック)』とは別の観点である。
- **出典**: Agentic Design Patterns Ch12 Exception Handling and Recovery; AIインターフェースデザイン 4章 p136

### 6. バッチ処理において1件の失敗が全体の処理を停止させず、スキップ・ログ記録・処理継続・最終報告ができる設計になっているか
- **なぜ重要か**: 1件のエラーでバッチ全体が止まると、残りの正常に処理できたはずの件数まで無駄になる。
- **出典**: Agentic Design Patterns Ch12 Exception Handling and Recovery

### 7. 優先的に使うモデル(またはサービス)が過負荷・利用不可になった際、別モデルへ自動的にフォールバックし、段階的に縮退する仕組みがあるか
- **なぜ重要か**: 単一モデル・単一サービス依存では、そのモデルの障害や過負荷がシステム全体の停止に直結する。
- **出典**: Agentic Design Patterns Ch16 Resource-Aware Optimization

### 8. 情報不足やエラー発生時に処理を停止するのではなく、安全なデフォルト値にフォールバックして処理を継続する設計になっているか
- **なぜ重要か**: 安易な停止はサービス可用性を損なう。安全なデフォルトへのフォールバックなら、処理継続とリスク抑制を両立できる。
- **出典**: Agentic Design Patterns Ch20 Prioritization

### 9. RAGの検索が失敗した場合、単にエラーを返すのではなく、外部ツール等の代替手段へ自動的にフォールバックする設計になっているか
- **なぜ重要か**: 検索失敗を無視して通常の生成を続けると、根拠のない回答を幻覚で埋めてしまうリスクが高まる。代替の情報源やツールへのフォールバック経路を持つことで、根拠不十分なまま応答を続けるリスクを減らせる。
- **出典**: 実践LLMアプリケーション開発 12.8; Agentic Design Patterns Ch14 Knowledge Retrieval

### 10. ナレッジギャップ(RAG検索失敗・情報不足)やドメイン外の要求など「答えられない」状況に対し、幻覚で埋めずに「わからない」と明示的に答えられる設計になっているか。またその拒否応答は、対話から切り離された唐突なエラーとしてではなく、短い説明+穏やかな理由+代替案の提示という形で対話の一部として自然に実装されているか
- **なぜ重要か**: トリガーとなる状況(検索失敗によるナレッジギャップか、そもそもドメイン外の要求か)は異なるが、いずれも『答えられないことを隠さず明示できるか』という同じ核心に帰着する。これを怠ると、知識不足を自信満々な誤情報で埋めてしまう、あるいは唐突で機械的な拒否によって対話そのものを断絶させてしまう、のいずれかに陥る。
- **出典**: 実践LLMアプリケーション開発 12.4.4.2(Chain-of-Note), 12.8; Agentic Design Patterns Ch14 Knowledge Retrieval; AIインターフェースデザイン 5章 p180; 生成AIデザインパターン 10章/H.その他77番

### 11. LLMの内部知識とRAGで取得した情報が矛盾した場合の扱いを設計しているか(矛盾時に確信度が低下する現象を誤情報検出シグナルとして活用できるか等)
- **なぜ重要か**: 矛盾を無視すると、古い内部知識と新しい外部情報のどちらを優先すべきか場当たり的になり、誤った回答を生みやすい。矛盾時の確信度低下は追加の検証コストなしに使える有用な信号であり、活用しないのは機会損失になる。
- **出典**: 実践LLMアプリケーション開発 12.8コラム; 特徴的知見

### 12. チェックポイント/ロールバック機構を持ち、障害発生時に過去の正常な状態へ戻せる(DBトランザクションに類する障害耐性)設計になっているか
- **なぜ重要か**: 復旧手段がないと、部分的な障害がそのまま永続的な不整合状態として残ってしまう。なお本項は『システムの状態をどこまで過去に戻せるか』という軸のチェックであり、後述の『AIの復旧を非決定論的な前進として捉えているか』という出力内容の非決定性の軸とは別物である。両者は矛盾ではなく異なる観点を指しており、状態のロールバックと、出力の再生成は非決定的であることの両方を同時に満たす設計が可能かつ望ましい。
- **出典**: Agentic Design Patterns Ch18 Guardrails; AIインターフェースデザイン 4章 p139/6章 p215

### 13. 処理が途中で失敗した場合、それまでの作業内容・出力・履歴を保持し、ユーザや後続処理をゼロからやり直させない設計になっているか
- **なぜ重要か**: コンテキストを失わせる復旧は、それまでの作業を無駄にし、ユーザの信頼とエンゲージメントを損なう。
- **出典**: AIインターフェースデザイン 4章 p136, p138

### 14. エラー発生後の処理が、単に過去の正常な状態に戻す(ロールバック)ことだけを「復旧」と定義していないか。保持したコンテキストを使って次の一手(新しい提案や代替アプローチ)をユーザーに提示する機能を持っているか
- **なぜ重要か**: AIシステムは非決定論的で同じ入力でも同じ結果には戻らないため、従来型システムのような決定論的な過去回帰をそのまま前提にすると復旧設計そのものを誤る。これは『状態をロールバックできるか』という軸(チェックポイント/ロールバック項)とは別に、『出力内容が非決定的であることを前提に、保持したコンテキストで前に進めるか』を問う軸であり、コード上は『エラー後に前のコンテキストを使った代替案・次の一手を提示する機能があるか』として確認できる。
- **出典**: AIインターフェースデザイン 4章 p138

### 15. 長時間かかるプラン実行を非同期かつ再開可能な設計にし、単一障害点(途中で落ちたら最初からやり直し)を防いでいるか
- **なぜ重要か**: 同期的・単一プロセス依存の長時間実行は、途中の障害で全プランの進行が失われるリスクを持つ。
- **出典**: Agentic Design Patterns Ch6 Planning

### 16. ツール内部で発生したエラーを単なる文字列として返すのでなく、例外として送出し、オーケストレーション層がそれを捕捉して分岐処理できる設計になっているか
- **なぜ重要か**: 文字列化されたエラーはオーケストレーション層が機械的に検知できず、エラーがそのまま握りつぶされたり誤って正常応答として扱われる恐れがある。
- **出典**: Agentic Design Patterns Ch5 Tool Use

### 17. MCP等でツール失敗・サーバ利用不可・不正リクエストが発生した際、LLMが理解し適切な次の行動を選べる形式でエラーを返却しているか
- **なぜ重要か**: LLMが解釈できないエラー形式では、リカバリ判断(リトライ/別手段への切替等)に使えず、無意味な再試行や誤った応答につながる。
- **出典**: Agentic Design Patterns Ch10 MCP

### 18. LLMの出力に対する検証ステップ(Verifierや構造化出力制約など)を設けているか
- **なぜ重要か**: 検証を挟まないと、誤った出力がそのまま後続処理やユーザにまで到達してしまう。
- **出典**: 実践LLMアプリケーション開発 12.4, 10章

### 19. マルチエージェント構成でエラーが発生した際、どの構成要素(どのエージェント/ツール)が失敗したのかを具体的に示せる設計になっているか
- **なぜ重要か**: 失敗箇所が特定できないと診断やリカバリの判断ができず、障害対応が長期化する。
- **出典**: AIインターフェースデザイン 6章 p200

### 20. ReActのような事前にステップ数が決まらないエージェント型タスクでは、従来の固定的な「リトライ回数」概念がそのまま適用できないことを理解し、試行回数や経過時間など別の指標で進捗を示す設計になっているか
- **なぜ重要か**: 固定ステップ前提の進捗表示をそのまま流用すると実態と食い違い、ユーザの期待を誤って誘導してしまう。
- **出典**: AIインターフェースデザイン 6章 p204

### 21. 「再試行」ボタン等の操作が、同じ処理をそのまま繰り返すのではなく新しい応答を生成するものであることをユーザーが理解できる設計になっているか
- **なぜ重要か**: AIの出力は非決定的であり、再試行は同じ結果を保証しない。この性質をユーザーに伝えないと、再試行後に結果が変わったことに対する不信や混乱を招く。
- **出典**: AIインターフェースデザイン 4章 p139

### 22. システムが自動検出できない種類のエラー(事実誤認・不適切な助言など)に備え、ユーザー自身による検証を促す摩擦(確認ステップ、警告表示等)を組み込んでいるか
- **なぜ重要か**: すべてのエラーを自動検出できるわけではなく、検出不能なエラーに対して何の対策もないと、誤った出力がそのままユーザーに受け入れられてしまう。意図的な摩擦の設計が最後の防波堤になる。
- **出典**: AIインターフェースデザイン 4章 p141

### 23. リフレクションループ・自己評価ループ・ループ型エージェントに、上限回数(max_iterations)と収束シグナル(終了条件)の両方を設定し、無限ループを防いでいるか
- **なぜ重要か**: 終了条件のみ、または上限回数のみでは、収束しない場合や終了条件を誤判定した場合に無限ループに陥り、コストとレイテンシが制御不能に膨張する。Reflection・Multi-Agent・Goal Settingの複数章で繰り返し強調される基本パターンである。
- **出典**: Agentic Design Patterns Ch4 Reflection項目11; Ch7 Multi-Agent項目22; Ch11 Goal Setting項目38
